# Design

## Context

См. proposal.md. EchoAccess уже проверяет каноническую owner-идентичность, совпадение всех физических companions HPT/JAM и отдельно обрабатывает персональные mailbox и приватные области. Общие эхи пока разрешаются исключительно через echo.links.

## Goals / Non-Goals

**Goals:** предоставить owner-доступ через единый серверный policy слой, сохранив fail-closed и физические запреты.
**Non-Goals:** новые HPT-подписки, API/Flutter изменения, расширение доступа поинтов, обход повреждённых сообщений или чужих mailbox.

## Decisions

- Сохранять owner-права отдельно для уже проверенных эх, аналогично имеющимся приватным областям. Применять их только после проверок mailbox/private и наличия эхи в policy; обычная ветка links сохраняется.
- can_read=true, can_post определяется writable/role_read_only физической JAM. Последующие lease/IO-проверки остаются обязательными.
- Удаление owner-роли возвращает обычные правила HPT для тех же действующих сессий. Адрес отправителя остаётся из профиля.
- На VPS сменить локальный образ сервера и совместимый worker, сохранив прежние KOI8-R изменения, public TLS, session.key и конфигурацию. Применять под maintenance lock с backup и возможностью возврата на текущий локальный образ.

## Risks / Trade-offs

- Случайное раскрытие mailbox → ветка mailbox остаётся первой; существующие тесты изоляции обязательны.
- Owner-bypass неизвестной эхи → права появляются только после согласования HPT/JAM; тест неизвестной базы.
- Реальная тестовая публикация ушла бы в FTN → успешные записи проверять только на временных JAM; production CreateMessage проверять намеренно невалидным запросом после проверки прав, до мутации.
