# Design

## Context

Мотивация — в `proposal.md`. Текущий `.github/workflows/build.yml` повторяет переносимые проверки в пяти клиентских заданиях. Три backend-задания восстанавливают общий native-prefix, но затем всегда запускают `scripts/release/dependencies.sh`. Ключ `scripts/release/cache_key.py` включает ImageVersion и строку ОС с ядром; изменение образа runner может обнулить полезный кеш без изменения совместимости компиляции.

Скрипт зависимостей уже закрепляет исходники, но хранит версии рядом с процедурой сборки. Prefix содержит не только библиотеки: backend использует исходники Husky, а пакеты включают лицензии и запись ревизий. `ffido-cache.cmake` содержит абсолютные пути. Простая проверка существования каталога недостаточна.

В `release.yml` android-sign ожидает verify; publish уже проверяет verify и android-sign. Android smoke последовательно запускает API 35, 24, 25 и каждый раз собирает QA APK A/B. QA origin содержит динамический порт, поэтому вынести сборку без изменения подготовки fixtures нельзя.

Опорные измерения: успешный стабильный workflow [40305500091](https://github.com/hashev/ffido/actions/runs/40305500091), source SHA `835af21fb1f5fe26c68474c369c13339de1cc880`. Native Linux — 46м22с; macOS Intel clang-tidy — 19м01с; три Android smoke — 10м24с; release APK после матрицы — 4м21с. Это один наблюдаемый запуск, а не статистическая база.

## Goals / Non-Goals

**Goals:** получить проверяемое восстановление готовых зависимостей; убрать дублирование; сохранить платформенные проверки и доверие к релизу; измерить эффект на одинаковом окружении. Критерии приёмки определены в `specs/ci-build-reuse/spec.md`.

**Non-Goals:** новые функции приложения, изменение HTTP-контракта или версий библиотек; перенос на собственные runners; введение внешнего registry; повторное использование PR-пакетов как релизных; сокращение платформенной матрицы или автоматических master-выпусков. Общий API не меняется.

## Decisions

### 1. Единый lock и проверяемый профиль совместимости

В `scripts/release/` добавить машиночитаемый lock источников и инструментов. Перенести существующие ревизии без обновлений; проверить потребителей в CMake и Docker, исключив независимые списки версий. Сохранить Flutter 3.47.7 и enforce-lockfile. Описать поддерживаемые compiler/SDK/target-профили и версии дополнительных кеширующих инструментов; фиксировать доступные версии Android emulator/system image. Валидатор сравнивает фактическое окружение с выбранным профилем и объясняет расхождение.

Fingerprint включает OS/CPU, compiler identity, ABI стандартной библиотеки и системных зависимостей, SDK/deployment target, исходники, параметры и версию схемы сборки. ImageVersion и версия ядра сами по себе не входят в ключ. Выводить нормализованные входы и их различия. Обновление доступного пакета brew/apt не означает автоматическое разрешение нового ABI: нужна проверка профиля либо явная корректировка lock.

Альтернативы: закрепление только имени runner не гарантирует toolchain; закрепление полного образа делает кеш чрезмерно хрупким. Выбрана проверка значимых входов. Точные значения профилей при реализации снять с текущего рабочего окружения, не обновляя библиотеки попутно.

### 2. Компонентные кеши и быстрый путь готового prefix

Выделить записи для Abseil, Protobuf, gRPC и компонентов Husky. Ключ каждого компонента включает транзитивные ключи его зависимостей и общий профиль совместимости. Сборку вести в staging с проверкой конфликтов устанавливаемых путей; публиковать completion manifest только после успеха. Сборка HPT по-прежнему получает согласованный набор Husky.

После восстановления проверить полный набор обязательных файлов, checksums и provenance: библиотеки, заголовки, host tools, исходники helper, лицензии и ревизии. Восстановить relocatable prefix и заново создать `ffido-cache.cmake` для текущего checkout. При подтверждённом комплекте не выполнять configure/build/install. При miss или повреждении пересобрать нужный компонент из закреплённых источников; неполный prefix не считается hit. Исходные build-каталоги не нужны в распространяемом комплекте.

Доверенный workflow прогрева по изменению lock/скриптов в master и ручному запуску наполняет кеш независимо от сборки приложения. Использовать GitHub Actions cache с точными ключами и штатными границами refs: PR может читать разрешённый default-branch cache, но его исполняемые кеши и результаты не продвигаются в релиз. Manifest подтверждает целостность, а доверие к производителю задаётся scope/workflow, не самозаявлением внутри архива. Не применять широкие restore-keys для несовместимых native-prefix.

Альтернативы: кеш одного общего prefix теряет всё при изменении Husky; хранение готовых библиотек в новом registry добавляет инфраструктуру. Компонентные Actions caches сохраняют текущую модель доступа. Основание: [GitHub dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

Для Docker вычислять профиль внутри закреплённого toolchain-слоя, восстанавливать
каждый компонент отдельным точным GitHub cache key и переносить snapshots в
cache mount текущего BuildKit daemon отдельными import/export targets. Основной
image build не зависит от вспомогательных targets, поэтому его слои продолжают
кешироваться. Экспорт сохраняет только завершённые компоненты после проверки
manifest; prewarm охватывает и Docker-профиль без сборки приложения.

Обычный `cache-to: type=gha` не сохраняет cache mounts между daemon:
[ограничение Docker](https://docs.docker.com/build/ci/github-actions/cache/#cache-mounts).
Один локальный mount без переноса snapshots не выполняет требование повторного
использования компонентов на новом hosted runner. Проверить перенос на свежем
BuildKit daemon до измерения GitHub CI.

### 3. Кеш компиляции и успешного анализа с точными входами

Подключить закреплённый compiler cache к backend CMake и проверить работу на Linux и обеих macOS. Ключ учитывает compiler/ABI и параметры; тесты всегда исполняются для текущего commit.

Повторно использовать только полный успешный C++-анализ для соответствующей платформы. Ключ включает все backend sources/headers, генерируемые контракты, параметры compile database, зависимости, compiler/SDK, версию анализатора, `.clang-tidy`, правила и скрипты проверки. Абсолютные пути нормализуются без потери значимых флагов. Хранить проверяемую запись входов и успешного завершения. Не включать случайную identity выпуска, если она не влияет на анализируемые входы; влияющие generated inputs включать обязательно. Отсутствие доказательства, несовпадение или недоверенный producer запускает полный анализ. Не кешировать успех тестов, smoke или сборки приложения.

Альтернатива — только Linux-анализ — исключает платформенные ветки. Анализ остаётся платформенным; форматирование C++ и Dart и Flutter analyze выполняются единожды отдельными обязательными заданиями. Платформенные Flutter tests и все сборки сохраняются. Изменение общего заголовка инвалидирует результат целиком; сложный инкрементальный анализ отдельных translation units не нужен.

### 4. Android: общие fixtures и независимые устройства

Разделить `scripts/update/test_android_flow.py` на подготовку QA APK A/B и выполнение сценария с готовым комплектом. Один producer собирает два APK на запуск. В manifest зафиксировать source SHA, версии/номера, hashes, QA origin и публичные данные проверки. Использовать постоянный локальный порт QA origin: отдельные API runners могут слушать одинаковый порт; конфликт порта явно завершает проверку. У каждого consumer собственные каталог, HTTP server, adb reverse и serial.

API 24/25/35 становятся независимыми заданиями: установка обычного APK, запуск, настоящий system-installer update A→B, сохранность настроек. QA fixtures не принимаются как release-пакеты. Production-ключи не нужны; ограничить срок хранения QA artifacts и не включать закрытые ключи в скачиваемый комплект.

Ограниченное восстановление ADB допустимо при диагностированной транспортной ошибке с проверкой состояния устройства. Не повторять вслепую действия установщика; crash или assertion остаётся ошибкой. Сохранять serial, boot state, logcat и emulator logs при сбое. Альтернатива — повторять целый job — тратит время и скрывает нестабильность.

### 5. Перекрыть подписание, сохранив полный publish gate

`android-sign` зависит от identity и существующих условий доверенного выпуска, а не от verify. Checkout и build используют SHA и identity текущего запуска. `publish` продолжает зависеть одновременно от identity, verify и android-sign; принимает только текущий комплект после существующей проверки состава, подписей и identity. Недоступность production-секретов не превращается в успешный пропуск обязательного подписания. PR не получает дополнительных permissions.

Альтернатива — переиспользовать PR APK — нарушает identity и границы доверия. Параллельная release-сборка сохраняет существующую упаковку и сокращает последовательный хвост, хотя при красной матрице её работа окажется лишней.

### 6. Управление очередью и наблюдаемость

Добавить concurrency только для обновлений одного PR; master, прогрев и стабильные версии не отменяются новым PR. Сохранить обязательные агрегаторы, явно отклоняющие failed/cancelled/skipped зависимости. Правила отмены соответствуют [GitHub concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency).

Сводка каждого запуска показывает очередь отдельно от execution, критический путь, длительности restore/build/analyze/smoke, hit/miss и причины. Долгие шаги дают периодический прогресс; полный native log сохраняется сжатым. Не подавлять диагностику проекта. Сравнить холодный запуск и минимум три тёплых PR-запуска без backend-изменений. Цели: native restore до 3 минут и медиана критического пути до 20 минут без очереди. Для backend-изменений замерять отдельно; обещание 20 минут на любую холодную сборку не задаётся.

## Risks / Trade-offs

- Неполный fingerprint → негативные тесты на compiler/ABI/flags/headers и консервативный miss при неизвестном входе.
- Кешу с истёкшим сроком хранения нужен холодный build → сохранить рабочий fallback и доверенный прогрев; отсутствие кеша не ломает корректность.
- Несовместимость компонентов или абсолютные пути → manifest DAG, проверка конфликтов и тест восстановления в другом checkout.
- Параллельные Android jobs увеличивают runner-minutes и очередь → измерять отдельно время исполнения, ожидание и стоимость; сохранить минимально необходимые три API.
- Повторное использование анализа может скрыть изменение → точный полный ключ, проверяемое успешное завершение, тесты инвалидации и доверенная область кеша.
- Очереди и дрейф hosted runners мешают целевому времени → публиковать фактические результаты; превышение цели означает незавершённую приёмку производительности, а не повод ослабить проверки.

## Migration Plan

1. Зафиксировать baseline и контракт входов; добавить тесты ключей и manifests.
2. Ввести новый namespace кеша, быстрый путь и доверенный прогрев; старые записи не переименовывать в совместимые.
3. Добавить compiler/analysis cache, затем переразложить проверки и Android fixtures.
4. Изменить DAG подписания и протестировать негативные условия публикации без публикации реального выпуска.
5. Выполнить холодные/тёплые CI-прогоны, проверить полную матрицу, оформить сравнение в документации.

Откат: вернуть прежние workflow и отключить новый namespace. Рабочие данные приложения и опубликованные выпуски не мигрируют; кеши можно удалить без потери исходников и возможности холодной сборки.


## Исправление ошибки, обнаруженной при CI-приёмке

Повторный Windows smoke выявил WinError 32 при удалении launch probe. Main и
UpdateShell одновременно подтверждали запуск; loading shell мог читать probe
после того, как другой callback уже опубликовал ready. Сохраняется один publisher
в main после initializeApp и первого frame; дублирование в UpdateShell удаляется.
Desktop smoke продолжает проверять тот же nonce и удалять marker при работающем
клиенте. Widget-тест контролирует отсутствие startup probe I/O у UI-оболочки.
Это точечное исправление обязательной проверки по запросу устранить ошибки CI,
без изменения HTTP-контракта, состава матрицы или допуска к публикации.
