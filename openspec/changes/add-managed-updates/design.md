# Design

## Context

Мотивация — в proposal.md. Сейчас scripts/release/version.py задаёт общую identity; package.py создаёт BUILD.json и package sidecar, publish.py собирает release-manifest.json и публикует полный набор через draft. container_publish.py сохраняет неизменяемые version-теги и digest. Эти реализации переиспользуются.

apps/backend/src/main.cpp принимает CONFIG/FIDOBACK_CONFIG и обрабатывает SIGTERM, но не имеет команд версии/обновления. Серверный tar.gz включает несколько binaries и lib. README уже рекомендует внешнее состояние и отдельный каталог новой версии.

apps/frontend/lib/main.dart восстанавливает сессию при старте; проверка обновлений должна запускаться независимо от этого результата. settings.dart — экран подключения, поэтому сведения об обновлениях выносятся в отдельный экран с доступом из главного экрана и экрана подключения. desktop_profile.dart и macOS runner обеспечивают независимые профили. macOS Release.entitlements включает sandbox. Android-пакет имеет постоянный release-ключ; macOS ad-hoc, Windows unsigned. Установочная подпись обновлений не устраняет предупреждений Gatekeeper/SmartScreen.

## Goals / Non-Goals

**Goals:** один понятный путь «уведомление → Обновить → загрузка → установка», общая проверяемая модель релиза, замена полного комплекта, сохранение состояния, предсказуемая ошибка на каждом этапе. UI-ориентир Telegram описывает удобство, а не требование повторить его внутренний протокол.

**Non-Goals:** установка без согласия пользователя, фоновые OS push-уведомления при закрытом клиенте, магазины, обход подтверждений ОС, собственный backend обновлений, горячая замена сервера, новые миграции данных, изменение gRPC-контракта. Доставка Developer ID/notarization и Authenticode не обязательна для этой задачи, статус подписи остаётся явным.

## Decisions

### 1. GitHub Releases и единый подписанный manifest

Расширить release-manifest.json добавочными полями schema_version, update_sequence, packages[].size, структурированными platform/min_os и compatibility. Сохранить identity/packages/container для прежних потребителей. Подпись Ed25519 — отдельный файл над точными UTF-8 байтами манифеста, без повторной сериализации при проверке. Ключ с key ID встроен в updater; приватный ключ доступен только trusted release. Ротация — переходный выпуск, добавляющий новый публичный ключ, прежде чем новые релизы перестанут подписываться старым. PR подписывает fixtures отдельным тестовым ключом.

Совместимость: protocol_major и диапазон поддерживаемых major клиента/сервера; state_schema_min/max для SQLite, config_format и jam_format. Это декларация поддержки существующих форматов, а не разрешение миграции. Неизвестные значения блокируют серверное apply. Для клиента сведения о сервере сейчас не передаются протоколом: updater не утверждает совместимость с подключённым сервером и не требует синхронного обновления обеих сторон. Показывать примечания о совместимости; протокол в этой задаче не расширять.

Проверка HTTPS через GitHub Releases API с пагинацией, кешем ETag и обработкой rate limit. Draft исключается; ссылки на пакеты берутся только из проверенных метаданных и сверяются с assets ожидаемого репозитория. Разрешать HTTPS redirects GitHub к его asset CDN без передачи credentials FFIDO. Ограничить время, размер ответа/скачивания, число redirects; не исполнять команды из манифеста. Отдельный сервис отвергнут как дополнительная инфраструктура без необходимости.

Версия сравнивается численно по SemVer, не строкой и не published_at. Для dev одного base сравниваются build number, SHA не используется для сортировки. Stable при том же base новее dev; Android дополнительно требует строго больший versionCode. Локальные check-сборки не обновляются автоматически. Канал по умолчанию соответствует сборке (stable/dev); пользователь может сменить его, но downgrade не запускается. Дополнительно монотонный update_sequence в подписанных данных и запомненная максимальная последовательность защищают от возврата к ранее виденному старому manifest. Это не доказывает свежесть при первом запуске; HTTPS и доверенный репозиторий остаются частью модели доверия.

### 2. Поведение уведомлений

Проверять после запуска UI и при возвращении в foreground не чаще раза в 6 часов, ручную проверку разрешать отдельно с учётом Retry-After. Состояния: проверка, доступно, загрузка, проверка пакета, готово к установке, установка, ошибка. До действия пользователя скачиваются только небольшие метаданные. Уведомление встроено в приложение, не модально: «Доступна версия …», «Обновить», «Позже». После «Позже» скрыть до следующего запуска; экран обновлений доступен всегда. При загрузке кнопка показывает прогресс; ошибки предлагают повторить. Установку и перезапуск не запускать поверх активной отправки или несохранённого текста: дождаться завершения и получить решение сохранить/отложить при необходимости. Не добавлять обход в браузер в обычный успешный путь.

### 3. Платформенные установки

**Android:** нативный bridge к PackageInstaller, private staging APK, REQUEST_INSTALL_PACKAGES после клика, переход в настройки разрешения при необходимости, обработка STATUS_PENDING_USER_ACTION, отмены и результата. До передачи проверить package ID, versionCode и сертификат подписи APK против текущей установки; после установки ОС сохраняет app data. Не использовать Play In-App Updates для sideload APK. API 24–25 и 26+ проверяются отдельно из-за различий разрешений. Основание: https://developer.android.com/reference/android/content/pm/PackageInstaller и https://developer.android.com/distribute/marketing-tools/alternative-distribution .

**macOS:** закрепить актуальный совместимый Sparkle 2 на этапе реализации без обновления Flutter. Использовать штатные installer XPC и entitlements для sandbox, native bridge с кастомным UI-driver для общего уведомления Flutter. Installer проверяет EdDSA-подпись архива; feed генерируется из того же release identity/manifest. Appcast — подписанный immutable asset каждого релиза; URL выбранного appcast извлекается из проверенного manifest. Подписываются сначала пакет и appcast, затем manifest с их hash/size; циклических подписей нет. Обновлять весь .app, не отдельный executable. Все процессы одного bundle координируются native lock; перед установкой каждый профиль подтверждает готовность к выходу, журнал открытых profile IDs позволяет восстановить окна и аргументы --profile после перезапуска. Не менять sandbox, bundle ID и namespaces Keychain/preferences. По решению пользователя сохраняется ad-hoc: системный запрос Keychain или повторный вход после обновления допустимы. Ошибка доступа к Keychain не должна мешать открытию UI; показать предложение разрешить доступ либо войти повторно, сохранив настройки. Испытать реальную ad-hoc сборку со Sparkle/XPC; если штатная установка требует другой подписи, зафиксировать блокер выпуска, а не подменять обновление ручным DMG. Основание: https://sparkle-project.org/documentation/sandboxing/ и https://sparkle-project.org/documentation/publishing/ .

**Windows/Linux:** небольшой отдельный updater рядом с приложением. Запускается с доверенными параметрами и повторно проверяет manifest и hash. Ждёт завершения всех процессов этой установки, распаковывает полный bundle в соседний staging и переключает каталоги с журналом восстановления при сбое между rename. Запретить traversal, абсолютные пути, выход через symlinks и превышение лимитов распаковки. Сохранить предыдущий комплект до успешного запуска. Установки для текущего пользователя обновляются напрямую; при отсутствии прав дать понятную инструкцию перемещения/системного разрешения. Не писать данные профиля в bundle. Собственный macOS installer отвергнут в пользу готового Sparkle; унифицированная загрузка с ручным открытием архива не соответствует согласованному UX.

### 4. Native сервер: подготовка и переключение

Команды `fidoback --version`, `fidoback update check [--channel stable|dev]`, `fidoback update download [--version VERSION] --install-root ROOT`, `fidoback update apply --install-root ROOT --config CONFIG`, `fidoback update rollback --install-root ROOT --config CONFIG`. check/download не открывают рабочие JAM/SQLite. Реализация CLI переиспользует имеющийся Python 3 как runtime helper рядом с ffido-run-hpt; добавить ffido-update в серверную упаковку, main.cpp диспетчеризует update до загрузки рабочего конфига. Использовать проверенную криптобиблиотеку, не собственную реализацию Ed25519; точную зависимость закрепить после проверки наличия совместимого backend в сборках.

Managed layout: ROOT/releases/<tag>/bin, lib, share и ROOT/current как атомарно переключаемый symlink. Служба использует ROOT/current/bin/fidoback CONFIG. Внешние конфиг/состояние не копировать и не менять. Проверять ownership, write permissions, место, lock обновления, остановку экземпляра и допустимость state schema до переключения. Для определения работающего экземпляра переиспользовать существующую instance lease; проверка должна удерживать её до завершения apply. Чтение SQLite schema для preflight — только после остановки сервера, без миграций. Старый и новый пакеты проверяются целиком; запретить применение поверх незнакомой структуры и in-place смешивание lib.

Существующий бинарник или helper может работать из старого каталога во время смены symlink. apply не запускает daemon: последовательность для foreground — stop → apply → start, для systemd/launchd — stop service → apply → start service → readiness check. Системный supervisor остаётся владельцем процесса, команды не угадывают имя службы и не вызывают sudo. Документация даёт готовые последовательности; установка не происходит автоматически при запуске. После старта выполнить ограниченную по времени TLS gRPC-проверку с конфигурируемым доверенным CA/именем; проверка не публикует сообщения. Добавить CLI режим проверки готовности, используемый также Docker wrapper.

Rollback использует предыдущий каталог и проверку текущей schema/форматов. Не обещать откат данных. Любая заявленная миграция вне диапазона блокирует apply до отдельной процедуры резервирования/миграции. Не включать в этот change механизм автоматического backup живых JAM: это требует остановки HPT и согласованного окна обслуживания.

### 5. Docker: host wrapper и Compose

Добавить пример deploy/docker/compose.yaml и host helper scripts/update/ffido-docker-update.py, использующий общие Python-модули проверки manifest. Интерфейс check/apply/rollback с обязательными --compose-file и --service; image override хранится в отдельном управляемом файле, пользовательский Compose не переписывается. apply проверяет подпись, совместимость и наличие mounts, запоминает предыдущий digest, скачивает hashev/ffido@sha256:… и вызывает compose up -d --no-deps для одного сервиса. Запретить смену проекта/сервиса по данным манифеста. Хранить журнал операции и обрабатывать повторный запуск после обрыва.

В примере Compose добавить проверку готовности через CLI TLS gRPC probe; host helper ждёт её с timeout и проверяет identity образа. Не считать running равным ready. После сбоя оставить понятную диагностику и команду отката; автоматического rollback по умолчанию нет, так как новый сервер мог изменить состояние. Перед rollback проверить совместимость текущего состояния с предыдущим выпуском. Для произвольного существующего docker run документировать переход к Compose с прежними mounts без удаления данных. Native apply внутри образа отказывает по встроенному признаку container distribution. Docker socket внутрь контейнера не монтируется.

## Risks / Trade-offs

- [macOS XPC, ad-hoc и профили] → ранний сквозной эксперимент двумя упакованными версиями обязателен до завершения платформенной реализации; не считать unit-тесты доказательством установки.
- [Android требует подтверждения ОС и иногда разрешения источника] → штатные диалоги после клика; не обещать бесшумную установку. Сходство с Telegram относится к UX внутри приложения.
- [Старые релизы без подписей] → только ручной bootstrap; не доподписывать и не заменять публичные assets задним числом.
- [Windows/Linux portable layouts различаются] → поддерживать явный layout, ошибку прав и документированный переход, тестировать весь bundle и DLL/lib.
- [Смена форматов данных] → неизвестная совместимость блокирует apply/rollback; резервирование согласуется с HPT.
- [Недоступность GitHub/лимиты] → ETag, backoff и не блокирующая работа клиента.
- [Компрометация ключа обновлений] → изолированный release environment, публичный key ID и переходная ротация; полное восстановление доверия при потере всех доверенных ключей потребует ручной установки.

## Migration Plan

1. Добавить и проверить release metadata/signing, затем упаковать updater во все обязательные пакеты; текущий публичный выпуск не изменять.
2. Один раз вручную установить первый клиент с updater. На Android сохранить application ID и release key; локальный старый com.example.fido остаётся отдельным приложением.
3. Остановить обычный сервер, перенести полный текущий пакет в managed releases и настроить current/путь службы, сохранив внешние данные. Для незнакомого layout показать инструкцию, не мигрировать его автоматически.
4. Для Docker сохранить mounts/UID/GID и перейти на пример Compose либо подключить wrapper к существующему сервису.
5. Проверить переход A→B на каждой платформе с синтетическими данными и двумя профилями macOS; выполнить отрицательные проверки подписи, отмены, сети, места и отката. После этого выпустить новую версию. Production базы не используются для испытаний.
