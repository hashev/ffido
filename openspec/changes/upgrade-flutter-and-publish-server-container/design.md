# Design

## Context

См. мотивацию в `proposal.md`. Локально и в трёх местах workflows используется Flutter 3.41.6 / Dart 3.11.4. Клиент задаёт SDK `^3.9.0`, runtime grpc/protobuf закреплены, генератор `tools/proto` использует protoc_plugin 25.1.0 и protoc 36.2. CI проверяет генерацию контракта, собирает macOS arm64/x86_64, Windows/Linux x86_64 и Android APK.

Сервер C++23 собирается корневым CMake. `scripts/release/dependencies.sh` закрепляет native protobuf/gRPC/Husky/HPT; `package.py` собирает переносимый пакет с библиотеками и лицензиями. CMake устанавливает fidoback, ffido-admin, ffido-hpt-auth и Python-wrapper ffido-run-hpt. Сервер принимает путь конфигурации аргументом, TLS обязателен; helper ищется рядом с executable. SIGTERM уже обрабатывается сервером. Конфигурация-пример слушает loopback: для контейнера нужен отдельный документированный пример с `0.0.0.0`.

Рабочее дерево содержит большой незакоммиченный перенос в монорепозиторий; реализация должна сохранить эти изменения. Существующие release-specs требуют полного проверенного набора и запрещают выдавать пропуск за успех.

## Goals / Non-Goals

**Goals:** согласованный закреплённый SDK, проверяемые обновления зависимостей, автономный серверный runtime и публикация проверенного контейнера в существующем релизном процессе.

**Non-Goals:** обновление всех C++-библиотек, изменение wire-контракта, схем данных, текущих платформенных минимумов без технической необходимости; контейнерный Web-шлюз, multiarch и оркестрация FTN-ноды.

## Decisions

### 1. Последний stable выбирается и фиксируется при apply

Получить точный актуальный релиз из официального Flutter release manifest, сохранить версию/Dart/дату проверки и обновить все установки SDK в CI и инструкции. Не использовать плавающий `stable` без номера: повторная сборка должна воспроизводиться. Не обновлять общий SDK разработчика молча; при необходимости использовать отдельную установку для проекта.

Снять `flutter pub outdated --json` до и после, обновить major constraints прямых зависимостей и lockfile. Согласовать `tools/proto` и runtime, регенерировать только затронутые generated-файлы и mocks. Нативный protoc 36.2 сохранить, если обновлённый Dart-генератор совместим; при доказанной несовместимости согласованно обновить связанные native pin и проверки версии, сохраняя wire-контракт. Не добавлять транзитивные пакеты в прямые и не использовать dependency_overrides для устранения сообщения outdated. Для каждого отставания от Latest записать цепочку ограничений: SDK pin или ограничение внешнего пакета. Это соответствует различию Resolvable/Latest в официальной документации Pub.

### 2. Многостадийный Dockerfile использует существующую сборку

Контекст — корень монорепозитория. Builder на Ubuntu 24.04 с clang-19 повторяет Linux-инструменты CI, `dependencies.sh`, корневые CMake configure/build/CTest и существующую упаковку сервера. Базовые builder/runtime образы закрепить digest при реализации. В runtime перенести проверенный staged server bundle с его библиотеками и лицензионными материалами, используя существующую логику упаковки вместо второго перечня native-зависимостей. Python 3 необходим wrapper; системные runtime-библиотеки установить явно и проверить ldd. Runtime не содержит Flutter, компилятора, рабочего дерева исходников, тестовых сертификатов и кешей. По согласованному решению пользователя лицензионные архивы исходников и материалы перелинковки сохраняются внутри образа. Предусмотреть упаковке необходимые метаданные зависимостей без установки Flutter в runtime.

Предпочесть Ubuntu runtime для согласованности glibc с builder; Alpine потребовал бы отдельной проверки musl. Извлечение произвольного внешнего архива вместо сборки из текущего SHA ухудшило бы связь с release identity.

### 3. Явные mounts и непривилегированный процесс

Рабочий каталог `/var/lib/ffido`, бинарники `/opt/ffido/bin`, конфиг `/etc/ffido/config.json`; exec ENTRYPOINT запускает fidoback с этим конфигом по умолчанию. UID/GID по умолчанию 10001:10001, допускается `--user UID:GID` для прав хоста. Каталоги и права подключаемых данных готовит оператор; автоматический рекурсивный chown FTN-базы недопустим.

Документировать read-only mounts конфигурации и сертификатов, writable state для SQLite/session key/uploads, FTN mounts с правами согласно операциям и общий coordination lock с внешним HPT. Согласовать `path_mappings` с контейнерными путями и включениями hpt.cfg. Использовать существующее место uploads, вычисляемое сервером; проверить его попадание на постоянный mount. Не запускать HPT-демон в контейнере; wrapper доступен для существующего внешнего процесса координации.

`.dockerignore` исключает локальные config.json, данные FTN/SQLite/uploads, ключи, VCS и build-кеши; COPY использует явный набор исходников. Публикуется порт 8080, пример слушает `0.0.0.0`, доверие сертификату остаётся обязательным. Не вводить health endpoint: readiness проверяется существующим TLS gRPC.

### 4. Проверяется тот же образ, который публикуется

Добавить container job в reusable `build.yml` и обязательный агрегатор. Собрать локальный OCI/Docker-артефакт, запустить на синтетической FTN-fixture с временными TLS и writable mounts, проверить запрос/авторизацию, административные инструменты, SIGTERM, ошибки конфигурации, пересоздание с теми же данными и отсутствие секретов в образе. Переиспользовать fixtures и проверки `check_acceptance.py`, адаптируя запуск к Docker. PR сохраняет артефакт без авторизации в Docker Hub. Публикация загружает именно этот проверенный образ текущего запуска и проверяет identity/SHA; повторной независимой сборки после smoke нет.

### 5. Docker Hub — часть существующего доверенного выпуска

Реестр `docker.io/hashev/ffido`; версия берётся из `scripts/release/version.py`/identity, без второго алгоритма версионирования. Для master публикуются уникальная prerelease-версия и `sha-<40 символов SHA>`; для stable `X.Y.Z`, SHA и `latest`. OCI labels включают source/revision/version/licenses. Digest записывается в release manifest/notes, оператор может использовать `image@sha256:...`.

Оставить `FFIDO_PUBLICATION_READY` и environment `release`. В доверенный этап передавать `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` с правом записи только нужного репозитория. Actions закреплять полным commit SHA согласно существующим workflows. Проверенная политика репозитория допускает только GitHub-owned actions и subosito; пользователь отдельно одобрил добавление только двух используемых SHA docker/setup-buildx-action и docker/login-action. Политику verified_allowed=false и остальные ограничения сохранить. Учетные данные не нужны при PR.

Сначала проходят все существующие release-gates, включая Android-подпись, и container smoke. Затем публикуется образ; полный GitHub Release завершается после успешного Docker push и регистрации digest. Между GitHub и Docker Hub нет атомарной транзакции: при частичном успехе повтор продолжает публикацию того же выпуска. Перед push проверять существующий version-тег: тот же digest допускает идемпотентный повтор, другой блокирует выпуск. По уточнению пользователя SHA-тег сохраняет первый проверенный образ коммита; позднейший stable с другими метаданными получает отдельный тег версии и latest. Для существующего SHA-тега проверяется source revision. Сериализовать публикации и перед обновлением `latest` сравнивать стабильные версии, чтобы запоздавший старый релиз не откатывал alias.

## Risks / Trade-offs

- Major-обновления могут потребовать миграции плагинов, mocks или платформенных настроек → минимальные правки, полный существующий matrix build; повышение минимальной ОС описать явно, если оно неизбежно.
- Часть Latest может оставаться недоступной из-за SDK pins → отчёт outdated/deps с причинами, без обещания нулевого числа предупреждений.
- Native-сборка дорогая → использовать существующие pins и BuildKit cache без подмены исходного SHA или пропуска тестов.
- Bind mounts и внешний HPT зависят от UID/GID и файловых блокировок → проверить на Linux Docker с синтетическими данными; сетевые FS без гарантии locks не заявлять поддерживаемыми.
- Доступность Docker Hub и права `hashev/ffido` не подтверждены: страница управления недоступна для публичного чтения → проверка credentials и push относится к этапу выпуска, ошибка должна быть явной.
- Локальная macOS не подтверждает Windows/Linux/Android сборки → выполнить доступные проверки локально, остальное подтвердить CI и обозначить ограничения.

## Migration Plan

1. Зафиксировать исходный отчёт зависимостей, обновить SDK/constraints/lockfiles и необходимые миграции, выполнить проверки клиента и генерации контракта.
2. Добавить Docker-сборку, пример конфигурации и проверку контейнера; подключить к обязательному CI.
3. Подготовить workflows публикации и документацию по secret-настройкам, тегам, pull/run, mounts и внешнему HPT. Настройку секретов не сохранять в репозитории.
4. При разрешённом выпуске проверить опубликованный digest через pull и повторный smoke. Если push недоступен, явно оставить внешнюю проверку невыполненной.
5. Rollback SDK — согласованное восстановление предыдущих pins/lockfiles. Rollback сервера — запуск прежнего digest с сохранёнными mounts; миграций форматов данных это изменение не вводит.

Источники решений: [Flutter SDK archive](https://docs.flutter.dev/install/archive), [Pub outdated](https://dart.dev/tools/pub/cmd/pub-outdated), [Docker: test before push](https://docs.docker.com/build/ci/github-actions/test-before-push/). Точные версии проверяются при apply; номер из поисковой выдачи не считается закреплённой версией SDK.
