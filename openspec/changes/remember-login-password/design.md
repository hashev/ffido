# Design

## Context

Нативный клиент уже использует flutter_secure_storage для сессий и локальную изоляцию macOS профилей. Пароль намеренно не сохранялся. Сервер закрепляет имя первого входа, поэтому диагностический Login с произвольным именем загрязнил профиль узла.

## Goals / Non-Goals

Сохранить пароль без plaintext preferences и без смены протокола. Не переименовывать профиль при каждом Login, не менять старые письма, не выполнять автоматический повтор входа с потенциально устаревшим паролем.

## Decisions

- Отдельная запись защищённого SessionStore содержит адрес и пароль, ключ включает endpoint и наследует namespace локального DesktopProfile.
- Пароль записывается только после успешной проверки сервером. Флаг блокировки в preferences предотвращает возврат старой записи при неудачном сохранении или удалении. В preferences хранятся только несекретные метаданные и эти флаги.
- При истечении сессии пароль остаётся доступен для скрытого заполнения формы. При явном выходе удаляются оба секрета. Web сохраняет прежний вход только в памяти.
- Автоматически заполненный пароль очищается при смене сервера или адреса; асинхронное чтение хранилища не затирает новые правки пользователя. Заполненный сохранённый пароль не считается несохранённым черновиком для обновлений.
- Исправление имени на amster2 — адресная транзакция users.name после SQLite backup. Сохраняются user_id, FTN-адрес, токены и все личные отметки. Проверка JAM хэшами; диагностические входы используют настоящее имя существующего пользователя.

## Risks / Trade-offs

При недоступном Keychain/Keystore ручной вход остаётся доступным; plaintext fallback отсутствует. Старый сохранённый пароль после смены серверного пароля нужно исправить вручную. Введённое в Login имя существующего профиля не переименовывает серверную идентичность.

## Migration Plan

Для новых клиентов запись создаётся при следующем успешном входе. Ранее не сохранённый пароль восстановить невозможно. Выход очищает запись и ставит tombstone даже при ошибке хранилища.
