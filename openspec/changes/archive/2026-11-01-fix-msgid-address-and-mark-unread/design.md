# Design

## Context

`OriginAddress` в `apps/backend/src/service/message_service.cpp` возвращает OADDRESS либо первый токен MSGID после проверки `ValidFtnAddress`. Последняя использует числовой `CanonicalFtnAddress`, поэтому `2:5001/100@fidonet` отклоняется. Один helper уже используется и для `from_address`, и для адресации ответа. Это позволяет исправить поведение без переписывания JAM и без изменения авторизации.

Прочитанность хранится как наличие строки `read_status(user_id, conference_id, generation, message_id)` в SQLite. `GetMessage` через `RecordMessageView` всегда отмечает просмотр, обновляя историю и позицию. Есть MarkRead и массовый MarkConferenceRead, но нет обратной операции. В клиенте `open()` также добавляет письмо в `opened`; навигация непрочитанных исключает этот набор даже при `isRead=false`.

## Goals / Non-Goals

**Goals:** единая корректная адресация из доменного MSGID; одна персональная операция непрочитанности с согласованным возвратом в список; сохранность JAM, истории, позиции и изоляции сессий.

**Non-Goals:** домены в адресах входа и профиля, маршрутизация по разным FTN-сетям, исправление исходных баз, массовая пометка непрочитанности, контекстное меню каждой строки списка, изменение правил кодировки или общий рефакторинг диагностики отправки.

## Decisions

### 1. Разбор домена только в резервном источнике адреса

Сохранить числовой парсер и его использование в авторизации без изменений. В узком helper извлечения из MSGID разделить первый адресный токен на числовую часть и необязательный домен, затем канонизировать числовую часть существующим парсером. Требовать непустой идентификатор после пробела/табуляции, не более одного `@`; домен ограничить 1–255 ASCII символами букв, цифр, дефиса и точки, с буквой/цифрой на обоих концах. DNS не используется. Корректные домены не ограничивать строкой `fidonet`. Непустой OADDRESS сохраняет приоритет и прежние проверки при отправке; не восстанавливать адрес из Origin/тела при повреждении MSGID.

Выбор вместо альтернативы «разрешить @domain в CanonicalFtnAddress» не расширяет допустимые идентичности пользователя и явные FTN-адреса. Полный MSGID остаётся неизменным для REPLY; `.0` канонизируется как существующим числовым парсером.

### 2. Добавочный RPC и удаление персональной отметки

Добавить `MarkUnread(MessageReference) returns (google.protobuf.Empty)` в `contracts/ffido/v1/ffido.proto` без изменения MarkRead и номеров существующих полей. C++ сервис повторяет проверки доступа, существования и поколения из MarkAsRead, не вызывая GetMessage/RecordMessageView. MetadataStore получает узкую операцию удаления строки read_status по всем четырём ключам; отсутствие строки — успех. Использовать существующий mutex/порядок SQLite для сериализации с чтением и массовой отметкой. Миграции схемы нет, история и позиция не обновляются.

Альтернатива с bool в прежнем MarkRead несовместима со старыми серверами; отдельная таблица overrides избыточна, поскольку все текущие отметки, включая bulk, уже представлены строками read_status. Идемпотентность означает set-unread без промежуточного чтения, а не отмену будущих просмотров. Автоматические повторы изменяющего RPC не добавляются.

### 3. Серверное подтверждение перед закрытием письма

Добавить действие в меню экрана чтения, только когда есть selected и право чтения поддерживаемой JAM. Во время запроса сериализовать его с открытием, навигацией и массовой отметкой. Использовать epoch, version и cancellation по образцу существующих действий; поздние ответы не применяются.

При успехе удалить идентичность из `opened`, обновить `isRead=false` в текущих строках, закрыть selected и вернуть список прежнего контекста без сброса фильтра/сортировки/цепочки. Инвалидировать кеш конференций, обновить список и счётчики; не вызывать getMessage при обновлении, не запускать автоматическое продолжение чтения. Ошибку актуализации после подтверждения отделять от ошибки самой команды. При неуспехе команды сохранить экран и позволить явный повтор. Дополнительное подтверждение обратимого действия не требуется.

### 4. Совместимость

Старый клиент с новым сервером продолжает работать. Новый клиент на старом сервере получает UNIMPLEMENTED для новой команды и показывает понятное требование обновить сервер; остальной API остаётся работоспособным. Не вводить capability negotiation только ради этой команды и не подменять её локальной отметкой. Обновить Dart transport, API client, fake transport и сгенерированные файлы штатным `tools/proto/generate.sh` (закреплённый protoc 36.2); C++ контракт собирается существующим CMake.

## Risks / Trade-offs

- [Слишком широкое удаление read-state] → тестировать точный user/conference/generation/message, разные профили и одинаковые номера баз.
- [Письмо сразу снова прочитано] → возврат к списку без GetMessage; тестировать `opened`, обновление списка и повторное ручное открытие.
- [Другое устройство читает после MarkUnread] → серверный порядок фиксации определяет состояние; новая операция не запрещает будущие просмотры.
- [Повтор завершённого bulk отменит пометку] → регрессионный тест прежнего operation_id: повтор не вставляет удалённую персональную строку заново.
- [Старый сервер не умеет RPC] → отдельное сообщение для UNIMPLEMENTED без ложного успеха.
- [Исторические спецификации после архивирования шаблона без sync описывают прежнее оформление] → это изменение не синхронизирует чужой архив и не меняет шаблоны; интеграционные тесты учитывают текущую реализацию v1.0.14.

## Migration Plan

Рекомендуемый порядок будущего развёртывания: сервер с новым RPC и извлечением адреса, затем клиент. Схемы SQLite и JAM неизменны; откат сохраняет данные и прежние API, но старый сервер снова не предоставляет MarkUnread и сохраняет прежнее ограничение доменного MSGID. Никакие рабочие файлы или журналы доставки на этапе реализации автоматически не исправляются.
