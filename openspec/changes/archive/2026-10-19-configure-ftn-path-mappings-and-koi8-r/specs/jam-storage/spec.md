# Spec Delta

## ADDED Requirements

### Requirement: KOI8-R через существующую настройку кодировки
`ftn.default_encoding` SHALL поддерживать KOI8-R для новых публикаций и резервного чтения сообщений без CHRS либо с IBMPC; отсутствие настройки SHALL сохранять CP866. Явный поддерживаемый CHRS SHALL иметь приоритет при чтении. Неизвестные или противоречащие CHRS SHALL оставаться ошибкой. Чтение SHALL не перекодировать файлы базы.

#### Scenario: База KOI8-R
- **WHEN** настройка равна KOI8-R и сообщение без CHRS либо с IBMPC содержит русский текст и текстовые подполя в KOI8-R
- **THEN** API возвращает правильный Unicode, включая Ё/ё, без изменения JAM

#### Scenario: Смешанные сообщения
- **WHEN** настройка равна KOI8-R, а письмо явно помечено CP866 либо UTF-8
- **THEN** декодирование использует CHRS письма, сохраняя прежние ошибки неизвестных и противоречащих кодировок

#### Scenario: Прежний профиль
- **WHEN** настройка отсутствует либо явно задана CP866
- **THEN** сохраняются прежние правила чтения и публикации CP866

### Requirement: Публикация KOI8-R без потерь
При `ftn.default_encoding=KOI8-R` публикации и ответы API SHALL сохранять тело, тему и имена в байтах KOI8-R с `CHRS: KOI8-R 2`, независимо от CHRS родителя. Непредставимый текст SHALL отклоняться до мутации JAM без замены, транслитерации или переключения кодировки. Правила адресов, MsgID, идемпотентности и существующая нормализация исходящего текста SHALL сохраняться.

#### Scenario: Независимый эталон
- **WHEN** клиент публикует русское сообщение с Ё/ё при настройке KOI8-R
- **THEN** байты тела и текстовых подполей совпадают с независимым эталоном после установленной нормализации, присутствует `CHRS: KOI8-R 2`, а чтение API и HPT сохраняет смысл текста

#### Scenario: Ответ другому CHRS
- **WHEN** создаётся ответ на письмо CP866 или UTF-8
- **THEN** ответ записывается в KOI8-R с собственным CHRS и корректной reply-связью, без изменения родителя

#### Scenario: Непредставимый символ
- **WHEN** тело, тема или имя содержит символ вне KOI8-R
- **THEN** API возвращает ошибку валидации, `.jhr/.jdt/.jdx` не меняются и сообщение не считается сохранённым

#### Scenario: Вложение UUE
- **WHEN** через API публикуется вложение при настройке KOI8-R
- **THEN** текстовые поля кодируются согласно настройке, а восстановленные байты вложения и его SHA-256 совпадают с исходными

### Requirement: Общая координация при разных путях монтирования
FFIDO на хосте и HPT в контейнере SHALL координировать доступ к общей JAM-базе через один физический coordination lock в общей файловой системе, даже при разных строковых путях к нему. Отображение путей SHALL не заменять общую lease, файловые блокировки и проверки идентичности. Поддерживаемый запуск HPT SHALL удерживать lease до завершения фактического процесса HPT.

#### Scenario: Общий bind mount
- **WHEN** FFIDO и wrapper используют один lock-файл через хостовый и контейнерный пути, а FFIDO удерживает shared lease
- **THEN** HPT ожидает exclusive lease или завершается по timeout без доступа к JAM

#### Scenario: Контейнерная команда
- **WHEN** wrapper запускает HPT через синхронный контейнерный запуск
- **THEN** lease сохраняется до завершения HPT, включая toss/pack/scan, а фоновый запуск не считается поддерживаемой координацией
