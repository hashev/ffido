# Design

## Context

Мотивация и границы изменения описаны в proposal.md. На amster2 оба контейнера монтируют `/home/yurik/fido:/home/fido`; `hpt.cfg` задаёт `basedir=/home/fido`, а `areas.cfg` содержит абсолютные пути `/home/fido/msgbase/...`. KOI8-R подтверждена оператором; это не результат автоматического определения по файлам.

`AppConfig` уже содержит `ftn.default_encoding=cp866`, проверяет имя через iconv и разрешает локальные пути относительно config.json. `main.cpp` и `service/point_mail_admin.cpp` независимо собирают каталог из `ConfigManager`, областей helper и ящиков. `EchoAccess::Build` сравнивает inode/dev трёх файлов JAM с путями из HPT. `ValidatePointMail` проверяет коллизии путей до открытия каталога. Все эти потребители должны видеть одно представление путей.

Helper `ffido-hpt-auth` вызывает `readConfig` установленной libfidoconfig. В доступных заголовках callback открытия нет; в исходнике той же локальной установки `fidoconf/src/cfg.c` основной конфиг и include открываются напрямую через `fopen`. Переменные и условия обрабатываются до открытия активного include. Поэтому отображение только результата helper не решает загрузку include.

Отдельный `ConfigManager` не поддерживает include/макросы и отклоняет неизвестные опции, в том числе `-p`, присутствующую в серверном areas.cfg. Добавление mapping не означает, что произвольный реальный areas.cfg станет поддерживаться этим парсером. Для режима с отображением каталог должен получать полные разобранные области из helper, а не повторно разбирать серверный файл ограниченным парсером.

## Goals / Non-Goals

**Goals:** однозначное преобразование контейнерных путей, семантика HPT без её повторной реализации, одинаковый каталог у сервера и admin, подтверждение KOI8-R независимыми байтовыми проверками.

**Non-Goals:** изменения API/Flutter, миграция баз и метаданных, автоматическое управление Docker, новый синтаксис HPT, обновление Husky или toolchain. Настройка `default_encoding` общая для экземпляра сервера; отдельные кодировки чтения/записи и настройки на каждую эху не вводятся.

## Decisions

### 1. Правила путей и их область действия

Добавить в FtnConfig массив `path_mappings` с `from` и `to`; по умолчанию пустой. Оба пути абсолютные POSIX-пути, без NUL и компонентов `.`/`..`; завершающие и повторные разделители нормализуются. Дубликаты нормализованного `from` запрещены. Вложенные правила разрешены: самое длинное совпадение по компонентам побеждает. Результат не отображается повторно. Не совпавший путь остаётся прежним и проходит обычные проверки.

Путь из тоссера с компонентом `..` отклоняется до нормализации и отображения. Относительные пути сначала разрешаются по существующим правилам конкретного источника (HPT сохраняет свою семантику cwd; прежний каталог ConfigManager — относительно JAM-корня), затем отображаются один раз. Режим с правилами использует области helper, поэтому cwd helper явно фиксируется так же, как в прежнем запуске, и покрывается тестом; не подменяется каталогом include без основания в HPT.

Локальные `auth.hpt_config_path`, `ftn.areacfg_path`, `jam_base_path`, `coordination_lock`, TLS/SQLite/session-key остаются путями FFIDO. `point_mail.points[].jam_base` остаётся относительным путём внутри JAM-корня. Их не пропускают через mapper. Например:

```json
{
  "auth": { "hpt_config_path": "/home/yurik/fido/hpt.cfg" },
  "ftn": {
    "areacfg_path": "/home/yurik/fido/areas.cfg",
    "jam_base_path": "/home/yurik/fido/msgbase",
    "default_encoding": "KOI8-R",
    "coordination_lock": "/home/yurik/fido/ffido/hpt.lock",
    "path_mappings": [
      { "from": "/home/fido", "to": "/home/yurik/fido" }
    ]
  }
}
```

Это фрагмент, а не полный рабочий config.json. Для контейнера тот же lock доступен как `/home/fido/ffido/hpt.lock`; каталог создаётся оператором с подходящими правами. Для запуска FFIDO в контейнере с совпадающими путями массив не нужен.

### 2. Отображение при открытии include, а не переписывание конфигов

Сохранить libfidoconfig единственным интерпретатором макросов, условий и ACL. Для mapped-режима использовать минимальный поддерживаемый патч текущей версии libfidoconfig: callback открытия основного файла/include в `cfg.c`, вызываемый после вычисления include-пути, перед `fopen`. Callback возвращает открытый только для чтения поток физического файла; логическое имя include и значения переменных сохраняются. Остальные операции библиотеки и внешние HPT-процессы не перехватываются.

Патч и воспроизводимую сборочную интеграцию хранить в репозитории; привязать к проверенной текущей ревизии Husky с проверкой применимости, без обновления версии. Helper с mapping должен явно проверять наличие адаптера и завершаться с понятной ошибкой при несовместимой сборке. Пустой массив сохраняет существующий путь загрузки установленной библиотеки. В реализации сначала доказать адаптер на Linux и macOS, затем интегрировать в сервис. Не опираться на отсутствующий публичный API и не модифицировать пользовательскую установку `/Users/yurik/ftn/usr`.

Отвергнуты: текстовая замена путей (может затронуть пароли и изменить условия), собственный разбор include/макросов (дублирование семантики), symlink/chroot/namespace (особые права и платформенные различия), глобальный LD_PRELOAD/DYLD-перехват (лишнее влияние на процесс и непереносимость).

Открывающий адаптер отображает только запрошенные конфигурационные файлы. Главный файл уже задан локальным путём и открывается без повторного mapping; include разрешается в логическом пространстве HPT, затем отображается. Время, объём вывода и изоляция диагностики helper сохраняются. Пределы количества/глубины include и суммарного объёма читаемых конфигов должны ограничивать адаптер; цикл или превышение лимита дают контролируемую ошибку без частичной политики. Значения лимитов согласовать с существующим бюджетом helper (16 MiB вывода, timeout), зафиксировать в тестах и документации.

### 3. Полный каталог HPT в mapped-режиме

Расширить внутренний ответ helper данными областей, нужными каталогу (имя, путь, формат, описание, существующие используемые атрибуты). Использовать libfidoconfig для всех областей mapped-режима; Passthrough и неподдерживаемые форматы сохраняют прежнюю политику исключения/доступа. Каталог и ACL строятся из одного результата helper, включая private areas. Так реальный `-p 3650` обрабатывается библиотекой HPT, а не самописным парсером.

Сохранять прежний режим `ftn.areacfg_path` при пустом mapping для совместимости существующих отдельных каталогов FFIDO. При непустом mapping `areacfg_path` служит подтверждением выбранного файла областей: он должен совпадать с одним из активных include HPT по физической идентичности; несовпадение отклоняется, а не молча игнорируется. Каталог этого режима включает области основного HPT-конфига и всех его активных include. Документировать эту область действия; не вводить второй переключатель источника каталога.

Один mapper применяется к исходным путям echo/private из helper до `ValidatePointMail`, построения каталога и ACL. Маппинг выполняется на границе загрузки конфигурации один раз; helper возвращает исходные логические пути областей, родитель преобразует их. Не изменять строки паролей, имена эх, адреса и описания. При чтении areacfg старым парсером без правил пути сохраняются как прежде.

Общий загрузчик/сборщик конфигурации повторно используется `main.cpp`, `RunMailStage` и подготовкой ящиков. Повторное добавление private areas исключить. Сохранить ограничения JAM-корня, descriptor-relative open/O_NOFOLLOW и inode/dev-сверку в EchoAccess. Alias/collision проверки должны работать после отображения, до мутаций. Внутренний helper-протокол меняется совместно с его вызывающими сторонами; публичный protobuf не меняется.

### 4. KOI8-R без новой настройки

Использовать существующий iconv и `ftn.default_encoding`. Для KOI8-R проверить обе стороны преобразования на старте; неподдерживаемое имя или недоступное преобразование дают ошибку до JAM-записи. Не вводить общий ограниченный whitelist, который сломает прежние допустимые кодировки.

Чтение сохраняет явный CHRS; fallback используется при отсутствующем CHRS/IBMPC. Публикации и ответы используют настройку сервера независимо от CHRS родителя, формируя `CHRS: KOI8-R 2`. CP866 по умолчанию остаётся прежней. Проверки байтов используют независимые фиксированные эталоны, а не тот же production converter. Учитывать уже установленную замену исходящей Н → H и неизменность UUE. Исторические письма не переписываются.

### 5. Блокировки и развёртывание

Mapping переводит пути, но не создаёт общую файловую систему. Backend и HPT должны видеть одни JAM-inode и один неизменяемый lock-файл, доступные соответствующему UID/GID. Файл lock нельзя заменять при работающих процессах.

Существующий wrapper может удерживать lock на хосте вокруг синхронного `docker compose exec -T ... hpt ...`; инструкция должна задавать compose-файл/рабочий каталог явно. Фоновый `exec -d`, перезапуск контейнера и сторонние неконтролируемые toss/pack/scan не покрываются такой координацией. Отдельный scope — полный операторский цикл point_mail: текущий `--hpt` принимает путь исполняемого файла, а передача inherited fd через Docker exec не работает автоматически. Не обещать прозрачный cross-container `--cycle`: документировать существующее ограничение, полный цикл выполнять там, где HPT и admin доступны в одной среде с прежним наследованием lease. Новую Docker-оркестрацию не добавлять.

Проверка координации — на временных файлах bind mount, без запуска HPT над рабочей нодой. Отображение разных строковых путей само по себе не доказывает общий inode.

## Risks / Trade-offs

- [Патч libfidoconfig требует воспроизводимой сборки] → узкий callback без новой семантики, фиксированная текущая ревизия, явная диагностика несовместимой сборки, тесты Linux/macOS; без подмены системной библиотеки.
- [Полный каталог HPT шире отдельного areacfg] → режим включается явно непустым mapping, требует участия areacfg в активных include, документируется; ACL и private owner-политика сохраняются.
- [HPT содержит байтовые описания не в UTF-8] → кодировку JAM не считать автоматически кодировкой всех конфигов. При передаче текстовых метаданных helper сохранить существующие ограничения и отклонять непредставимые данные контролируемо; не перекодировать секреты. Поддержка произвольной кодировки конфигов вне объёма.
- [Два файла lock вместо одного] → инструкция с парой хостового/контейнерного пути и проверка общей lease на синтетическом mount.
- [Смешанная база без CHRS] → использовать явно настроенный fallback; автоматическое угадывание и массовую перекодировку исключить.

## Migration Plan

1. Реализовать и проверить на синтетических конфигах и JAM; Linux и macOS должны подтвердить include-адаптер.
2. Подготовить документированный пример для amster2 с KOI8-R и mapping, не копируя credentials/рабочие конфиги в репозиторий.
3. Развёртывание выполнять отдельным запросом: проверить mount, UID/GID, активные include и общий lock; согласовать остановку HPT/FFIDO перед изменением процесса координации.
4. Существующие CP866-профили не менять. KOI8-R применяется к новым публикациям и резервному чтению, без миграции файлов.
5. Откат: вернуть прежний бинарный комплект и конфигурацию, сохранив кодировку, соответствующую фактическим сообщениям. Удаление mapping допустимо только в среде с доступными исходными путями HPT; файлы JAM/SQLite не откатываются автоматически.
