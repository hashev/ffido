# Design

## Context

Мотивация — в `proposal.md`, воспроизводители и границы доказательств — в `audit.md`. Проект использует Flutter 3.47.7/Dart 3.13.5, C++23, TLS gRPC, общий protobuf, персональные метаданные SQLite и внешнюю координацию с HPT. Существующие слои сохраняются. Штатные наборы проходят в Debug, но не покрывают четыре найденных межоперационных сценария; ASan install gate имеет отдельный воспроизводимый сбой загрузчика.

`SessionManager` создаётся экранами заново и разделяет ApiClient/store/preferences; значит защита на экземпляре manager не покрывает все операции. `ApiClient.configure` меняет epoch до ожидания отмены старых RPC и завершения канала. Каталог допускает неподдерживаемые приватные области без `JamFiles`. MCP принимает до четырёх tools/call, но вывод результата идёт синхронно под mutex учёта активных операций.

## Goals / Non-Goals

**Goals:**

- Исправить F1–F5 с постоянными воспроизводящими тестами и понятными контролируемыми исходами.
- Закрыть риск R1 тестом медленного потребителя и ограниченной моделью выходных ответов.
- Для R2–R8 и R11–R16 получить конкретные показатели и оптимизировать только обнаруженную существенную стоимость/ошибку; решение «не менять» с результатом измерения допустимо.
- Сохранить корректность восстановления, персональные данные, repeat operation ID и совместимость старых клиентов/серверов.

**Non-Goals:**

- Смена state manager, транспорта, криптографии, toolchain; новый API, миграции SQLite и переписывание JAM.
- Автоматический ремонт рабочих баз, публикация FTN, системный deploy и настройка чужих процессов.
- Обещание отсутствия всех ошибок или фиксированного ускорения без измерений.

## Decisions

### 1. Проверять physical owner до входа в файловый карантин

Разделить отказ операции в metadata и блокировку существующего `JamFiles`. Если owner отсутствует, журнал переводится в контролируемое состояние отказа без файлового доступа; не создавать фиктивный owner и не искать похожую область. Ошибка metadata возвращается наружу. Сохранить нынешнее поведение изменённой identity и существующих recovery fault injections.

Альтернативы: исключение/перехват SIGSEGV не обеспечивает корректности и не подходит; проверка только ID уже показала свою недостаточность. Проверка формата только при загрузке конфигурации не заменяет безопасность публичного recovery-входа.

### 2. Общий порядок локальных операций сессии

Держать идентификатор текущего намерения на общем клиенте или общем координирующем объекте его lifecycle, а не на каждом временном manager. Выход/смена подключения/закрытие немедленно инвалидируют прежние операции. Внутри ApiClient отдельно учитывать собственную смену epoch при успешном Login; проверять версию и ожидаемое подключение после configure и до публикации профиля. Финализаторы старой операции не должны очищать более новую сессию.

Операции store/preferences одного клиентского профиля упорядочиваются общей очередью, которая продолжает работать после ошибки. Перед каждым разрешением автовосстановления проверяется намерение. Tombstone устанавливается для выхода до ожидания медленных операций, а завершение выхода гарантирует, что более старая queued запись не сможет его снять. Сетевой отзыв не должен зависеть от доступности Keychain; UI получает различимый результат отмены/несохранения. Очередь не охватывает сетевой RPC целиком, чтобы медленная сеть не задерживала локальную инвалидизацию.

Альтернативы: один `_busy` в Settings защищает только экран; один epoch-check до await не защищает продолжение; полная сериализация сети блокирует выход на срок RPC. Повторное чтение только tombstone закрывает один случай, но не позднюю запись и две конкурирующие сессии.

### 3. Отделить stdout от registry активных MCP-вызовов

Воспроизвести backpressure отдельным process-тестом, затем вынести сериализацию/вывод из `active_mutex`. Использовать одного владельца вывода с очередью, ограниченной байтами и числом сообщений. Начальный внутренний бюджет: 4 MiB суммарно и 32 сообщения; сообщение по-прежнему не больше 512 KiB. При достижении бюджета не блокировать reader/отмену на ожидании свободного места: отменить активные RPC, вывести безопасную диагностику в stderr и управляемо завершить соединение. Это соответствует новой spec; ресурсный предел не становится частью wire-формата.

Успешный backend send и его operation ID не откатываются из-за невозможности доставить ответ: повтор использует прежний durable operation, как сейчас. JSON-сообщения не перемешиваются, duplicate ID и лимит четырёх активных calls сохраняются. EOF не ждёт бесконечно заблокированного writer: writer должен иметь прерываемое ожидание/ограниченное завершение без конкурирующего чтения stdin. На POSIX подходят poll/nonblocking stdout и сигнал остановки, без глобального изменения чужих дескрипторов.

Альтернативы: только перенести write за mutex полезно, но reader всё ещё может блокироваться при собственном ответе; неограниченная очередь меняет зависание на рост памяти; detached writer нарушает lifetime и shutdown.

### 4. Исправить install gate с его собственными instrumented зависимостями

Сверить install RPATH и runtime-комплект в ASan-prefix. Обеспечить запускаемый stage с корректными instrumented dylib либо явным тестовым runtime-prefix, предусмотренным установленной моделью сборки; production install проверяется без такого окружения. Не использовать обычные dylib для маскировки ошибки. Добавить в `test_mcp_install.py` сообщение returncode и безопасный stderr; сохранность assert и запрет лишних runtime-артефактов остаются обязательными.

Альтернативы: исключение McpInstall из sanitizer набора или ослабление его результата не устраняет дефект проверки установки.

### 5. Измерения до оптимизаций

Переиспользовать `LargeCatalogGrpcTest.CatalogPerformanceFixture`, thousand-area и concurrent/recovery fixtures. Данные только искусственные. Размерности: 1/100/1000 областей, 100/10000 писем, 1/16/64 одновременных запросов; 5000 областей — отдельный тест масштабирования Build. Отдельно измерять cold/warm проходы, p50/p95, число SQL-запросов, JAM bytes/opens, lease/mutex wait, threads и peak/retained RSS. Для time-замеров сохранять SDK/compiler/config и не включать sanitizer overhead в сравнение обычной сборки.

Сначала убрать доказанное N+1 через пакетные metadata-операции в рамках текущего запроса. Не вводить долгоживущий общий кеш прочитанности без отдельной модели инвалидации. Для archive registry рассмотреть lock на cursor только при измеренном межпользовательском блокировании; сохранять current permissions, fingerprints, cursor revision и bounded scan memory. Изменение CancelMonitor оправдано измерениями, а не самим наличием thread. В footer snapshots освобождать память только при доказанном финальном завершении операции: uncertain send сохраняет неизменяемый snapshot для повторов.

Сравнение: минимум 20 повторов одного fixture на одинаковой машине, raw результаты и медиана/p95 до/после. Для R2/R3 критерий — уменьшение SQL-вызовов с порядка числа писем до порядка batch/page без изменения счётчиков; целевой p95 на выбранном нагруженном fixture не хуже baseline, желаемое снижение не менее 20%. Для остальных — доказанное снижение целевого ресурса без ухудшения p95 более 10%; иначе оставить исходную реализацию и сохранить отрицательный результат. Эти пороги — критерии эксперимента, не обещание пользователю.

### 6. Постоянные регрессии и MCP

Перенести временные сценарии в существующие API/recovery/process suites с assert правильного конечного состояния. Использовать barriers/completers, не случайные sleeps; добавить normal/error/dispose/endpoint-switch и разные manager. Настроить Dart MCP на закреплённый SDK при следующей runtime-сессии, не принимать результаты старого анализатора. После будущих executable `lib/` правок выполнить hot restart для фундаментального lifecycle либо hot reload для простых widget-правок через нужный DTD; при отсутствии приложения указать ограничение.

LLDB применять к своему тесту F1: breakpoint перед recovery и quarantine, backtrace/owner и повтор после исправления. Если MCP снова зависает, CLI LLDB допустим с явным ограничением. TSan — отдельная конфигурация с согласованными protobuf/gRPC/Abseil; debugger и ASan не заменяют TSan.

## Risks / Trade-offs

### Обязательный порядок ресурсов

Карта исходных цепочек и точные места — в дополнении `audit.md`. Для изменений принять следующие внутренние инварианты:

- coordination lease предшествует physical JAM mutex и byte lock; metadata может вызываться внутри JAM lease, но metadata mutex/транзакция не должна ждать новый JAM lease в обратном направлении;
- registry владельцев/операций/черновиков защищает только поиск/создание записи и lifetime ссылки; не удерживается на файловом I/O, RPC, сериализации, join и ожидании другого mutex;
- source lease в MailBridge освобождается перед target lease; не вводить одновременный захват двух баз или shared readers одной physical base как попутную оптимизацию;
- per-draft/per-cursor mutex удерживает согласованность конкретной операции; общий registry не заменяет этот mutex и не закрывается вместе с ещё работающим waiter;
- callbacks под mutex допускаются только после проверки их ограниченности и отсутствия обратного входа; нынешний active callback bulk-read проверяет активность, но новые callbacks не должны вызывать metadata;
- join выполняется после снятия registry locks, с механизмом остановки writer и ожиданий; успешный durable commit никогда не откатывается только из-за cancel или потери stdout.

Это внутренние ограничения проектирования, а не новый wire-контракт. Статическая карта не доказывает отсутствие циклов во всех путях; тесты обязаны охватить сценарии, изменённые реализацией.

### Отменяемые ожидания операций

Для R11 сначала тестом разделить время ожидания общего draft mutex и время RPC. Подготовка нового черновика может выполнять Preview без общего send mutex; отправка сериализуется по конкретному draft ID. Lifetime per-draft lock удерживается владельцем и всеми waiters; удаление registry допускается только без создания второго живого lock для того же draft. Запись attempted/result и повтор OUTCOME_UNKNOWN остаются под защитой одной операции.

Для R12 сохранить текущую гранулярность UUE stripes и crosspost operation key на первом этапе: заменить непрерываемое ожидание отменяемым helper в существующем стиле, с проверкой до/после захвата и без обновления deadline в цикле. Если замер покажет существенные коллизии пользователей в 64 UUE stripes, отдельно сравнить registry по user/operation; увеличение числа stripes вслепую не является решением отмены. Запросы к одной операции по-прежнему сериализованы, включая чтение и изменение upload state.

Для R14 измерять участок auth до семафора отдельно от бизнес-операции. WAL/busy_timeout не ограничивает C++ mutex wait; нельзя объявлять deadline соблюдённым по одному времени возврата клиента. Не заменять единое SQLite-соединение пулом до доказательства выигрыша и модели атомарности. Bulk-read остаётся одной атомарной транзакцией с receipt; частичные commits запрещены.

### Payload UUE и in-flight память

R13 — первый кандидат на снижение копий без изменения сетевого API: отделить immutable payload от metadata cache entry, удерживать payload ссылкой на время Chunk, под cache mutex брать ссылку и необходимые небольшие metadata. В ответ копируется только slice. Prune/TTL может убрать cache entry, но не разрушить buffer работающего запроса. Учёт quota должен явно учитывать payload, удерживаемый активными readers после удаления из map; обычное число записей в map не равно живым байтам.

Fingerprint/ACL каждого source проверяется по прежним правилам. Кешировать положительный результат проверки между chunks без нового доказательства согласованности нельзя; это изменило бы защиту от отзыва доступа и изменения JAM. Повторные источники/большие тела измеряются отдельно от устранённых копий.

Для R16 учитывать cached, in-flight и queued bytes раздельно. Бюджет writer 4 MiB/32 сообщения относится только к очереди; дополнительно ограничить одновременно сериализуемые ответы и освободить резервирование на всех ошибках/EOF/cancel. Не выдавать этот бюджет за предел RSS и не добавлять скрытое усечение ответа. Перед лимитированием декодирования UUE сверить текущие quotas и совместимость ошибок; новая reservation не должна ослабить или произвольно ужесточить публичные лимиты.

### Эксперименты и условия отказа от оптимизации

Матрица и очередность приведены в `audit.md`. Основные fixtures: 1000×100 небольших писем, 10000 писем в одной горячей базе, отдельно Build 5000 областей. Cold — новый тестовый процесс/пустой application cache, без системного сброса OS page cache. Измерять p50/p95, throughput и долю ошибок вместе; быстрый RESOURCE_EXHAUSTED не считается улучшением latency.

Для cancel-сценариев использовать barriers и watchdog 1 секунду при deadline 5 секунд: worker/slot должен освободиться до отпускания блокирующего owner. Это проверка конкретного тестового окружения, не обещание нового SLA. Для HPT coordination использовать отдельный EX-probe процесс и метрики максимального ожидания/timeout; настоящий HPT остаётся отдельной интеграцией. Каждый test process имеет собственный внешний watchdog и гарантированную очистку, иначе ошибка тестируемого lock способна повесить весь CTest.

Предпочтительный результат R13 — количество скопированных payload bytes порядка F за загрузку вместо K×F при K chunks. Для прочих кандидатов действуют критерии сравнения из Decisions; добавляется запрет принимать снижение p95 ценой роста отказов/неполноты результата. Если выигрыш не превышает разброс 20 повторов, оставить исходный алгоритм. Уменьшение correctness-риска (например, прерываемая отмена) принимается по детерминированной регрессии и не обязано обещать ускорение.

### Дополнительные риски решений

- [Новый per-draft lock registry разделится при premature erase] → strong references у waiters, сценарий три последовательных/параллельных send одного draft и одна durable операция.
- [Shared payload переживёт eviction и превысит quota] → учитывать живые payload/reservations, тестировать prune/TTL во время нескольких Chunk.
- [Polling helper добавит wakeups] → stop notification, ограниченный интервал и общий deadline; измерить CPU и не размножать monitor thread на каждый waiter.
- [Непрерывные SH readers задерживают EX HPT] → сначала уменьшить работу под lease, измерить fairness; не менять межпроцессный протокол в рамках обычной оптимизации.
- [Пул SQLite/освобождение JAM посреди scan нарушит snapshot] → не применять без отдельного доказательства generation/atomicity; сохранить существующие fault tests и EX-probe.

- [Общая очередь store может задержать завершение logout] → немедленно инвалидировать память/намерение; явно ожидать устойчивый tombstone и упорядоченную очистку перед успешным окончанием logout, не держать очередь на сетевом RPC.
- [Прежняя queued очистка может удалить новый секрет] → версия проверяется внутри очереди; отдельные тесты connect→logout→connect на одном endpoint и на разных.
- [Карантин без физических файлов может маскировать metadata failure] → ошибка записи состояния всегда распространяется; никакого ложного успешного восстановления.
- [Разделение MCP writer меняет порядок ответов/завершение] → асинхронные ID разрешают разный порядок, но каждый ответ целый; проверить duplicate IDs, EOF, заполненный pipe и неопределённый send.
- [Оптимизация статистики меняет точность/ACL] → сверять старый и новый результат на разных пользователях, generation, deleted messages и inaccessible areas; только scoped batches.
- [Платформенные риски обновлений пересекаются с активным change] → результаты Android/macOS сначала сопоставить `add-managed-updates`; менять его артефакты только отдельным update workflow при изменении его плана.
- [Неполная среда] → HPT, TSan и реальные устройства — самостоятельные gate с явным статусом, без заимствования исторических результатов.

## Migration Plan

Миграции форматов и protobuf нет. Реализацию выполнять адресными группами: recovery → session → MCP/install → измерения и обоснованные оптимизации. После каждого блока — focused tests, затем полный набор. Развёртывание не входит в текущий запрос; перед будущим выпуском пройти release gate с HPT и нужные platform builds. Откат кода не должен удалять журнал операций или секреты новой сессии; работающие базы и пользовательское состояние не откатывать автоматически.
