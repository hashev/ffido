# Design

## Context

Мотивация приведена в proposal.md. Основание — локальный отчёт
docs/deployment/amster2-miniapp/update-readiness-20261119.md; это исторический
аудит, а не новая проверка сервера в рамках proposal.

Рабочая пара — локальные образы safe-mailbox-restore с нестандартной BUILD identity,
без RepoDigests. SQLite уже имеет schema 12. Опубликованный stable v1.0.27 допускает
только 9–11. Его нельзя использовать как цель или менять его подписанный manifest.
Номер локальной сборки 2026111804 нельзя трактовать как signed sequence.

Compose updater управляет одним backend, заменяет override целиком и не имеет
полноценного rollback по локальным image ID. Серверный ops/manage.py отдельно
пересобирает tosser и использует прежний backup; scripts/node_backup.py уже имеет
проверку manifest и согласованности, но ещё не объединён с этим обслуживанием.
Рабочий gateway размещён отдельно от узла; snapshot до его окончательной настройки
не является актуальным полным deployment backup. По аудиту свободно около 5,84 GiB,
что меньше прежнего рабочего бюджета 14 GiB. Эти значения надо перепроверять при
будущем применении, очистка не входит в change.

## Goals / Non-Goals

**Goals:**

- Ввести явную проверяемую границу между локальной provenance и подписанным каналом.
- Сделать подготовку, смену и возврат пары восстанавливаемыми после прерывания.
- Связать данные и внешние deployment-зависимости одним доверенным manifest.
- Проверить сценарии на изолированных копиях без доступа к рабочим mounts и FTN.

**Non-Goals:**

- Публикация релиза, перенос всех незавершённых изменений в релиз или выбор его номера.
- Выполнение процедуры на amster2, очистка, изменение firewall, каталога или Pages.
- Автоматическое снятие пауз, изменение Telegram API либо redesign gateway.

## Decisions

### 1. Отдельная регистрация локальной пары

Добавить явный режим перехода в существующий updater, сохранив строгий обычный
валидатор common.version_key. Приватный план связывает точные image ID backend и
tosser, фактические BUILD, архитектуру, контрольные суммы Compose/config и внешний
доверенный digest плана. Непосредственно перед остановкой значения проверяются
повторно. Нестандартная identity допускается только как зарегистрированный источник
или зарегистрированный rollback, но никогда как подписанный целевой релиз.

Цель выбирается явно по проверенному manifest и immutable digest. Signature, канал,
identity, архитектура и совместимость данных проверяются обычными средствами
discovery/common. Подмена BUILD или исключение проверки подписи отвергнуты: они
скрыли бы реальное происхождение работающих образов.

Signed floor хранится отдельно от локального build number. При регистрации он
подтверждается ранее доверенными подписанными метаданными; при отсутствии такого
основания переход блокируется. Пример из аудита: локальный 2026111804 не блокирует
новый подписанный sequence 1066 при подтверждённом floor 1065. После приёмки
закрепляются signed provenance и новый floor. Восстановление старого backup или
локального образа не понижает уже закреплённый floor: при restore берётся максимум
актуального доверенного значения и подтверждённого значения снимка. Продолжение
автоматического канала после возврата локального кандидата требует явного перехода.

### 2. Подготовленная пара и сохранение Compose

Парный режим включается явно; одиночный остаётся совместимым. Backend берётся по
подписанному digest. Tosser собирается до окна остановки из этого точного backend
по закреплённому рецепту с проверяемыми входами HPT и необходимыми patch/config.
Его backend BUILD должна совпадать с целью; итоговый image ID и происхождение
фиксируются в плане. Это производный локальный worker, а не отдельно подписанный
registry-артефакт. Случайный mutable base/tag без разрешённого digest недостаточен.

Сохраняются обе исходные identity, необходимые локальные образы/их проверенные
экспорты для восстановления, эффективная конфигурация и исходные override-файлы.
Updater меняет только управляемые image-поля, сохраняя посторонние поля и службы.
Оба pins записываются одним атомарным обновлением управляемого файла. Docker не
запускает два контейнера атомарно: согласованность обеспечивает журнал и запрет
рабочих записей между запусками. Отдельные gateway и тестовый backend не пересоздаются.
Альтернатива «обновить backend, затем пересобрать worker» отвергнута из-за смешанной
пары и возможной ошибки сборки уже после миграции.

### 3. Один координатор и закрытые писатели

Версионируемый host-координатор разместить рядом с updater в scripts/update/;
подготовка замены серверного ops/manage.py и runbook остаются в
docs/deployment/amster2-miniapp/. Не поддерживать две независимые процедуры backup.
Координатор использует maintenance/instance/HPT locks, учитывает все механизмы
паузы и сохраняет исходные состояния служб. Для jamnntpd соблюдается корректное
завершение SIGINT. Старый finally с безусловным запуском писателей исключается.

Фазы: prepared → quiesced → backed-up → switching → validating → private-ready →
admitting → accepted → complete; ошибки ведут в rollback-required/restoring/rolled-back.
Журнал содержит исходную и целевую пару, manifest/digests, pins, проверенный backup,
исходные состояния и отметку допуска новых записей. Каждая мутация следует после
устойчивой записи намерения; повторный запуск продолжает или безопасно отменяет
конкретную фазу. Нельзя выводить успех только из наличия healthy-контейнера.

На validating пользовательский ingress и FTN-писатели закрыты. Host-адаптер должен
обеспечивать проверяемый maintenance gate: backend проверяется через приватный
listener/контейнерный probe, worker проходит проверку старта и конфигурации с
блокированными обработкой очередей и экспортом. Gate не требует изменения
production firewall или доверия gateway. Поддержку такого gated-start у worker
реализовать и проверить в версионируемой обвязке; до этого парный режим недоступен.
Проверяются identity, загрузка admin/helper, разбор HPT и read-only схема SQLite;
готовность worker обозначается приватным loopback socket без записи в root FS.
Для проверки полного gateway→backend допускаются только read-only probes; открытие
обычного listener считается началом допуска записей и предварительно фиксируется
в журнале. Любой сбой после этой границы обрабатывается как возможные новые данные,
даже если оператор ещё не наблюдал запросов. Автообновления остаются на паузе.

### 4. Полный bundle поверх штатного snapshot helper

Сохранить проверки scripts/node_backup.py для данных узла. Добавить deployment-профиль
с явно разрешёнными внешними корнями и отдельными компонентами: конфигурация и pins
пары, инструменты host/updater с журналами и pause markers; gateway Compose/Envoy,
TLS и полное ACME-состояние, renewal helper, относящиеся к нему cron/systemd записи,
действующий firewall script и снимок политики. Если инструментам требуется runtime,
фиксируются его версия и воспроизводимый способ подготовки, без слепого переноса
непереносимых venv. Все компоненты связывает общий версионированный manifest и
внешне закреплённый digest. Нужны архивы/образы и данные, а не одни ссылки на них.

Включение внешних путей не ослабляет запрет произвольных symlink и выхода из корня:
используются логические назначения и явные mappings. Для ACME допускается только
проверенное разрешение штатных ссылок внутри объявленного ACME-корня. Секреты,
владельцы и права сохраняются; отчёт содержит хеши и результаты без ключей/паролей.
Restore сначала распаковывает и проверяет staging; правила firewall/cron никогда
не применяются к хосту автоматически при репетиции.

Backup делается при остановленных писателях и исключённом параллельном renewal или
изменении включённых настроек. Сам helper не останавливает и не запускает службы.
Ошибка до изменения данных допускает возврат исходного набора работающих служб;
ошибка после миграции требует решения координатора. Старые архивы остаются читаемыми,
но без нового deployment-профиля не проходят gate полного перехода.

Координатор удерживает maintenance lock также во время mailbox-restore. Поэтому
ffido-admin получает опциональный --maintenance-lock-fd: унаследованный через
pass_fds дескриптор уже эксклюзивно удерживаемой первой блокировки manifest.
CLI проверяет regular file, inode/device, уже установленный exclusive lock и
совпадение open-file-description; сохраняет lease через dup, не освобождая родителя.
Остальные instance/HPT locks захватываются как прежде. Без флага поведение прежнее.
Новый admin должен входить в подготовленный restore toolkit; старый CLI не
используется с этим флагом. Это согласованное расширение административного CLI,
не изменение сетевого API. Передача непроверенного номера fd и временное снятие
maintenance lock отвергнуты из-за возможности гонки с renewal.

### 5. Совместимость, откат и новые записи

Перед остановкой проверяются совместимость цели, наличие обеих исходных identity,
backup-зависимости и бюджет диска: снимок, распаковка/репетиция, временные данные,
целевая и исходная пары и резерв не менее 2 GiB по умолчанию. Учитываются реальные
размеры и консервативная верхняя оценка сжатия, повторная проверка перед копированием;
14 GiB из аудита служат ориентиром runbook, а не универсальной константой.

Image-only rollback разрешён только при доказанной совместимости прежней пары с
текущими данными и receipt/generation контрактами. RepoDigests не обязательны для
зарегистрированного локального rollback: используются сохранённые image ID без pull.
При несовместимости до допуска записей восстанавливается весь проверенный baseline
данных и deployment, затем штатный ffido-admin восстанавливает физические mailbox
привязки. Ручной SQL и изменение PRAGMA user_version не допускаются.

После допуска записей автоматический возврат старого snapshot блокируется. Сначала
сохраняется текущее состояние и требуется отдельная процедура reconciliation новых
сообщений, receipts и очередей; автоматизация такой reconciliation вне этого change.
Даже успешно выполненный rollback сохраняет итог исходного update как неуспех.

### 6. Репетиция и release gate

Расширить существующие tests updater/Compose и node_backup. Для интеграции использовать
локальный registry, временные QA-ключи и отдельное discovery, сохранив настоящую
проверку Ed25519 и digest. Production trust не меняется. Проверить полный цикл с
локальным источником без RepoDigests, успешную цель, ошибки подготовки worker,
backup, readiness, gateway, несовместимость схемы и прерывания по фазам.

Для Mac полный прогон выполняется Linux-координатором в отдельном Docker volume:
provisioning, SQLite/JAM stat и наследование lease должны использовать одно ядро
с сервером. Временный QA host содержит matching Docker CLI, Python 3.12 с прежними
pinned requirements и Envoy; Docker socket не передаётся FFIDO-контейнерам. Его
immutable image включается в полный backup как restore toolkit. Прямое смешивание
macOS provisioning и Linux backend не является корректной репетицией JAM identities.

Копия не имеет рабочих mounts, доступа к FTN и production endpoints. Telegram и
сеансы проверяются тестовыми ключами/учётными данными; реальные секреты не включаются
в fixtures. Проверяются границы поинтов, mailbox generations, UUE/crosspost receipts
и повтор операции без повторной доставки. Изменение физических JAM проверяется
через штатное восстановление, не через исправление таблиц вручную.

Schema gate запускает фактический сервер: новая база, миграции 9/10/11→12,
повторное открытие 12, отказ для 13; обновляются существующие release metadata tests.
API/protobuf не меняются, старые клиенты сохраняют контракт. Старый подписанный
v1.0.27 остаётся несовместимой целью, новый production-релиз публикуется отдельно.

## Risks / Trade-offs

- Нехватка места → блокирующий расчёт и отдельное решение об очистке; не удалять rollback.
- Ошибка классификации старой локальной identity → явная регистрация обоих image ID и
  повторная проверка перед остановкой; никакого общего обхода signature/sequence.
- Записи сразу после открытия listener → предварительная отметка admission и запрет
  автоматического возврата старого snapshot после этой границы.
- Обвязка worker может запустить FTN раньше readiness → обязательный тест gate,
  отсутствие FTN-сети в репетиции и запрет применения до успешной проверки.
- Приватный backup содержит Telegram/session/ACME секреты → закрытые каталоги,
  сохранение прав, внешний digest и очищенные отчёты.
- Изолированный тест не доказывает состояние amster2 → отдельный свежий preflight и
  разрешение на production-переход; результаты старых аудитов не засчитываются заново.

## Migration Plan

1. В рамках будущего apply реализовать и проверить инструменты только локально,
   подготовить runbook и отчёт изолированной репетиции, оставить server pause.
2. Отдельным поручением подготовить и подписать совместимый релиз с проверенным
   составом исходников; зафиксировать manifest, backend digest и производный worker.
3. После отдельного разрешения выполнить свежий production preflight, регистрацию
   исходной пары, проверку места, полный stopped-node backup и переход по журналу.
4. Принять оба сервиса, Telegram/mailbox и gateway; при ошибке применить допустимую
   ветвь rollback. Сохранить оба baseline и отчёт.
5. Возобновление штатных автообновлений разрешать отдельным действием после приёмки.
