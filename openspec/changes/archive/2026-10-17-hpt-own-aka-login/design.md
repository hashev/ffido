# Design

## Context

HPT реального поинта содержит Address 2:5015/120.1 и один явный Link босса 2:5015/120. Существующий helper исключает виртуальный линк собственного AKA; снимок содержит только пароль и подписки босса. Локальный конфиг FFIDO /Users/yurik/ffido-live/config.json уже подготовлен для семи реальных JAM-эх, но не запущен.

Реализованные изменения hpt-password-login и hpt-echo-access ещё не синхронизированы с основными спецификациями. Новый delta user-identity добавляет отдельную ветку и не переписывает их артефакты. Поля libfidoconfig: config.addr, link.hisAka/ourAka, area.useAka.

## Goals / Non-Goals

**Goals:** вход владельца поинтовой установки без изменения HPT config; прежняя изоляция пользователей и ACL явных линков; безопасный локальный запуск для проверки пользователем.

**Non-Goals:** автоматический вход любых собственных нодовых AKA, пароли боссов из binkd/других файлов, выбор произвольного аплинка, новые поля UI, изменение FTN-маршрутизации и отправка тестовых писем в рабочие эхи.

## Decisions

1. **Деривация внутри helper.** После извлечения реальных явных линков пройти собственные AKA с point>0. Для каждого без явного реального Link найти ровно одного реального босса: hisAka совпадает с zone/net/node собственного адреса, point=0, ourAka совпадает со всем адресом поинта. Виртуальные линки никогда не являются источником пароля. Внешний формат снимка не меняется: добавить обычную запись credentials собственного адреса с эффективным паролем босса. Пустой SessionPwd не заменять Password. Не найденная пара не создаёт учётной записи, неоднозначная пара останавливает загрузку. Дубликаты собственных адресов не порождают дубликатов credentials.

2. **Синтетические локальные разрешения.** Только для собственного поинта с найденной парой добавить read/post=true в записи JAM-эх с area.useAka, равным этому поинту. Существующий EchoAccess проверяет совпадение баз и применяет права ко всем сервисам. Виртуальные права собственного линка, если они есть в данных libfidoconfig, заменить проверенной записью, а не дублировать. Если адрес имеет реальный явный Link, не создавать синтетические credentials/ACL; иначе можно обойти ReadOnly/WriteOnly. Права босса не копируются: это вход владельца локального поинта, явно выбранный пользователем.

3. **Сессии и контракт.** AuthService уже привязывает профиль и fingerprint к каноническому адресу/паролю. Новая запись остаётся адресом .1, поэтому смена пароля или исчезновение записи отзывают его сессии существующим механизмом. Проверить это процессным тестом. gRPC/protobuf и форма macOS/Android остаются прежними; существующая сборка клиента совместима.

4. **Запуск с реальными базами.** Пользователь авторизовал использование существующего пароля босса и локальных эх AKA, но пароль не выводится и не переносится в репозиторий. До запуска проверить отсутствие активных JAM-редакторов/HPT, сделать согласованный backup конфигураций и JAM, перевести активные команды HPT на общий scripts/run_hpt.py с конфигурацией ffido-live. Прямой pack в старом /Users/yurik/ftn/usr/bin/toss не запускать рядом с сервером: заменить его проверкой, которая требует остановленного FFIDO, либо вынести в явно отдельную команду обслуживания, сохранив backup исходного скрипта. Настройки линков HPT остаются неизменными. Изменения запуска локальны и обратимы.

## Risks / Trade-offs

- Расширение входа виртуального AKA → только собственный поинтовый адрес, проверенная пара boss/OurAKA и непустой эффективный пароль; отдельные отрицательные fixtures.
- Подмена пользователя боссом → профиль/MSGID/origin проверяются для .1 в синтетической базе.
- Несогласованный AKA эхи → сравнение полного адреса area.useAka и проверка путей существующим EchoAccess.
- Одновременный прямой HPT/pack → согласованный запуск через wrapper и отдельное окно pack; сервер не запускается поверх обнаруженного активного редактора.

## Migration Plan

1. Реализовать и проверить на искусственных конфигурациях; документацию дополнить новым способом входа и его приоритетом.
2. Подготовить обратимые локальные изменения запуска HPT, резервные копии и проверить live-конфигурацию без раскрытия секретов.
3. Остановить тестовый сервер на 8080, запустить новый backend с ffido-live/config.json и проверить TLS/login/catalog для реального AKA без отправки сообщений. Открыть macOS-клиент; пользователь вводит привычный пароль самостоятельно.
4. Откат: остановить live backend, вернуть сохранённые скрипты запуска и тестовый сервер; рабочие HPT-линки не менялись.

## Дополнение по результатам запуска реальных баз

Пользователь разрешил исправление CHRS IBMPC и построение каталога по заголовкам.
В трёх реальных эхах обнаружены старые сообщения с IBMPC; iconv не знает это
имя, а ConferenceService ошибочно декодирует каждый текст ради счётчиков/даты.
Для IBMPC использовать настроенный default_encoding (здесь CP866), сохранив
отказ неизвестным явным кодировкам и контроль конфликтующих CHRS. Сравнение
имён кодировок не зависит от ASCII-регистра. Каталог читает структурно
проверенные заголовки и SQLite-прочитанность без ReadMessage. Реальные JAM
не переписываются; регрессионные тесты используют искусственные файлы.
