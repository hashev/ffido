# Proposal

## Why

Нужно явно подтвердить, что публикации из клиента сохраняются в JAM в CP866, а не в транспортном Unicode/UTF-8. По исследованному коду текущий путь уже выполняет преобразование, реальный config.json задаёт cp866 и пять существующих проверок кодеков проходят; отдельного доказательства сырых байтов полного клиентского RPC-пути пока нет.

## What Changes

- Закрепить гарантию записи тела, темы и имён в CP866 при серверной настройке CP866, с CHRS: CP866 2; транспорт protobuf остаётся Unicode.
- Добавить независимую побайтовую проверку JAM после CreateMessage через API, включая новую публикацию и ответ родителю с иной исходной CHRS.
- Проверить отказ для непредставимых символов без замены на вопросительные знаки, транслитерации или частичной записи.
- Проверить чтение/экспорт HPT на синтетической CP866-базе и описать настройку в документации. Производственный код исправлять только при обнаруженном нарушении этой гарантии.
- Не менять реальные JAM и не отправлять в рабочие эхи. Существующие настройки UTF-8 и других кодировок сохраняются: задача проверяет CP866-конфигурацию, не вводя глобальный запрет других кодировок.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `jam-storage`: явная гарантия CP866 для публикаций API при соответствующей серверной настройке и отказа без потерь при непредставимых символах.

## Impact

`apps/backend/`: тесты RPC/process/JAM и, только если регрессия обнаружится, узкое исправление записи. `apps/frontend/`: проверяется действующий Unicode-контракт отправки; перенос кодирования на клиент не требуется. `scripts/` и `docs/`: независимая проверка байтов/экспорта и результаты. Protobuf, схема SQLite, зависимости и существующие рабочие конфигурации не меняются.
