# Design

## Context

Исследован действующий путь: apps/frontend/lib/repositories/message_repository.dart передаёт Unicode-строки в CreateMessage; MessageService создаёт новое JamMessage без CHRS родителя; JamAccess получает encoding_ из ftn.default_encoding; JamMessageBase::PrepareAppend вызывает ConvertText из UTF-8 в выбранную кодировку для тела, темы, имени отправителя и получателя, затем добавляет CHRS.

В /Users/yurik/ffido-live/config.json указано cp866; AppConfig также использует cp866 по умолчанию. Чтение умеет принимать CHRS UTF-8/CP1125/другие кодировки и IBMPC через fallback — это не выбор кодировки новой публикации. Факт наличия UTF-8 старых писем не доказывает, что текущий клиент пишет UTF-8.

В рамках исследования прошли пять существующих тестов: UnicodeCodecsAndHeaderMetadataRoundTrip, InvalidOrConflictingEncodingDoesNotMutate и три TextCodec. Они подтверждают преобразование, round-trip и отказ кодека, но round-trip одной библиотекой не является независимой проверкой сырых байтов полного RPC-пути. Некоторые существующие acceptance fixtures намеренно настроены на UTF-8; менять их назначение не требуется.

## Goals / Non-Goals

**Goals:** независимое доказательство фактической CP866-записи публикаций клиента и контролируемого отказа без потерь. Узкое исправление реализации допустимо только при воспроизведённом нарушении требований.

**Non-Goals:** глобальный запрет других серверных кодировок, перекодирование существующих JAM, изменение чтения CHRS, перенос кодека в Flutter, новые protobuf-поля, транслитерация или разрешение потери неподдерживаемых символов. Рабочие эхи не используются для тестовой отправки.

## Decisions

1. **Источник истины — байты новой записи.** В RPC/process тесте создать временные HPT/config/JAM/SQLite и явно задать cp866. Отправить через существующий клиентский API кириллический текст с Ё/ё, тему и имена. Получив подтверждение, прочитать только диапазоны тела и подполей новой записи из .jdt/.jhr по документированным wire offsets. Сравнить с фиксированными эталонными байтами либо эталоном Python codecs cp866, не с тем же ConvertText. Проверить CHRS: CP866 2, типизированный текст и адрес отправителя. Для reply использовать родителя с CHRS UTF-8: родитель не меняется, новый CHRS задаёт текущая настройка.

2. **Сохранить текущую конфигурационную модель.** В обычном CreateMessage нет клиентского поля encoding или переноса CHRS родителя; поэтому кодировка берётся из серверной настройки. Если цепочка уже удовлетворяет проверкам, не добавлять write_encoding или жёсткую константу в общий JamMessageBase: это сломает поддерживаемые UTF-8 fixtures и другие режимы. В документации прямо указать, что для русской установки нужно ftn.default_encoding=cp866. Реальный конфиг проверяется только на чтение.

3. **Ошибки до durable intent.** Проверить непредставимый символ отдельно в теле, теме и имени. Зафиксировать исходные байты всех трёх файлов и отсутствие новой operation; требовать INVALID_ARGUMENT и неизменность данных после отказа/повтора. Существующая обработка валидации в Flutter должна оставлять черновик редактируемым; использовать текущий тест, расширив его лишь при отсутствии соответствующего покрытия.

4. **Отдельная CP866-проверка HPT.** Использовать существующий wrapper и синтетический HPT round-trip/process fixture. Проверить соответствие записанных CP866-байтов и CHRS, корректное чтение/экспорт кириллицы HPT. Если добавляется режим в scripts/check_acceptance.py, сохранить прежний UTF-8-сценарий; не заменять все тестовые конфиги CP866 ради нужного результата.

## Risks / Trade-offs

- Симметричная ошибка кодера/декодера скрывается round-trip → независимый эталон .jdt и трёх текстовых подполей .jhr.
- Путаются Unicode транспорта и кодировка диска → документация с явной цепочкой клиент → RPC → преобразование → JAM.
- Входящий CHRS принимается за исходящую настройку → отдельный сценарий ответа родителю UTF-8.
- Проверка случайно отправит письмо в рабочую сеть → только временные синтетические базы; реальный config.json читается без изменения и без CreateMessage на live-сервере.

## Migration Plan

Миграции нет. Если тесты подтверждают текущую реализацию, достаточно добавить проверки и документацию. Если обнаружится дефект, исправить только доказанную причину, сохранив существующие конфигурации и API. Существующие сообщения не перекодируются.
