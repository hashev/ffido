# Design

## Context

Мотивация и объём — в proposal.md. `contracts/ffido/v1/ffido.proto` уже содержит Message.ftn_message_id и uint32 attributes, но `apps/frontend/lib/api/model_mapping.dart`/`models/message.dart` их не сохраняют. Протокол не содержит FTN REPLY или кладжей. `MessageService::Detail` собирает `ftn_kludges` в доменной модели, однако gRPC Map их не передаёт. `in_reply_to` вычисляется по JAM reply_to и обозначает локальный родительский ID, не исходное REPLY.

`GetMessage` вызывает RecordView и меняет пользовательское состояние; PeekMessage не меняет его, но использует Detail и полное декодирование. Даже `JamMessageBase::ReadMessage(number, false)` вычисляет кодировку и декодирует имена/тему, поэтому неизвестный CHRS может скрыть диагностику. Уже есть безопасные ReadHeader/ReadSubFields, JamAccess с координацией, generation и ограничением 64 KiB подполей. Основные флаги определены в JamMessageAttribute; второе слово хранится, но не расшифровано.

## Goals / Non-Goals

**Goals:** отдельное ограниченное чтение сырых технических метаданных; единая достоверная модель для отображения и копирования; проверка обеих сторон API.

**Non-Goals:** дамп тела/произвольных файлов, сведения о базе и физических путях, правка заголовка, восстановление повреждённых файлов, новые клавиатурные команды и изменение обычного Message/GetMessage.

## Decisions

### Отдельный RPC и модель диагностики

Добавить `GetMessageTechnicalData(MessageReference)` в общий сервис. Ответ содержит точный reference, uint32 attributes/attributes2, упорядоченный список технических подполей (low_id, high_id, bytes value) и результат определения effective_encoding. Для кодировки использовать явно различимые статусы «определена»/«не определена», без внутренних путей и необработанных исключений. Локальный ID служит подписью контекста, а не заменой FTN-поля.

В список включать сохранённые MSGID (low_id=4), REPLY (5), FTS kludge (2000), сохраняя high_id, порядок, пустые значения и повторы. Известные MSGID/REPLY трактуются только при high_id=0; прочие варианты остаются явно подписанными сырыми техническими подполями. Текстовые значения не возвращать как protobuf string: исходные байты могут не быть UTF-8. CHRS остаётся в исходных кладжах, а не перегенерируется из effective_encoding. При группировке CHRS сохранять полные исходные строки/блоки, повторения и доступность остальных кладжей; не трактовать строки тела как кладжи.

На клиенте добавить отдельный MessageTechnicalData и отдельный метод MessageRepository. Не превращать неполный MessageSummary в диагностику и не расширять обычный Message кешем диагностических данных. Альтернатива с новыми полями GetMessage проще, но требует побочного RecordView и всё равно не позволяет диагностировать ошибку декодирования.

### Ограниченное чтение исходных метаданных

Добавить в JamMessageBase небольшой публичный путь чтения raw metadata без чтения/декодирования тела, имён и темы. Переиспользовать существующие проверки заголовка/подполей, границ, generation и удалённости; допустимо выделить общую фазу чтения метаданных из ReadMessage, сохранив прежний контракт его декодирования. Не использовать небезопасный самостоятельный парсер файлов в сервисе.

После чтения raw metadata применить существующий EffectiveEncoding к исходным подполям. Успех возвращает выбранную кодировку с учётом override/default/CHRS. Ошибка определения кодировки не отменяет структурно корректные технические данные: вернуть статус и исходные байты. Структурное повреждение, неверные диапазоны и удалённость остаются ошибками операции, без обхода защит ради диагностики. Это не обещание восстановления произвольной повреждённой базы.

Читать под обычным JamAccess read lease и текущими cancellation/deadline. Суммарный исходный блок подполей ограничен существующими 64 KiB, включая их заголовки; не снимать лимит для нового RPC. Ответ не содержит тела, произвольных подполей имён, путей базы/конфигурации или секретов. Максимальное число элементов уже ограничено размером блока; UI должен строить длинный список лениво, а не молча обрезать его.

### Доступ и отсутствие RecordView

В MessageService проверить EchoAccess для текущего пользователя до открытия хранения, затем точный MessageNumber с generation. Разрешить любую поддерживаемую JAM-область с read, включая read-only эху и свой личный ящик. Сохранить отказ чужому ящику/отозванному read и неизвестному формату. Не вызывать GetMessage, RecordView, MarkAsRead, обновление истории или позиции.

Действие из строки списка важно: диагностика непрочитанного не должна открывать его ради запроса ID. Не загружать технические данные для каждой строки автоматически. Из открытого письма взять стабильный snapshot reference. Для свежей диагностики каждый явный вход выполняет читающий RPC, а закрытие не обновляет список обычным открытием письма. Никаких глобальных или дисковых кешей диагностики.

### Представление и копирование

Добавить адаптивный прокручиваемый диалог/экран «Технические данные» в `apps/frontend/lib/`, вызываемый из меню строки списка MessageScreen и меню «Действия области» открытого письма. Не сдвигать позицию списка и не запускать open(message) при выборе меню строки. Показать reference, отдельные MSGID/FTN REPLY/CHRS, раздел остальных кладжей, masks и effective_encoding/status. Отсутствие подполя и пустой bytes различать по наличию элемента, не по пустоте строки.

Формат байтов для показа/отчёта: ASCII 0x20–0x7E отображается буквально, backslash как `\\`, CR/LF/TAB как `\r`/`\n`/`\t`, прочие байты как `\xNN`. Это диагностическое экранированное представление, а не попытка исправить UTF-8/CP866. Пояснение видно в UI; копирование всего отчёта берёт тот же formatter, не преобразует экранированные строки обратно и не включает тело письма. Индивидуальные значения доступны обычным выделением. Не создавать кликабельные внешние ссылки.

Основную маску форматировать `0xXXXXXXXX` в беззнаковых 32 битах, имена известных флагов сверить с JamMessageAttribute. Неизвестная маска вычисляется из исходной, второй DWORD показывается отдельно без выдуманных названий. JAM READ снабдить пояснением о независимости от пользовательской прочитанности. Не добавлять переключателей/редактора флагов.

### Совместимость и жизненный цикл

Зарегистрировать читающую операцию в ApiTransport/ApiClient, FakeTransport и C++ GrpcService. Генерировать bindings только `tools/proto/generate.sh`, номера существующих полей/методов не менять. Контрактные тесты с перечнем методов обновить точечно, сохранив проверки идентичности и лимитов. Новый RPC доступен через существующий gRPC-Web шлюз без дополнительного HTTP API.

На старом сервере UNIMPLEMENTED означает «Для просмотра технических данных обновите сервер»; не показывать неполный набор как успешную диагностику. Клиент отменяет запрос при закрытии/смене сессии, проверяет epoch/reference до принятия результата, блокирует повтор во время загрузки и даёт явный retry при ошибке. При потере доступа старые данные и действие копирования очищаются. Отсутствие кладжей — успешный ответ, сеть/отказ — отдельная ошибка.

Текущий CommandScope проверяет активность маршрута: новый просмотр как отдельный маршрут/диалог должен блокировать команды фонового читателя. Закрытие Back/Escape/кнопкой возвращает исходный фокус/позицию; не менять реестр горячих клавиш.

## Risks / Trade-offs

- Смешение FTN REPLY с локальным parent → отдельные подписи и тест с внешним/отсутствующим родителем.
- Диагностика падает на плохом CHRS → raw metadata без декодирования; ошибка effective_encoding отделена от ошибки целостности.
- Потеря байтов и повторов → repeated bytes с low/high ID; byte oracle и единый formatter отчёта.
- Персональное чтение меняется при запросе → отдельный RPC без RecordView, снимки SQLite/JAM до и после в тестах.
- Повреждённые/огромные поля → прежние bounds/deadline, тесты предельного блока и повреждённых длин; без бесконтрольного дампа.
- Сырой отчёт менее удобен для не-ASCII текста → явное пояснение экранирования; декодированный редактор и hex-экспорт файлов не входят в первую версию.

## Migration Plan

Миграции SQLite/JAM и новые зависимости не нужны. Сначала обновить сервер с новым RPC, затем клиент. Старые клиенты продолжают работать, новый клиент со старым сервером сохраняет чтение/ответы и сообщает ограничение диагностики. Откат не меняет сохранённые данные. Проверки включают native TLS и gRPC-Web контракты; недоступное внешнее HPT/платформенное окружение фиксируется как ограничение, а не как успешный прогон.
