# Design

## Context

См. `proposal.md` о мотивации и согласованном поведении. В текущем коде
`MessageService::GetMessages` строит полные данные через Detail и затем preview;
`GetMessage` и успешный `FindMessage` вызывают RecordView. `MessageScreen.open`
добавляет результат в opened и заменяет строку прочитанной. Поэтому скрытие тела
только Flutter-виджетом нарушит согласованную прочитанность.

SQLite `IMetadataStore` уже изолирует персональные закладки, историю и отметки
пользователей. Общий protobuf используется native gRPC и gRPC-Web. В клиентах
есть epoch/cancellation и refresh-on-resume. Поиск имеет серверное сопоставление
и диапазоны UTF-16, которое нужно сохранить после явного раскрытия.

## Goals / Non-Goals

**Goals:** единая серверная оценка правил, отдельное состояние свернутого письма,
предсказуемая навигация, подтверждаемая синхронизация с защитой от lost update.

**Non-Goals:** удаление/бан отправителя, скрытие от старых клиентов как мера
безопасности, фильтрация тела, regex/wildcards, приоритеты/allow-list, push,
фоновая очередь offline-записей, фильтры Netmail и перенос настроек между серверами.

## Decisions

### 1. Серверные правила и точная семантика

Новый домен правил: стабильный UUID rule_id, enabled, scope ALL_ECHOS или
CONFERENCE с точным conference_id, optional author_contains/address_equals/
subject_contains. Новое правило требует доступной JAM EchoArea; существующее
правило недоступной эхи можно хранить/отключать/удалять, не расширяя права.
Смена области такого правила заново проверяет назначение. ALL_ECHOS не требует
права публикации. Аккаунт берётся только из подтверждённой сессии RPC.

Для имени/темы — буквальная подстрока с тем же ASCII/русским case folding, что
в поиске, включая Ё/ё, но БЕЗ CP866-подмен похожих букв: такая подмена имени
слишком легко свернёт другого автора. Другие алфавиты и Unicode-нормализации
не добавляются. Пустые после trim поля отсутствуют, внутренние пробелы сохраняются.
Для адреса переиспользовать `domain::CanonicalFtnAddress`: числовой zone:net/node
с optional .point, нулевой point эквивалентен отсутствующему. Domain-суффиксы и
маски в правилах первой версии не поддерживаются; неверный/пустой адрес письма
не совпадает с условием адреса. Сравниваются декодированные заголовки, не тело.
Все непустые условия правила — AND; активные общие и локальные правила — OR.
Возвращать IDs всех совпавших правил для объяснения, без приоритетов.

Лимиты: 200 правил на профиль, по 256 UTF-8 bytes на имя/тему, адрес до 64 bytes
с проверкой канонизатором, полный запрос до 256 KiB; UUID уникален в наборе,
неизвестные scope/поля отвергаются. Количество учитывает выключенные правила.
Обработку ограничивают действующие RPC deadline/cancellation. Клиент показывает
те же лимиты, но сервер остаётся источником валидации.

Альтернатива — клиентский matcher и SharedPreferences — не даёт единого поведения
устройств и не предотвращает преждевременный RecordView.

### 2. Хранение, ревизия и повтор записи

Добавить транзакционную миграцию от текущей версии SQLite: набор правил и
монотонная uint64 revision на пользователя; пустой набор revision=0. Метаданные
не зависят от поколения JAM. Правило привязано к ID эхи; не переносится по имени
или совпадению файлового пути. FK/изоляция соответствует существующим users.

`GetPersonalMessageFilters(Empty)` возвращает полный набор и revision.
`ReplacePersonalMessageFilters` принимает expected_revision, operation_id и весь
набор. Сервер валидирует всё до атомарной записи; CAS по revision, при конфликте
ABORTED без частичных изменений. В той же транзакции сохранять operation_id, digest и подтверждённую revision
в отдельном журнале mutations правил; текущий storage::Operation содержит JAM
append plan и для настроек не подходит. Ответ записи — подтверждённая revision,
набор перечитывается отдельным GET. Повтор того же ID/содержимого возвращает ту же
revision, иное содержимое — ALREADY_EXISTS.
При конфликте редактор сохраняет черновик; пользователь загружает актуальный
набор и явно повторяет правку. Автослияния и last-write-wins нет.

Успешное повторное чтение после потерянного ответа восстанавливает состояние;
отмена RPC не обещает отката уже зафиксированной записи. Repository не принимает
revision ниже последней подтверждённой в текущем epoch. Полное сохранение выбрано
вместо пяти CRUD RPC: при 200 правилах меньше контракт и единая атомарность.

### 3. Совместимое представление без чтения свернутого письма

Добавить RPC `GetMessagePresentation` с точным MessageReference, reveal=false
по умолчанию и optional контекстом поиска (query/scope). Ответ содержит
rules_revision, совпавшие rule IDs и явный oneof: полное письмо или свернутые
метаданные. Запрещён неявный fallback из свернутого состояния в полный Message.
Права/поколение/удаление проверяются тем же порядком, что для GetMessage.

При reveal=false сервер оценивает актуальный снимок правил; совпадение возвращает
только заголовки, reference, thread/reply-связь и персональную прочитанность, без
тела/preview/RecordView. Читать заголовки через существующий metadata путь,
декодируя только нужные текстовые поля той же политикой CHRS/default/override.
Технический raw-view не превращать в источник декодированного текста. При ошибке
декодирования — контролируемая ошибка, не «не совпало». При отсутствии совпадения
выполнить обычное чтение с RecordView. При reveal=true пользователь явно запросил
тело: обычные права/прочитанность/история и текущий текст; правила не отключаются.
Для поискового раскрытия пересчитать диапазоны тем же серверным SearchRanges
для именно выданного текста, не применять диапазоны от старого результата.

Совместимо добавить opt-in `respect_personal_filters` в ListMessagesRequest,
GetThreadRequest и FindMessageRequest (default false). В новых ответах явные
данные сворачивания и revision; totals/offset/has_more остаются прежними.
В opt-in списках у совпавших строк нет preview; имена/тема остаются. В opt-in
FindMessage сначала найти совпадение прежним matcher, затем вернуть свернутый
результат без текста, диапазонов и RecordView либо прежний полный результат.
Новый клиент включает opt-in и не делает второй обычный GetMessage для маркера.

Старые поля и номера не менять: GetMessage и запросы без opt-in сохраняют прежнюю
семантику. Старые клиенты смогут прочитать свернутые новым клиентом письма:
фильтр — пользовательское представление, не право доступа. Новый клиент проверяет
поддержку правил. UNIMPLEMENTED явно отключает функцию для этого сервера и
оставляет обычное чтение; сетевой сбой не считается отсутствием правил/поддержки.

### 4. Состояние Flutter и интеграция

Отдельные FilterRule/FilterSet и PersonalMessageFiltersRepository через существующий
ApiTransport. Кеш только памяти, namespace endpoint+epoch, сброс при logout/смене
профиля/сервера. Загрузка при входе в читатель/редактор, refresh-on-resume и явном
обновлении; push не обещается. Запрос представления всегда оценивается сервером
заново. После успешной правки обновить список и переоценить текущую карточку по
читающему opt-in списку без GetMessagePresentation/GetMessage. Если правило
перестало совпадать с ещё непрочитанной карточкой, предложить «Открыть»; тело и
RecordView получать только после этого действия. Если появилось совпадение,
свернуть прежнее представление и очистить отображаемое тело. Уже прочитанное не становится непрочитанным.
При смене revision на ответе списка/поиска актуализировать правила и не показывать
тело, основываясь только на старом локальном matcher.

В MessageScreen хранить выделенный reference и представление (visible/collapsed),
отдельно от opened/прочитанности. Свернутый переход не добавлять в opened и не
менять серверную позицию; повтор Next начинает после выделенной позиции, даже
если та ещё непрочитана. Сохранять сортировку, страницы, chain и scroll. При
переходе в следующую эху использовать правила назначения. Свернутые соседи цепочки
не исчезают; отключить reply/cross-area reply/forward и UUE до «Показать», включая
горячие клавиши. Диагностика по reference доступна без раскрытия. Поиск сохраняет
курсор на свернутом результате; повтор идёт после него.

Редактор из персональных настроек и меню текущей эхи; быстрые действия из меню
строки и открытого письма заполняют только выбранное поле и текущую эху. На
карточке доступно управление причиной/правилом. Удаление требует явного действия,
не теряет черновик при конфликте. При недоступном сервере показывать retry;
не маскировать сбой пустым списком и не отправлять изменения позднее автоматически.
Новые modal routes используют прежние CommandScope guards и восстановление фокуса.

### 5. Наблюдаемые побочные эффекты

Свертывание/изменение правил меняет только настройки пользователя. totals и
unread_count включают все письма; массовое «Прочитать всю эху» остаётся явной
операцией над всеми письмами. Фильтры не меняют JAM/атрибуты/доставку/экспорт HPT.
Явное раскрытие имеет прежние необратимые при отмене эффекты чтения; поздний UI
ответ отбрасывается по epoch/version, серверная отметка не обещает откат.

## Risks / Trade-offs

- Скрытие UI после RecordView → отдельное представление и opt-in поиск, тесты
  снимков JAM/SQLite до показа маркера, запрет обычного GetMessage для маркеров.
- Параллельные изменения устройств → CAS, атомарность, идемпотентный operation ID,
  конфликт с сохранённым черновиком, тесты рестарта и потерянного ответа.
- Устаревший локальный кеш → серверная оценка и revision в ответах, refresh по
  жизненному циклу. Мгновенная синхронизация без запроса не обещается.
- Непрочитанное остаётся в счётчике → осознанный выбор пользователя; Next использует
  выбранную позицию, не отметку чтения, исключая зацикливание.
- Рост цены списков → один ограниченный снимок правил на запрос, чтение заголовков
  для оценки без тела, ограничения размера и измерения на многостраничной базе.

## Migration Plan

Сначала контракт и SQLite migration/tests, затем backend и новый клиент.
Новый сервер с прежними клиентами проверять отдельно. Существующие данные и
номера полей не изменяются; миграция добавляет персональные таблицы/операции.
Откат клиента безопасен, но старый клиент не сворачивает письма. Откат сервера
проверить на копии upgraded SQLite по текущему version guard; не обещать чтение
новой схемы старым бинарником. Для отката использовать резервную копию metadata
или forward fix, не удалять таблицы автоматическим downgrade.
