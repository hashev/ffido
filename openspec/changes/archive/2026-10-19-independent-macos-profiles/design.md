# Design

## Context

См. proposal.md. `lib/main.dart` создаёт SharedPreferences до восстановления SessionManager; `pages/settings.dart` также получает singleton напрямую. `SecureSessionStore` использует ключ только по endpoint; tombstone и поля формы общие. `ConferenceRepository` хранит кеш в тех же preferences и перебирает ключи при очистке. `MainFlutterWindow.swift` пока только регистрирует плагины, AppDelegate закрывает процесс после последнего окна. MaterialApp.title не управляет явно нативным заголовком.

## Goals / Non-Goals

**Goals:** стабильная идентичность профиля на весь процесс, изоляция всех сохранённых настроек и секретов, понятные команды двух запусков и нативный заголовок.

**Non-Goals:** менеджер профилей в UI, перенос аккаунтов между профилями, несколько аккаунтов в одном окне, изменение других платформ, шифрование против администратора ОС. Backend и protobuf остаются совместимыми и неизменными; реальные FTN-данные не затрагиваются.

## Decisions

1. macOS Runner читает `ProcessInfo.arguments` и принимает единственный `--profile <id>` либо `--profile=<id>`. ID соответствует `[a-z0-9][a-z0-9_-]{0,31}`; отсутствие аргумента означает legacy/default. Слово `default` зарезервировано для этого же legacy-профиля. Повтор аргумента, пустой или неверный ID дают понятную ошибку запуска до инициализации хранилищ. Регистр не нормализуется молча. Остальные штатные аргументы macOS не становятся профилем. Нативный bridge отдаёт выбранный ID Flutter до первого чтения preferences. Аргументы запуска предпочтительнее разных bundle ID/двух сборок: один артефакт, команды `open -n ... --args --profile point1` и point2.
2. Перед первым SharedPreferences.getInstance конфигурируется prefix `ffido_profile.<id>.` для именованного профиля; legacy сохраняет существующий `flutter.`. Prefix именованных профилей намеренно не начинается с `flutter.`, иначе legacy getAll/очистка увидят чужие ключи. Исходники установленных shared_preferences 2.5.5 и foundation 2.5.6 подтверждают setPrefix до singleton, фильтрацию getAll/clear и поштучные UserDefaults.set/remove. Все потребители получают единый выбранный контекст, включая настройки и тестовые DI. Не создавать собственный JSON движок и не менять глобальный bundle ID. Кеш и настройки представления входят в namespace; неперсистентные черновики остаются в памяти процесса.
3. SessionStore получает тот же immutable profile ID. Именованный ключ содержит профиль и endpoint с однозначным кодированием; старый ключ сохраняется исключительно для default. При connect/logout/tombstone нельзя обращаться к чужому namespace. Пароли не сохраняются. Новые профили не импортируют общие данные; повторный вход потребуется только при первом создании или недействительной сессии.
4. Runner удерживает неблокирующий flock отдельного lock-файла профиля в доступном sandbox Application Support. Блокировка берётся до Flutter bootstrap, освобождается закрытием FD, включая аварийный выход. Занятый профиль показывает NSAlert и завершает второй процесс; PID-файл без flock не годится из-за stale PID. Аналогично блокируется default. Ошибка создания/захвата файла не допускает небезопасного запуска. Каталог создаётся для профилей с обычной защитой данных пользователя.
5. Native MethodChannel задаёт NSWindow.title на main thread. Flutter подписывается на смену авторизации и передаёт только профиль и подтверждённые SessionInfo.profile.name/address после login/restore. Учесть порядок событий ApiClient: событие смены session epoch может предшествовать установке SessionInfo, поэтому обновление после успешного результата и очищение при сбросе обязательны. Формат: `FFIDO — Demo Point 1 (2:1/2.1) [point1]`; без входа `FFIDO [point1]`. В заголовке используются имя и адрес вошедшего FTN-аккаунта: API не сообщает отдельное имя серверной ноды. Передавать секреты bridge запрещено. На других платформах bridge — no-op.

## Risks / Trade-offs

- Общая связка ключей и defaults принадлежат приложению → все ключи/очистки проходят выбранный namespace; тесты двух профилей одного endpoint.
- Старый уже запущенный binary не знает lock → перед первой проверкой закрыть старые экземпляры вручную, без завершения несохранённых редакторов агентом.
- macOS SecurityAgent может запросить доступ к Keychain → пользователь подтверждает системный запрос; не считать это ошибкой восстановления.
- Профиль не обходит expiry/revocation и сеть → штатное сообщение повторного входа, без fallback на чужую сессию.
- Native код недостаточно проверить widget-тестами → обязательная macOS release-сборка и ручной перезапуск двух профилей; недоступный UI явно отметить.

## Migration Plan

Обновить одну сборку, сохранив default-ключи. Создать point1/point2 первым входом на временный endpoint стенда с одним и тем же написанием адреса сервера. Перезапустить каждый с тем же аргументом и проверить восстановление и заголовки. Выход в одном окне не должен влиять на другое. Rollback: прежняя сборка видит только старый default; именованные данные не удаляются и не импортируются в default. Для возврата новой сборки они остаются доступны. Рабочий HPT-конфиг/реальные JAM/сервер не изменяются.
