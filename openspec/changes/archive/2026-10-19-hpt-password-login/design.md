# Design

## Context

См. proposal.md. Сейчас SettingsWidget и ApiClient принимают заранее выданный 64-символьный токен, сохраняют только endpoint. AuthService проверяет SHA-256 токена в SQLite; GrpcService::Dispatch требует Bearer для всех RPC. Профили и персональные данные уже серверные, но кеш первой страницы может задерживать видимость изменений второго устройства.

Существующий EchoAreaConfig читает отдельный разрешающий список конференций и сознательно не интерпретирует полный HPT Include/условия/макросы. Его нельзя использовать для проверки паролей. Локально доступны исходники Husky fidoconfig; документация подтверждает наследование Password при отсутствии SessionPwd и допустимость явно пустого SessionPwd. Реальные пароли при подготовке плана не читались.

## Goals / Non-Goals

**Goals:** единая идентичность по FTN-адресу, вход через HPT, безопасное восстановление нативных сессий, независимые устройства и актуальное серверное состояние при возобновлении работы.

**Non-Goals:** фоновая мгновенная синхронизация, офлайн-очередь отправки, перенос черновиков, Netmail, смена имени через повторный вход и изменение прав конференций по HPT ACL. Для Web сохраняется вход в рамках запуска; постоянное браузерное хранение не входит в этот этап.

## Decisions

### 1. Читать HPT штатным парсером

Добавить отдельный путь `auth.hpt_config_path`, разрешаемый относительно config.json. Использовать совместимую с установленным HPT библиотеку libfidoconfig через отдельный служебный процесс `ffido-hpt-auth` и CMake-поиск библиотеки/заголовков. Парсер учитывает Include, наследование и условия согласно своей реализации; загрузка выполняется при старте последовательно, до обработки RPC. Самодельный разбор строк отвергнут из-за риска неверного эффективного пароля. Версии существующих библиотек не менять, конфигурацию HPT не переписывать.

Служебный процесс запускается без shell, подавляет stdout/stderr парсера до его вызова и передаёт только структурированный результат через закрытый pipe. Родитель ограничивает размер результата и время выполнения, проверяет код завершения; `exit()` парсера не завершает FFIDO. Секреты не передаются через argv, файлы или журналы. Процесс исключает виртуальные линки, добавленные парсером для собственных AKA; они не предоставляют доступ к FFIDO.

Из результата построить неизменяемый снимок адресов линков и эффективных паролей. Канонизация числовых адресов включает эквивалентность отсутствующего point и `.0`; дополнительные AKA одного линка не объединяют автоматически разных пользователей. Если API парсера не различает отсутствующий и явно пустой SessionPwd, адаптер должен получить эту семантику из штатного представления/парсера; запрещено молча подменять пустой пароль общим. Проверить на искусственных fixture до подключения адаптера к AuthService.

Пустой эффективный пароль, неоднозначный адрес, ошибка чтения или разбора блокируют соответствующий вход; некорректная конфигурация блокирует старт с безопасной диагностикой. Обновление конфигурации применяется перезапуском FFIDO. Нет fallback к старому снимку при неудачном старте.

### 2. Адрес определяет пользователя

Пароль сравнивается точно, без обрезания и изменения регистра, с защитой сравнения от зависимости времени от совпавшего префикса. Нужен непустой валидный UTF-8 текст имени с существующими ограничениями профиля. При первом подтверждённом входе сервер создаёт профиль по адресу и введённому имени; в дальнейшем сохраняет серверное имя и возвращает его обоим клиентам. Имя не служит дополнительным секретом и не создаёт нового пользователя для того же адреса.

Сохранить user_id старого профиля при однозначном совпадении канонического адреса. Добавить уникальное сопоставление адреса; конфликты миграции требуют администратора, автоматического объединения нет. Идентичность не зависит от устройства или случайного секрета сессии.

### 3. Отдельная внутренняя сессия для каждого входа

Добавить Login, RestoreSession и Logout в общий proto, регенерировать C++/Dart штатными средствами. Login проходит без Bearer, но с общими ограничениями размера/deadline/конкуренции и ограничением попыток: по адресу и источнику, с ограниченным объёмом памяти и временем жизни записей. Не доверять произвольным forwarded-заголовкам. Ошибки неизвестного адреса и неверного пароля одинаковы.

Переиспользовать криптографическую генерацию и проверку Bearer внутри транспорта. В SQLite хранить только digest, user_id, срок действия и отзыв сессии; по умолчанию срок 30 суток с явной датой истечения. RestoreSession проверяет текущую сессию без продления и возвращает профиль/срок; после истечения требуется пароль. Logout отзывает только текущую сессию. Удаление линка и изменение эффективного пароля инвалидируют прежние сессии при следующем запуске; для определения изменения хранить HMAC-отпечаток учётных данных с отдельным локальным серверным ключом, не сам пароль и не обычный несолёный digest пароля. Ключ вне Git с ограниченными правами; при его потере все сессии требуют нового входа.

Ручные provision/revoke заменить администрированием сессий без печати секретов и без выдачи доступа в обход HPT. Старые заранее выданные токены отозвать при миграции.

### 4. Сохранение входа и понятная форма

SettingsWidget содержит «Имя», «FTN-адрес», «Пароль», «Адрес сервера», «Подключиться», «Выйти». Успех показывается только после подтверждения сервера. Пароль скрыт и очищается после входа; секрет сессии не отображается. Ошибки полей, неверного пароля и недоступности различаются понятным текстом.

На Android/iOS и настольных платформах использовать защищённое системное хранилище через Flutter-пакет с нужными реализациями. На macOS используется системная login Keychain (`usesDataProtectionKeychain: false`), доступная локальной настольной сборке без provisioning profile; на остальных платформах остаются штатные защищённые реализации пакета. В SharedPreferences допустимы только несекретные поля; секрет привязан к нормализованному endpoint. На Web сессия только в памяти. Если защищённое хранилище недоступно, не переходить к plaintext: разрешить текущую сессию с явным сообщением, что вход не сохранён.

При запуске восстановить сессию до загрузки личных данных. Временная недоступность не удаляет сохранённый секрет, но не считается успешным восстановлением; UNAUTHENTICATED удаляет его и открывает вход. Смена сервера/пользователя отменяет старые RPC, меняет epoch и очищает кеш; поздние ответы не попадают в новую сессию. Выход очищает локальные данные даже при сетевой ошибке, отдельно сообщает о невозможности серверного отзыва.

### 5. Два устройства и VPS

Android и ноутбук используют одинаковый `https://fido.example.org:порт` и нативный gRPC по TLS, без прямого доступа к HPT, SQLite или мейлеру. На VPS открыть только нужный порт API, настроить DNS и доверенный сертификат; прокси, если используется, должен поддерживать HTTP/2 gRPC. Web использует существующий gRPC-Web gateway. Сервер не получает от клиента путь к HPT.

При возврате приложения на передний план и ручном обновлении заново запросить конференции, открытый список сообщений и активные личные экраны, обходя пригодный кеш первой страницы. Кеш остаётся резервом только при транспортной недоступности и с прежней изоляцией. Общие SQLite-данные уже обеспечивают серверную прочитанность, историю и закладки; новые сессии не создают новые аккаунты. Отправка с телефона доступна на ноутбуке после успешного сохранения и обновления; доставка в FTN по-прежнему выполняется HPT/мейлером. Незавершённые черновики и позиция чтения не синхронизируются.

## Risks / Trade-offs

- [Различия установок Husky] → связать с совместимой fidoconfig, проверить штатные fixture Include/условий/пустых значений, документировать установку и ошибку отсутствующей библиотеки.
- [Пароль линка даёт доступ к FFIDO] → только настроенные линки, TLS, ограничения входа, отсутствие секретов в диагностике; не использовать пароль глобального Sysop вместо пароля линка.
- [Зависимости защищённого хранилища] → добавить только необходимый пакет без обновления остальных, проверить Android и ноутбук; отказ хранилища не приводит к plaintext.
- [Изменения видны после обновления] → обновлять при resumed и вручную; push и непрерывный polling не обещать.
- [Удалённый logout не выполнен без сети] → удалить локальный секрет немедленно, уведомить пользователя, серверная сессия ограничена сроком.

## Migration Plan

1. Согласованно остановить FFIDO и сохранить резервную копию SQLite и конфигурации.
2. Транзакционно сопоставить старые профили с каноническими адресами, проверить уникальность, добавить сессии/отпечатки, отозвать legacy-токены. При конфликте откатить всю миграцию, не менять JAM и личные данные.
3. Настроить HPT-путь и ключ, установить совместимую fidoconfig, обновить сервер и клиент. Новые поля proto добавляются без перенумерации старых; legacy-вход не поддерживается. Старый клиент требует обновления.
4. Проверить два клиента и перезапуск. Для отката остановить сервер, восстановить SQLite из копии и прежнюю сборку; изменения после backup отдельно согласовать, не откатывать работающую базу поверх новых записей.
