# Design

## Context

Мотивация описана в proposal.md. Исходное дерево чистое. План затрагивает существующие Flutter-клиент, C++ backend и операторские средства HPT.

Наблюдения 29.10.2026 через `ssh amster2` (alias из SSH-конфигурации):

- Backend работает в контейнере `ffido`, `/opt/ffido/bin/fidoback /etc/ffido/config.json`. Каталог хоста `/home/yurik/fido` смонтирован в `/home/fido` и `/srv/fido`.
- HPT объявляет `echoarea utf-8 /home/fido/msgbase/utf-8 -b Jam`; сервер использует default KOI8-R и override `utf-8: UTF-8`.
- Авторизованный `ListMessages` владельца для `utf-8`, limit 10, offset 0/10/20, сортировка date descending возвращает `INTERNAL: Message storage operation failed`. В рамках проверки выполнены Login/ListMessages/Logout, без получения полного сообщения и изменения его прочитанности.
- Независимый структурный разбор `.jdx/.jhr/.jdt` выявил 30 записей: 28 с `CHRS: UTF-8 4`, две без CHRS. Среди 120 значений тела, sender/receiver/subject 55 невалидны как UTF-8, 65 валидны. Для всех 55 обратное `decode(koi8-r).encode(cp866)` даёт валидный UTF-8 и точный round-trip. Ни одно значение не оказалось необратимым. Содержимое писем и секреты не копировались в артефакты.
- Это свидетельствует о прежней побайтовой CP866 → KOI8-R перекодировке UTF-8; конкретный исторический процесс не установлен. Текущий `deploy/hpt/hpt-transport.patch` уже исключает `utf-8` из intab/outtab. Проверка исторической базы не доказывает отсутствие дефекта во всех путях текущего HPT, поэтому нужен изолированный транспортный регрессионный тест.
- Журнал `ffido.log` содержит транспортные TLS/HTTP2 ошибки, но не даёт полезной диагностики конкретного сбоя декодирования. Основное доказательство — RPC и независимая проверка байтов.

В `MessageService::MarkConferenceRead` после проверки read permission явно отклоняется kind != kEcho. Клиент повторяет ограничение в `markEchoRead` и меню. SQLite уже хранит массовые операции по пользователю, области и поколению; отдельная схема для эхи не нужна. `GetMessageNumbers` не требует декодирования тела.

`quoteReply(String original)` добавляет `> ` всем строкам; редактор передаёт только тело. `quoteDepth` уже распознаёт инициалы и вложенные `>`. Действующие спецификации запрещают массовую отметку вне эхи: delta явно расширяет этот контракт. Незавершённые и завершённые соседние changes не редактируются.

## Goals / Non-Goals

**Goals:** единый read-state для всех разрешённых JAM-областей, безопасное восстановление конкретного исторического искажения, однозначное FTN-цитирование.

**Non-Goals:** автоматическая догадка кодировки, пересоздание базы с новыми ID, очистка/ретоссинг служебных областей, смена технологий, новая версия RPC или изменение политики публикации.

## Decisions

### 1. Расширить существующую массовую операцию

Убрать только ограничение EchoArea, сохранив проверку доступа до открытия базы, проверки operation_id, FindBulkRead, снимок номеров и транзакцию SQLite. Учитывать доступность поддерживаемой JAM через действующий каталог. Служебное read-only запрещает публикацию, но не персональную отметку; чужие owner/point области по-прежнему недоступны.

Клиент использует canRead и доступность базы вместо kind == echo, обобщает сообщения до «области»/«сообщений» и повторяет прежний operationId после неопределённого результата. `refreshBulkPage` проверяется для personalMailbox: обновление не вызывает GetMessage, не меняет positionRevision, последнее открытое письмо, предложение продолжения и историю. Смена сессии по-прежнему отменяет устаревший результат.

Альтернатива — отдельный RPC для каждого типа или обход писем — дублирует готовую транзакционную семантику и ухудшает атомарность.

Совместимость: wire-контракт остаётся прежним; обновлённый сервер поддерживает старый клиент. Новый клиент со старым сервером получает штатный отказ вне эхи, не показывает успех и не запускает обход. Развёртывать сервер перед клиентом; capability RPC ради этого изменения не добавлять.

### 2. Восстановление как отдельная операторская процедура

Добавить узкий инструмент в `scripts/` со стандартной библиотекой Python и описанием в `deploy/hpt/README.md`. По умолчанию dry-run: ограниченный структурный разбор JAM, номера/типы полей, хеши файлов и план замен без содержания сообщений. Обрабатывать только явно выбранную UTF-8 базу в разрешённом каталоге, отвергать выход через путь/симлинк и повреждённые структуры. Правило действует на тело и текстовые подполя имён/темы; MsgID/REPLY, адреса и kludges не перекодируются.

Для каждого невалидного UTF-8 значения проверить обратимость KOI8-R → CP866 → UTF-8 и точный round-trip. Валидные значения сохранить; неизвестные варианты блокируют весь apply. Дополнительно требовать ту же длину байтов: данное побайтовое восстановление позволяет менять только диапазоны `.jhr/.jdt`, оставляя все смещения, `.jdx/.jlr`, поколение и идентичность нетронутыми. Проверять контрольные суммы исходных файлов непосредственно перед применением.

Применение — при остановленных backend, worker и остальных пользователях базы (включая jamnntpd/cron), под общим exclusive coordination lock. До записи сделать и проверить согласованную резервную копию всех файлов базы; сохранить manifest и hashes вне Git. Частично применённая база остаётся в maintenance до завершения или полного отката. Запись, fsync, повторный разбор и независимое сравнение разрешённых диапазонов обязательны; при ошибке восстановить полный набор исходных файлов перед запуском. Повтор dry-run после успеха должен давать ноль замен.

Не выбирать override KOI8-R: это замаскирует проблему и даст неверный текст. Не добавлять эвристическое восстановление в ReadMessage: успешное однобайтовое декодирование само по себе не доказывает правильность. Не пересоздавать JAM через append: это нарушит generation/номера, SQLite read-state, ссылки и reply-цепочки.

Сам propose и обычный apply кода не разрешают автоматическое исправление рабочих данных: отдельный запуск подготовленной процедуры на amster2 выполняется только по явному запросу оператора на восстановление. Тесты и репетиция на временной базе входят в реализацию.

### 3. Единый FTN-форматтер ответа

Передавать в `quoteReply` имя `original.fromName`. Использовать общий разбор префикса для форматирования и `quoteDepth`, чтобы не разошлись генерация и подсветка. Обычная строка Yuriy Khashev → `YK> текст`; `AB> текст` → `AB>> текст`; старое `> текст` → `YK>> текст`. Инициалы существующей цитаты сохраняются, инициалы текущего отвечающего не подставляются.

Инициалы: первая буква/цифра каждой части имени, разделённой пробелами, верхний регистр Unicode, максимум восемь символов после преобразования; резерв `?`. Это проектное соглашение FTN-формата, а не утверждение о единственном внешнем стандарте. Поддержать резерв в подсветке. Пустые/пробельные строки не получают префикса; CR/CRLF нормализуются, остальной текст и отступы сохраняются; после блока два LF. Адресация и in_reply_to не меняются. Изменения касаются ответов, формат пересылки остаётся существующим.

## Risks / Trade-offs

- Ошибочная интерпретация исторических данных → явный выбранный набор, строгая обратимость, отчёт и сверка с независимым образцом; никаких общих fallback.
- Сбой между записями двух файлов → остановленные читатели, полный backup, fsync и полный откат до снятия maintenance. Двухфайловая запись не объявляется атомарной.
- Повторная порча транспортом → изолированный цикл API → JAM → HPT scan/pack → toss → API с UTF-8 телом, темой и именами; новую рабочую отправку ради теста не выполнять.
- Скрытое изменение позиции личного ящика → отдельные widget/integration тесты ревизии, истории и отсутствия GetMessage после bulk.
- Сохранённые валидные поля могли уже быть семантически искажены → инструмент не меняет их без доказательств; текущие количественные проверки доказывают валидность/обратимость, но не восстанавливают историческое происхождение.

## Migration Plan

1. Реализовать и проверить код на искусственных JAM, включая смешанный исторический пример; прогнать проверки обоих компонентов.
2. Обновить backend перед клиентом штатной процедурой отдельного развёртывания. Миграции RPC и SQLite не нужны.
3. Оператору передать dry-run, ожидаемые изменения и инструкцию; в отдельной разрешённой операции репетировать на согласованной копии и проверить все сообщения.
4. Для рабочей базы остановить пользователей и worker/cron, удерживать lock, сделать backup/manifest, сверить hashes, применить исправление, проверить структуры и метаданные. При неуспехе полностью откатить до запуска.
5. Запустить сервисы, проверить все страницы ListMessages и выбранные сообщения через API; полное чтение меняет read-state, поэтому использовать отдельный проверочный профиль или заранее согласованную проверку. Сопоставить счётчики и прежние ID/закладки. Производственные публикации не нужны.
6. Код откатывается обычным образом; восстановление данных откатывается всем согласованным набором файлов только при остановленных процессах и отсутствии новых записей после backup. При новых записях автоматический откат запрещён.
