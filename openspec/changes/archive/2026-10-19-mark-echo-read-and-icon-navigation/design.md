# Design

## Context

`MarkRead(MessageReference)` в общем protobuf и `GrpcService::MarkRead` сейчас отмечают одно письмо через `MessageService::MarkAsRead`. `GetMessage` дополнительно фиксирует историю/позицию через `RecordMessageView`. SQLite использует read_status с user/conference/generation/message; метаданные общие между устройствами одного аккаунта. Эти два поведения нельзя смешивать при массовой отметке.

`MessageScreen` знает тип области, права чтения, выбранную цепочку и epoch сессии. `MainScreen` в `pages/reader_app.dart` использует BottomNavigationBar с четырьмя Material-иконками и подписями. Актуальные ACL поддержаны реализацией и незасинхронизированными изменениями hpt-echo-access/add-owner-private-areas: новый RPC использует текущую серверную проверку прав, не старое обобщение user-identity о равном доступе всех пользователей. Эти изменения не архивируются и не переписываются здесь.

## Goals / Non-Goals

**Goals:** серверная массовая операция с определённым охватом и повтором; компактная доступная навигация без смены четырёх разделов.

**Non-Goals:** отметка всех эх сразу, отмена прочитанности, массовые действия в личной/служебной почте, новые иконографические библиотеки, push-синхронизация, изменение HPT/JAM. Новая отметка не означает просмотр каждого письма.

## Decisions

1. Добавить RPC `MarkConferenceRead` с request `conference_id` и обязательным `operation_id`; response содержит `marked_count` (число новых отметок), `snapshot_count` (все живые сообщения снимка) и `generation`. Старые поля/методы не меняются. Auth и read ACL проверяются до доступа к данным и до выдачи результата повтора. Только AreaKind.echo и доступная JAM. Для отказа типа — FAILED_PRECONDITION, неизвестной эхи — NOT_FOUND, отсутствия чтения — действующая ACL-ошибка. Генерация операции клиентом использует имеющийся UUID/nonce-подход; API не принимает user_id.
2. Один вызов сервиса под штатной coordination/catalog lease строит снимок текущих живых номеров и generation, используя индекс/заголовки без чтения/декодирования тел. Каталог должен сохранять неизменность поколения и списка на период снимка/commit; повторно использовать существующую синхронизацию читателя и писателя. Не считать «всё» диапазоном от 1 до max: удалённые/несуществующие записи исключаются. Обход имеет линейную стоимость по числу живых записей и использует подготовленные SQL-операторы; при нехватке ресурсов/ошибке хранения транзакция откатывается целиком с понятной ошибкой UI. Не делать N клиентских MarkRead/GetMessage: это создаёт частичные результаты и ложную историю.
3. Расширить MetadataStore пакетной транзакцией: INSERT OR IGNORE точных read_status для user/conference/generation/номеров и durable receipt операции (user_id, operation_id уникальны; conference, generation, snapshot_count, marked_count). Это новая миграция от текущей схемы 7, не изменение существующих миграций. Receipt и отметки коммитятся вместе. Конкурентное одиночное чтение не теряется; счётчик новых отметок отражает только фактические вставки транзакции. Повтор готового ключа возвращает receipt, не пересобирая снимок даже после HPT/рестарта/смены generation; другая конференция с тем же ключом — ALREADY_EXISTS. После rollback без receipt повтор получает новый снимок первой успешной фиксации. История, reading_positions/revision, JAM Read и JLR не изменяются. Никакой бессрочной watermark-отметки всех будущих писем.
4. В MessageScreen добавить пункт overflow-меню с иконкой done_all и подписью «Отметить всё прочитанным», только для читаемой эхи. Диалог: «Отметить все сообщения в <имя> прочитанными? Это относится ко всей эхе, включая сообщения вне текущей страницы и цепочки». Кнопки «Отмена»/«Отметить». Ключ создаётся один раз при подтверждении. Заблокировать повторное нажатие до ответа. При сетевой неопределённости сохранить immutable conference/key в состоянии экрана и предлагать «Проверить/повторить» с тем же ключом; не выдавать новое действие, пока исход не уточнён. После ухода с экрана новый явный запуск является новой операцией, что отражено в документации. На epoch/session change сбросить UI операции и игнорировать поздний ответ. Отмена до запроса не вызывает RPC; отмена ожидания после отправки не обещает rollback сервера.
5. После подтверждения обновить текущую страницу/цепочку и счётчики конференции, инвалидировать кеш конференций текущего аккаунта, обновлять главный список/закладки при возврате штатным механизмом. Сохранить порядок, фильтр, открытое письмо и scroll насколько они ещё валидны. Для обновления selected использовать загрузку списка/кеша, а не GetMessage, чтобы bulk не перемещал last-opened. Не присваивать unread_count=0 оптимистично: могли поступить новые письма. Другой клиент видит изменения при refresh/resume; push не вводится.
6. Оставить BottomNavigationBar и текущие четыре маршрута. `showSelectedLabels=false`, `showUnselectedLabels=false`; сохранить label для semantics и добавить явные tooltip. Использовать статические Material home/home_outlined, bookmark/bookmark_border, history, person/person_outline с различимой выбранной формой (для history — индикатор выбора/контейнер вместо выдуманной динамической иконки). Поддержать активный/неактивный контраст, hover/focus и 48px hit targets. Не заменять нижние кнопки «Предыдущее/Следующее» чтения: запрос относится к четырём основным вкладкам.

## Risks / Trade-offs

- Большая эха и долгая SQLite-транзакция → один подготовленный INSERT, измерение fixture на 100000 записей и проверка rollback при ошибке/отмене до commit; никаких частичных батчей.
- Потеря ответа/поступление новых сообщений → durable receipt и повтор того же ключа; пользовательское новое действие намеренно включает новый снимок.
- Замена базы и HPT pack → существующий coordination протокол и generation, тесты новой базы/удалённых сообщений без изменения реальных файлов.
- Скрытые подписи ухудшают распознавание → знакомые Material-иконки, tooltip, semantics и выбранная форма, проверки клавиатуры и телефона.
- Старый сервер → UNIMPLEMENTED объясняется как «Сервер не поддерживает массовую отметку», без имитации через поштучное чтение и без ложного успеха.

## Migration Plan

Сохранить согласованный backup SQLite до запуска обновлённого сервера. Миграция добавляет receipt-таблицу, сохраняя read_status/профили/позиции. Старый клиент продолжает работать с новым сервером; новый клиент корректно сообщает о старом сервере. Для rollback сохранить изменённую БД и восстановить совместимый backup либо использовать новую серверную версию: прежняя бинарная версия может отвергать новую schema_version. Сначала проверить только временные JAM/SQLite, два аккаунта и две сессии одного аккаунта, затем отдельным запросом решать запуск на рабочих данных.
