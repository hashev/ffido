## Серверная репетиция и блокировка

`python -m unittest discover -s scripts/update -p 'test_*.py'` — 64 прошли.
Использовано отдельное Python-окружение с зависимостями updater.

Новый `scripts/check_footer_upgrade.py` поднимает отдельный Compose с
искусственными RU.ONE/RU.TWO и официальным digest 1.0.4. Seed через настоящий
Dart ApiClient выполнен. Реальный подписанный update до 1.0.7 отвергнут:
`Container state schema is incompatible`. В тестовой SQLite обнаружена схема
10, в опубликованном manifest разрешена только 9. Проверка не обходилась,
рабочие базы и production credentials не использовались. Контейнеры удалены.

После согласования диапазон текущих release metadata исправлен на 9–10.
`test_schema_compatibility.py` запускает реальный backend: новая БД, миграция
9→10, повторное открытие и отказ при 11. Release-тесты: 96 прошли. Проверка также зарегистрирована в CTest как
ReleaseSchemaCompatibility и отдельно прошла после повторной конфигурации CMake.
CMake configure/build прошли; CTest: 380 без ошибок (5 HPT сценариев сначала
пропущены, затем отдельно запущены с FFIDO_TEST_HPT — все 5 прошли).
Компилятор сообщил существующее предупреждение nodiscard в test_process.cpp:244;
этот файл не изменялся.

Локальная подписанная репетиция с исправленными metadata прошла:
`/tmp/ffido-footer-metadata-candidate-20261029-r4/result.json`.
Проверены отказ для фактической схемы 11 до переключения, update 1.0.4→1.0.7,
readiness и точный локальный digest, прежняя сессия и supports_message_footer,
автоматический/пользовательский footer в обычном письме, ответе и кросспосте,
сохранность после HPT scan и согласованное восстановление backup. SHA256 старого
`.jdt`: 38d1ad1b4766e3a4b859cb62234d0df8dfe6de95bac6eed5466af2dcb277f98c.

Кандидат — официальный бинарник 1.0.7 в частной обёртке с исправленным BUILD
metadata, подписанный временным QA-ключом; registry loopback, updater — отдельная
копия. Только у неё заменены транспорт discovery, allowlist registry и публичный
ключ. Проверки подписи, платформы, digest, schema и Docker выполняются реально.
Это не опубликованный исправленный выпуск; доверенные ключи production не менялись.

При restore файлов меняется JAM generation, поэтому тест обновляет список,
проверяет тело по новой ссылке и отдельно сверяет `.jdt`. Первоначальный отказ
по старому MessageReference был ожидаемой защитой от устаревшего поколения,
а не потерей сообщения. Неполные ранние репетиции не считались успехом.

Существующий test_compose_flow.py отдельно выявил ошибку отрицательной fixture:
несовместимый manifest отбрасывается discovery и даёт no-update вместо ожидаемого
отказа apply. Этот тест не ослаблялся; новая репетиция проверяет именно фактическую
неподдерживаемую схему 11 при валидном manifest 9–10.

Для production по-прежнему нужен новый официальный подписанный выпуск и
отдельный запрос на обновление. Опубликованный 1.0.7 не изменялся.
