# Design

## Context

Мотивация — proposal.md. Анализ выполнен 28.10.2026 по рабочему дереву b418909; до создания change дерево чистое. Скриншот — свидетельство интерфейса, а не инструкция и не доказательство состава APK.

### Подтверждённые факты

1. На скриншоте диалог Google Play Защиты «Вредоносное приложение заблокировано», FFIDO, «Это приложение может быть опасным» при установке обновления. Это соответствует классу Harmful App Blocked в документации Google, а не App Scan Recommended. Конкретная категория вредоносности, версия и хеш файла на скриншоте отсутствуют.
2. `apps/frontend/android/app/src/main/AndroidManifest.xml` запрашивает INTERNET и REQUEST_INSTALL_PACKAGES. В исследованном локальном merged release manifest дополнительно присутствуют штатные AndroidX startup/profileinstaller; нет SMS, accessibility, notification listener, device admin. Это не подменяет исследование публичного APK.
3. `AndroidUpdater.kt`: запрашивает право установки неизвестных приложений после действия пользователя; принимает APK только из закрытого cache; проверяет совпадение package ID и текущих сертификатов, возрастающий versionCode; использует PackageInstaller и обязательное действие пользователя на API 31+. Receiver не экспортируется. Скрытая установка и установка произвольных сторонних пакетов в этом пути не обнаружены.
4. Dart `update_service.dart`, `update_metadata.dart`, `update_host_io.dart` проверяют Ed25519-манифест, размер/SHA-256, канал, совместимость и HTTPS-адреса GitHub, включая redirects. Это ограничивает подмену обновления, но не является антивирусной проверкой и не доказывает безопасность SDK.
5. Gradle подписывает обычный локальный release debug-ключом; публичный путь с FFIDO_PUBLIC_RELEASE=true требует постоянного ключа. `.github/workflows/release.yml` собирает подписанный APK отдельно; `package.py` проверяет apksigner, ожидаемый fingerprint и запрещает Android Debug. Нельзя приписывать публичному APK debug-подпись по одной настройке fallback.
6. Git: встроенный updater добавлен a564b0f от 22.10.2026. В `docs/testing.md` прямо зафиксирован выбор Install without scanning, в том числе для QA с production-сертификатом. В `scripts/update/test_android_flow.py:345` есть соответствующая подсказка. Эти проверки подтверждают установку и сохранение данных, но не приёмку Play Protect.
7. Локальный APK — версия 1.0.0/build 41001, Android Debug сертификат SHA-256 `0272c3acfb8dbcf7f3cf902252f12952c5d22974dcab0d4b491ea3f9a50da4fc`; его нельзя считать текущим публичным выпуском. Локальный manifest targetSdk=36/minSdk=24, поэтому гипотеза «слишком старый targetSdk» по нему не подтверждается.
8. GitHub Releases сообщает для v1.0.4 (27.10.2026) commit `4da3372d57ae9da50490d6187a4733a4a8596827`, APK `ffido-v1.0.4-client-android-universal.apk`, размер 55620341, SHA-256 `3b5a867af40d60dad8d98dc63fbb21ccd8f0245563d04a6a2663bdeac3e6c39c`. Владелец при применении подтвердил Pixel 6a и встроенное обновление 1.0.3→1.0.4; совпадение фактического APK с этим хешем остаётся непроверенным.

9. Официальный v1.0.4 скачан и проверен: SHA-256 совпал с Releases; apksigner verify --verbose успешен, схема v2, один RSA-4096 signer CN=FFIDO Android Release, fingerprint `61f1f10c15f8d3724dfe19938f9923ed2878dd9c81113c90489aded29af3fbd0`, совпадает с ранее документированным постоянным сертификатом. Версия 1.0.4/build 1019, minSdk=24/targetSdk=36, packaged identity содержит тот же commit. ZIP testzip успешен, стандартный заголовок 504b0304. v1/v3/SourceStamp отсутствуют, но apksigner подтверждает корректность для заявленного minSdk; само отсутствие этих схем не доказывает причину блокировки.
10. В binary manifest публичного APK нет debuggable/testOnly; INTERNET, REQUEST_INSTALL_PACKAGES и собственное signature-permission `io.github.hashev.ffido.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. Экспортированы launcher Activity и штатный ProfileInstallReceiver с android.permission.DUMP; updater receiver и startup provider закрыты. Нет SMS/accessibility/notification listener/device admin. Найдены ожидаемые Flutter/Dart JNI/datastore .so для трёх ABI; файлов с fixture/integration_test/update_driver в именах нет. Поиск имён не доказывает отсутствие QA-кода в AOT и не является полным анализом вредоносности.
11. `git diff v1.0.3 v1.0.4` не показывает изменений Android-кода/manifest, pubspec.lock, update_service/metadata/host/controller или package.py. Есть изменения release CI/cache и удаление desktop-startup вызова из update_ui. Следовательно, если 1.0.3 действительно устанавливалась без предупреждений, это ослабляет версию о новом updater/permission в 1.0.4; нужны сравнение байтов двух официальных APK и проверка возможного изменения облачной классификации. Утверждать отсутствие компрометации только по исходникам нельзя.

### Вывод о причине и гипотезы

Подтверждён непосредственный механизм отказа: классификация устанавливаемого APK Google Play Protect как потенциально вредоносного. По изображению и исходникам нельзя доказать внутреннюю причину классификации или объявить её ложной.

Одна из приоритетных проверяемых гипотез — добавленный 22 октября путь «скачивание и установка APK вне магазина» с REQUEST_INSTALL_PACKAGES стал фактором эвристики. Совпадение по времени и наличию поведения не доказывает причинность. Отдельно проверить репутацию конкретного APK/сертификата, ложное срабатывание на native Flutter/SDK, отличие раздаваемого файла от официального и компрометацию цепочки сборки. Смена текстов/иконки или обфускация не являются доказанным исправлением.

Политика Google Play ограничивает REQUEST_INSTALL_PACKAGES и самообновление приложений в магазине; FFIDO распространяется через GitHub, поэтому нарушение этой политики нельзя автоматически объявить причиной вне-магазинного Play Protect verdict. Проверка личности Android-разработчика — отдельный механизм; текст скриншота не даёт оснований связывать инцидент с ним. Подпись APK, Ed25519-подпись metadata и одобрение Play Protect — три разные проверки.

### Первичные источники

- https://developers.google.com/android/play-protect/warning-dev-guidance — виды предупреждений, проверки и апелляция.
- https://support.google.com/googleplay/android-developer/answer/2992033 — app verification и оспаривание классификации.
- https://support.google.com/googleplay/android-developer/answer/12085295 — правила REQUEST_INSTALL_PACKAGES для Google Play; не универсальный запрет стороннего распространения.
- https://support.google.com/android/answer/17065026 — отдельная проверка личности разработчика.

## Goals / Non-Goals

**Goals:** доказуемая идентичность APK; выявление реальных дефектов; воспроизводимая оценка блокировки; корректный отказ updater; пакет доказательств для пересмотра Google; редактируемый footer исходящих эховых писем; проверка API 35 и передаваемый владельцу APK с постоянным сертификатом.

**Non-Goals:** обещать отсутствие предупреждений Google, обходить защиту, менять package ID/сертификат, внедрять Google Play distribution или удалять встроенное обновление без отдельного решения. Новые внешние зависимости не требуются. Сервер и gRPC меняются только для согласованной функции Tagline/Origin; это не доказанное средство устранения предупреждения Play Protect.

## Decisions

### 1. Сначала связать инцидент с байтами APK

Получить от владельца версию A и версию B, канал, источник APK, его SHA-256, модель/Android, дату первого появления и полный текст через «Подробнее», без личных данных. Скачать официальный B и предыдущий успешный выпуск; проверить ZIP/APK структуру, apksigner, fingerprint, manifest, packaged identity и entrypoint. Сравнить permissions/components/SDK/native libraries/dependency lock по тегам. Отчёт хранить как безопасный JSON и краткую запись в docs/testing.md; полные дампы/локальные APK не коммитить.

Если хеш не совпадает — расследовать источник/раздачу до изменения приложения. Если сертификат отличается — остановить распространение подозрительного файла через отдельное решение владельца, не предлагать удалять рабочее приложение. Если байты подлинные — исследовать вердикт и зависимости. Сборка текущей ветки вместо проверки установленного файла не отвечает на вопрос об инциденте.

### 2. Проверять конечный пакет в существующем release pipeline

Расширить имеющийся `scripts/release/package.py` и тесты, используя установленные Android build-tools. Сверять отчёт с уже существующей release identity и хешем упакованного APK; валидировать release сертификат, package ID, versionCode/versionName, SDK, debuggable/testOnly, список разрешений и экспортируемых компонентов. Утверждённый baseline брать после проверки реального APK, не запрещать штатные защищённые AndroidX-компоненты по одному exported=true. Проверять отсутствие именно QA entrypoint/fixture assets, не считать слово integration_test в исходных dev_dependencies доказательством включения QA в release.

Публичный job блокировать при локальном структурном/идентификационном нарушении. Play Protect — отдельная ручная запись со статусом, привязанная к SHA-256; не вводить фиктивный автоматический API проверки и не заявлять, что каждый CI APK прошёл Google. Секреты подписи остаются в существующем release environment.

### 3. Разделить функциональный QA и Play Protect

Существующая API 24/25/35 матрица сохраняется. Убрать из общих пользовательских инструкций совет обходить сканирование; изолированный fixture QA помечать как тест установщика с явным непроверенным статусом Play Protect, если сканирование не выполнено. Отдельно проверить оригинальный публичный APK на сертифицированном устройстве с активной защитой: чистая установка B, обновление A→B вручную и встроенным updater. Фиксировать отказ, предупреждение, успех и недоступность проверки раздельно. Сертифицированное устройство с GMS необходимо, AOSP/adb installation не заменяют эту проверку.

Для проверки эвристики допустим отдельный непубликуемый эксперимент без установки пакетов/REQUEST_INSTALL_PACKAGES при сохранении остального поведения и прежнего доверенного сертификата, если он доступен владельцу. Учитывать, что изменение байтов/версии и облачного verdict мешает строгому сравнению; исчезновение предупреждения только усиливает гипотезу. Не раздавать эксперимент как исправление и не переносить его в main без решения о смене UX.

### 4. Обработать доступный отказ без выдуманной причины

`AndroidUpdater.complete()` сейчас возвращает только общую ошибку с числом; Dart install path не сохраняет подробный контекст отказа. Передавать стабильный тип результата, числовой PackageInstaller status и безопасную диагностическую сводку; STATUS_FAILURE_BLOCKED обозначать как запрет системы, не автоматически как Play Protect. Не показывать сырой EXTRA_STATUS_MESSAGE без очистки. Отмена — отдельный исход, без автоматического повтора.

Проверить фактическое завершение callback при Play Protect на устройстве: система может не выдать точную причину. Возврат/пересоздание activity должно давать возможность восстановить состояние по доступной session-информации; не превращать произвольный timeout в диагноз «вредоносный APK». Все исходы оставляют старую версию и настройки.

### 5. Исправление по доказательствам и апелляция

Обнаруженный реальный дефект исправляется минимально, с регрессионным тестом и повторной проверкой того же пути. Если проверенный официальный APK остаётся заблокированным и нарушения не обнаружены, подготовить обращение через официальную Play Protect appeal форму: package ID, version/build, APK URL/SHA-256, сертификат, снимок предупреждения, результаты аудита, объяснение ограниченного self-update и пользовательского подтверждения. Не отправлять автоматически в рамках planning/apply; владелец отправляет или отдельно поручает это действие. Удаление permission не гарантирует снятие уже существующей классификации; при необходимости изменения updater сначала обновить требования «без обязательного браузера» и согласовать последствия.

### 6. Настройки Tagline и Origin

При согласовании дополнения владелец подтвердил: Tagline — текст строки после `---` (в терминологии FTN это tearline). Сейчас `MessageService::CreateMessage` в `apps/backend/src/service/message_service.cpp` добавляет для эхи фиксированные `--- FFIDO` и ` * Origin: FFIDO (<адрес>)`. Клиентский `SettingsWidget` сохраняет поля подключения через SharedPreferences, а сообщения, crosspost и UUE проходят отдельные пути API. Простое добавление текста в body клиента оставило бы старый серверный footer и нарушило единое оформление.

В настройках добавить отдельную группу «Оформление исходящих сообщений»: однострочные Tagline, Origin, сохранение без переподключения к серверу и «Сбросить к значениям по умолчанию». Использовать действующее хранилище предпочтений текущего экземпляра/профиля клиента, не смешивать их с серверным профилем имени/FTN-адреса. Изменения должны учитываться существующей защитой от обновления при несохранённых данных. Пустой ввод означает возврат к автоматическому значению, а не отключение footer. В отсутствие override Tagline вычисляется как `FFIDO <version>` из той же встроенной identity, что отображает версию клиента и согласована с собираемым пакетом; default Origin — `https://github.com/hashev/ffido`. Обновление клиента меняет только автоматический Tagline, пользовательские значения сохраняются. Reset удаляет overrides, не фиксирует текущую версию навсегда.

Сервер для новой отправки в эху формирует ровно один footer:

```text
--- <tagline>
 * Origin: <origin> (<подтверждённый FTN-адрес отправителя>)
```

Текст после `---` и описание Origin — пользовательские; адрес в скобках берётся только из подтверждённого профиля сервера. Содержимое цитат и ранее написанные в body строки не переписываются, новый footer не добавляется в netmail/local. Применение едино для нового письма, ответа, пересылки, всех копий кросспостинга и частей UUE в эхе. Настройки захватываются перед первой отправкой операции, остаются теми же при повторах и частичном продолжении после изменения настроек. Все существующие правила адресации, доступа, CP866/CHRS и нормализации исходящей кириллической Н сохраняются.

### 7. Аддитивный gRPC-контракт и совместимость

В `CreateMessageRequest` добавить необязательный объект оформления с Tagline/Origin; отсутствие объекта отличается от явно переданного оформления. Передать тот же снимок в операцию UUE и вложенный запрос кросспостинга. Номера существующих protobuf-полей не менять. В `SessionInfo`, получаемый Login/RestoreSession, добавить узкий признак поддержки пользовательского footer. Старый клиент игнорирует новые поля; новый сервер при запросе без оформления сохраняет исторический `--- FFIDO` / `Origin: FFIDO`, чтобы не менять письма старых клиентов и историю их повторов.

Новый клиент на новом сервере передаёт явные эффективные значения, включая defaults. На старом сервере отсутствие признака поддержки не мешает обычной отправке с прежним оформлением, но клиент заранее объясняет, что пользовательский footer требует обновления сервера. При явно заданных пользовательских overrides отправка не должна молча игнорировать настройки: до RPC показать необходимость обновить сервер, сохранив черновик. Локальное редактирование/сохранение настроек доступно и без подключения; подтверждение применения зависит от серверной поддержки. Не вводить отдельную универсальную систему capabilities или изменение major версии протокола.

Валидация на клиенте и сервере: корректный UTF-8, максимум 256 UTF-8 байт на поле, отсутствие CR/LF, NUL, SOH и остальных управляющих C0/DEL. При сборке JAM дополнительно проверять кодируемость и суммарный размер уже оформленного тела в действующих лимитах; не применять тихую потерю символов или усечение. Ошибки указывают поле и оставляют настройки/черновик доступными для исправления. Пользовательские значения проходят существующую нормализацию исходящих полей, а хеш операции строится по исходному запросу до неё.

Включить наличие и исходные значения оформления в отпечатки обычной отправки, crosspost и UUE. Для отсутствующего объекта сохранить старую последовательность хеширования и существующие завершённые операции. Для нового объекта использовать однозначное разделение/маркер версии; новый запрос с тем же operation_id и иным footer даёт прежний конфликт ALREADY_EXISTS. Снимок оформления хранить вместе с существующим durable состоянием незавершённых group/UUE-операций. Если существующему формату хранилища понадобится добавление полей, читать старые записи как «оформление отсутствует» и покрыть миграцию тестами; не удалять журнал и не пересоздавать пользовательскую базу.

### 8. API 35 и APK для Pixel 6a

После реализации footer и проверок обеих сторон выполнить реальное A→B на API 35: подтверждение, отказ в праве установки, отмена, запрет/ошибки в доступных тестовых сценариях, чужая подпись/пакет, равная и меньшая версия, восстановление после замены и сохранение настроек/защищённой сессии. Для API 35 x86_64 использовать существующий закреплённый образ и Linux/KVM в доступной среде; если на текущем Apple Silicon он не запускается, допустим совместимый API 35 arm64-образ с отдельно записанным происхождением и ограничением относительно CI. API 36 не выдавать за API 35 и отсутствие инфраструктуры не отмечать как успех. QA одноразовых APK и облачный verdict Google по-прежнему разделены.

Подготовить обычный main-target universal APK, без QA entrypoint, с тем же application ID `io.github.hashev.ffido` и постоянным сертификатом SHA-256 `61f1f10c15f8d3724dfe19938f9923ed2878dd9c81113c90489aded29af3fbd0`. Использовать существующий publicRelease-путь Gradle и установленный Flutter 3.47.7, без debug fallback и смены ключа. Если ключ недоступен, сообщить конкретное ограничение; не заменять сертификат одноразовым. Приватные ключи/пароли не копировать в репозиторий, APK или журналы.

Новая видимая версия должна отличаться от 1.0.4 и быть согласована с клиентом, сервером и packaged identity по существующим release-правилам; конкретный номер выбрать при реализации после сверки актуального состояния. versionCode выбрать выше максимума опубликованных публичных сборок и известной установленной версии Pixel; не переносить QA-номера 41001/41002 в реальный канал. На этапе подготовки сверить номера снова, не фиксировать 1020 как гарантированно свободный.

После сборки выполнить `apksigner verify --verbose --print-certs`, аудит конечного APK и проверку его SDK/versionCode/identity/отсутствия QA-маркеров. Передать владельцу локальные APK, SHA-256 и audit JSON с описанием изменений и известным статусом Play Protect. Если сборка содержит незакоммиченные изменения, записать это в сопроводительном отчёте с воспроизводимым описанием исходного diff; не выдавать HEAD за точный опубликованный проверенный коммит. Для будущего выпуска сохранять существующий gate чистой release identity. Непубличная сборка для ручной проверки не требует публикации GitHub Release; сам APK не добавляется в Git. ## Risks / Trade-offs

- [Непрозрачный и меняющийся облачный verdict] → не обещать срок и результат; сохранять дату и хеш каждого прогона.
- [APK пользователя неизвестен] → вывод о точном триггере остаётся неподтверждённым до сопоставления; это не мешает подготовке аудита и диагностики.
- [Перепутан локальный QA и публичный release] → идентификация по хешу/подписи, отдельные отчёты.
- [Изменение ключа ломает обновление и доступ к данным] → сохранять существующую идентичность, не рекомендовать переустановку.
- [Разрешение установки необходимо текущему контракту] → сохранить его; эксперимент без него не является утверждённым продуктовым изменением.
- [Вердикт может зависеть от SDK или компрометации] → не ограничиваться updater; исследовать состав реального APK и историю зависимостей.

## Migration Plan

Сохранить внедрённые аудит и диагностику без изменения схемы update metadata. Сначала обновить совместимый backend с аддитивным gRPC-расширением footer, затем клиент; старые запросы и записи операций сохраняют прежнее поведение. При откате backend клиент обнаруживает отсутствие поддержки и не теряет черновик; настройки остаются локально. Не удалять пользовательские данные или журнал операций. Прогнать проверки клиента/сервера и Android A→B, включая API 35; подготовить подписанный APK для отдельной проверки защиты владельцем на Pixel 6a. Публикация — только по отдельному запросу. Если исправление требует нового выпуска, использовать возрастающий versionCode и тот же release-сертификат. Уже опубликованные APK не заменять. Откат исходников выпускать новой версией с большим build number; не пытаться понизить установленный versionCode.

Дополнительные риски: [Старый сервер игнорирует новые protobuf-поля] → проверка поддержки до отправки пользовательского footer; [Смена настройки во время повтора] → неизменяемый снимок операции; [Неверная release identity или занятый versionCode] → повторная сверка перед сборкой и отдельное описание непубличного source tree.
