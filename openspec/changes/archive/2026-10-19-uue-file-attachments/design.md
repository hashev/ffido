# Design

## Context

Мотивация и согласованный объём — в `proposal.md`. В `apps/backend/include/domain/message.hpp` и `apps/frontend/lib/models/message.dart` есть заготовки attachments, но общий protobuf-контракт и mapping не передают вложения. Файловых диалогов в клиенте нет. Реальный путь отправки проходит через `message_service.cpp`, durable operation journal и JAM writer; повторное независимое append для частей обошло бы гарантии восстановления.

Существующая отправка нормализует Н → H и записывает CP866. Личные ящики отделены от транспортного Netmail; эту границу нужно сохранить при поиске частей. Каталог JAM специально не декодирует тексты. Текущая SQLite schema — 8; незавершённые изменения других OpenSpec в этом предложении не синхронизируются и не архивируются.

## Goals / Non-Goals

**Goals:** сервер является источником метаданных и сборки; одинаковая работа на телефоне и ноутбуке; ограниченные расходы памяти/диска; восстановление частичной отправки; сохранение оригинальных JAM и видимого редактируемого текста.

**Non-Goals:** универсальное распознавание всех исторических split-диалектов, исправление повреждённых данных, автоматическое чтение чужих областей, атомарная публикация группы писем во всей FTN, повторная отправка вложения при обычном ответе. Первая версия отправляет один файл за операцию; reader распознаёт несколько самостоятельных блоков в письме.

## Decisions

### 1. Классический кодек и проверяемая совместимость

Серверный кодек работает с байтами и целыми строками, отдельно от текстовой нормализации. До 45 исходных байтов на строку, поддержка space/backtick, строгие длины и алфавит. Поток имеет один `begin 644 <ascii-name>`, нулевую строку и `end`; начало только в первой части, конец только в последней. Данные не переносятся по ширине редактора, не обрезаются и не проходят замену символов. Текст письма, темы и имена продолжают действующие CP866/Н → H правила. Для заголовка используется безопасное ASCII-имя; оригинальное отображаемое имя сохраняется в метаданных FFIDO, при отсутствии метаданных показывается имя из begin.

Проверены локальные исходники GoldED+: `golded3/geedit2.cpp` (begin/45 байтов/нулевая строка/end), `goldlib/uulib/uuencode.cpp` (частичный encode), `goldlib/uulib/uunconc.cpp` (распознавание section-разделителей). Источник: [GoldED+](https://github.com/golded-plus/golded-plus), [encoder](https://github.com/golded-plus/golded-plus/blob/master/goldlib/uulib/uuencode.cpp), [decoder](https://github.com/golded-plus/golded-plus/blob/master/goldlib/uulib/uunconc.cpp). Распознавание строк `sum -r/size … section…` и `section … end…` в decoder не доказывает проверку контрольных сумм. В первой версии эти точные хвосты допускаются как разделители вне полезных строк; неизвестные оформления не удаляются эвристически.

Матрица fixture: одиночный GoldED-подобный блок; классический поток, разделённый по строкам с темами `[n/N]`; указанные section-хвосты; FFIDO-метаданные. Независимый oracle — стандартный `binascii`/внешний uudecode для классического потока. Честно фиксируем: структурно корректный старый UUE без размера/хеша может скрывать незаметную порчу. Автоматическая «починка» запрещена.

### 2. Идентичность передачи и поиск

Исходящие части получают тему `<subject> [n/N]`, уникальный MsgID и дополнительный FTN-kludge `FFIDO-UUE` с версией, случайным transfer-id, номером/числом частей, полным размером, SHA-256, безопасным отображаемым именем. Конкретное экранирование — версионированная ASCII-грамматика с ограниченными длинами, зафиксированная в тестах и документации. Это расширение FFIDO, а не заявленный стандарт FTSC. Обычный декодер игнорирует kludge и читает объединённый классический поток.

Ключ сборки: logical conference, поколение, адрес источника, transfer-id и адрес назначения/направление для Netmail. Каждая часть сохраняет ссылки на реальный MsgID/номер/поколение. Повтор одинаковой части не увеличивает количество; конфликтующие байты блокируют готовность. Один transfer-id без совпадения области и источника не даёт права объединения.

Для внешнего multipart без идентификатора передачи и контрольной суммы разрешена автоматическая сборка по одной области/поколению, FTN-отправителю, основе темы без `[n/N]` и общему числу частей. В Netmail дополнительно совпадают адресат и направление. Полный набор сортируется по номерам без обязательного диалога; одинаковые дубли схлопываются, пропуски и конфликтующие дубли блокируют готовность. Имя файла само по себе не объединяет передачи. При отсутствии пригодной нумерации остаётся ручной выбор состава и порядка; ручной выбор также доступен для исправления предполагаемой группы.

Это уточнение заменяет первоначальное решение об обязательном подтверждении состава. Пользователь принял риск: даже единственный структурно корректный набор может смешивать разные передачи одного отправителя. Карточка, включая готовый файл и preview, постоянно показывает «Контрольной суммы нет; возможно смешивание частей разных передач». Сохранение и preview после полной структурной проверки допустимы без отдельного подтверждения; результат не помечается как проверенный хешем. FFIDO-UUE с идентификатором и SHA-256 собирается автоматически после проверки всех полей и хеша. Неизвестный split-диалект остаётся исходным текстом.

Индекс частей — производные данные. Поиск запускается ограниченными страницами по всей доступной области, не только по загруженному списку; возвращает cursor/progress и не помечает письма прочитанными. Полное сканирование не выполняется внутри GetMessage или каталога. Поздние части находятся повторным поиском; смена поколения инвалидирует cursor и результат.

### 3. Добавочный API с ограниченными порциями

В `contracts/ffido/v1/ffido.proto` добавляются attachment metadata, limits/capabilities и RPC для поиска, явной сборки, загрузки файла, commit/status отправки и получения байтов. Существующие номера полей и CreateMessage сохраняются. Новые поля optional/repeated; старый клиент читает обычные UUE-письма, новый при UNIMPLEMENTED отключает действия вложений с понятным сообщением, обычное чтение работает.

Используются unary chunk RPC по 64 КиБ: upload с operation-id, offset и проверкой повторной порции; download с attachment-id, offset и ограничением длины. Это работает через существующие gRPC и gRPC-Web без зависимости от streaming. Сервер ограничивает размер до выделения памяти; конфликт повторной порции отклоняется. Commit принимает неизменяемые метаданные, текст, адреса и хеш файла; идентичность операции учитывает исходный запрос до Н → H. Клиент узнаёт ограничения до выбора/загрузки. Отдельный статус доступен владельцу исходящей операции даже при праве только на публикацию; это не даёт чтения входящих писем области.

По умолчанию max decoded file 1 МиБ, target part body 32 КиБ, max parts 128, chunk 64 КиБ. Серверная конфигурация валидирует взаимную совместимость этих лимитов с жёсткими пределами JAM и RPC, а также лимиты активных upload/кеша на пользователя и сервер. Ограничены суммарный UUE-текст, число кандидатов за страницу и время обработки. Target включает текст и завершающее FTN-оформление; текст с файлом, не помещающийся в первую часть, отклоняется до commit с объяснением. Загрузка текста не дублируется в каждой части. Увеличение file limit не обходит max parts или квоты.

### 4. Устойчивая публикация через существующий writer

До первого append полностью проверяются права, адреса, файл, CP866-представимость текста, число/размер частей. На диске устойчиво сохраняются закрытый staging и immutable manifest с идентичностью пользователя, области/поколения, получателем, SHA-256, исходным запросом и заранее назначенными MsgID/operation-id частей. Состояния: uploading, prepared, publishing, partial, completed, failed. Каждая часть публикуется существующим восстановимым путём JAM writer, не обходя HPT coordination lock. Многочастная отправка не держит общую блокировку на время сетевой загрузки.

После сбоя журнал восстанавливает подтверждённые append и продолжает с первой незавершённой части. Повтор commit не создаёт новый пакет. Перед каждой записью повторно проверяются ACL и идентичность базы; отзыв прав или смена поколения останавливает остаток. Уже экспортированные части не удаляются автоматически и не выдаются за отменённые. Успех — все части сохранены локально, а не доставлены. Для Netmail каждая часть проходит действующий outbox/user-copy путь с тем же адресатом и без обхода маршрутизации HPT.

### 5. Авторизация и кеш

Никаких публичных URL или session secret в query. Каждый запрос метаданных/частей/байтов повторно проверяет сессию и разрешённость всех source references; пользователь не передаёт файловый путь. Сборка личного ящика не ищет недостающие части в общей транспортной или чужой JAM. Удалённая/изменённая часть, смена поколения или отзыв ACL сбрасывают готовность; старый decoded cache не является основанием доступа.

Серверный кеш находится в памяти процесса, ограничен размером/TTL и привязан к источникам; незавершённые upload имеют отдельную квоту и срок. Клиентский кеш разделяется по endpoint/user/profile и очищается по действующим правилам выхода; поздние ответы старой сессии игнорируются. Уже сохранённый пользователем файл вне приложения отозвать невозможно — это обычный экспорт данных.

### 6. Reader/composer и системные файлы

Reader заменяет распознанные span на карточки в их позиции, сохраняя переключатель исходного UUE и обычный текст. В неполной карточке есть счётчик частей и «Найти части»; старый нумерованный multipart собирается автоматически с предупреждением, ручной выбор состава остаётся доступен. Распознавание span происходит до FTN quote highlighting: строка UUE может начинаться с `>`. Цитируемые UUE-блоки с добавленными quote-префиксами не активируются как новое вложение. Существующее требование видимой полной редактируемой цитаты сохраняется; скрытого повторного прикрепления нет. При пересылке исходный видимый текст сохраняется по действующим правилам, автоматической новой бинарной передачи нет.

Composer показывает выбранный файл, размер и оценку частей отдельно от текста; итоговое число подтверждает сервер. Кнопки имеют tooltip/semantic label, hover/focus/disabled, доступны касанием. Ошибка не стирает текст/выбор; частичная публикация показывает результат и повтор той же операции.

Для выбора — официальный Flutter `file_selector`, версия совместимая с текущим SDK без обновления toolchain. [Документация](https://pub.dev/packages/file_selector) подтверждает выбор на всех платформах, но save-location только на desktop. Поэтому сохранение: desktop — системный save dialog, macOS user-selected.read-write entitlement в Debug/Release; Android — узкий platform channel ACTION_CREATE_DOCUMENT, iOS — UIDocumentPicker export временного файла; Web — браузерная загрузка bytes через отдельный web-adapter. Не вызывать неподдерживаемый getSaveLocation на мобильных платформах. Одна новая зависимость оправдана отсутствием существующего picker; нативные bridge не расширяются до общего файлового менеджера. Отмена не является ошибкой или успехом. Не требуются broad storage permissions.

Имя очищается от путей, управляющих символов и зарезервированных имён; mode из begin игнорируется. Файл не открывается и не распаковывается автоматически. Preview определяется по сигнатуре и реальному декодированию PNG/JPEG/GIF/WebP; до декодирования проверяются заголовки и размеры: по умолчанию до 16 мегапикселей и 8192 по стороне. Первый кадр GIF/WebP статический, без автоматической анимации. Decode error/превышение заменяются карточкой сохранения. Размер виджета ограничен, оригинальные bytes не перекодируются.

## Risks / Trade-offs

- Исторические split-диалекты неоднородны → явная матрица fixtures, автоматическая группировка по согласованным признакам, ручной состав и просмотр исходника; обещания «любой UUE» нет.
- Хеш отсутствует у старых отправок → пользователь разрешил автоматическую сборку с риском смешивания; постоянно показываем предупреждение и различаем проверку структуры и целостности. Имя не становится доказательством принадлежности частей.
- Обрыв в середине публикации → durable manifest и честный partial; многочастная FTN-отправка не атомарна.
- Неизвестные kludge могут удаляться внешним софтом → классический поток и нумерованные темы сохраняют возможность внешней/ручной сборки; HPT round-trip входит в приёмку.
- Вложение до 1 МиБ может декодироваться в огромное изображение → проверка размеров до image codec, ограничение памяти и статический первый кадр.
- Новые платформенные файловые действия → отдельные тесты отмены/ошибок и smoke на доступных платформах; недоступные проверки явно указываются.

## Migration Plan

1. Добавочные protobuf-поля/RPC и генерация клиента/сервера; старые сообщения остаются читаемыми без миграции JAM.
2. Следующая свободная SQLite-миграция после текущей schema 8 добавляет журнал UUE-операций; производный индекс восстанавливается в памяти; номер проверяется при apply, чужие миграции не заменяются. Кеш/staging не попадают в Git.
3. Сначала сервер, затем клиент; сервер сообщает capability и лимиты. Новый клиент на старом сервере сохраняет текстовые сценарии.
4. Все проверки — на временных JAM, HPT-конфигах и персональных ящиках двух поинтов. Рабочие конфиги/базы не меняются.
5. Откат отключает новые действия и сохраняет уже опубликованные UUE как обычные письма. Перед возвратом старого backend остановить незавершённые пакеты; downgrade SQLite не выполнять автоматически, использовать резервную копию либо совместимый backend.
