# Design

## Context

Мотивация — proposal.md. Текущая реализация уже имеет вход по паролю HPT, профиль по каноническому адресу, EchoAccess, безопасный JamCatalog, один durable JamWriter и персональные SQLite-отметки по user/conference/generation/message. Приватные HPT-области пока требуют owner_addresses. Flutter обновляет данные при resume, защищает сессии epoch и не кеширует приватные каталоги для offline fallback.

Исследованы AppConfig, main, helper HPT, EchoAccess, MessageService, metadata_store/operation/read_key, клиентские репозитории и контракт. Один append журнала сейчас относится только к одной базе: устойчивой связи персональной копии и транспортной очереди ещё нет. История хранит конференцию, а не последнее открытое письмо. Результаты восьми маршрутизационных экспериментов и выявленные wire-константы — research/hpt-routing.md.

Основная user-identity устарела относительно реализованных активных изменений hpt-password-login/hpt-echo-access/add-owner-private-areas. Наш delta уточняет только разграничение; синхронизация выполняется после владельческого delta с сохранением его сценариев. Остальные активные изменения автоматически не переписываются и не архивируются.

## Goals / Non-Goals

**Goals:** одна центральная инфраструктура HPT босса, отдельное физическое хранение почты поинтов, устойчивый транспортный переход, два устройства одной идентичности и отсутствие доступа между поинтами.

**Non-Goals:** собственный HPT на устройствах, Squish, вложения/запросы файлов и управление роботами, автоправка живого toss, синхронизация черновиков и scroll offset, push, end-to-end шифрование от администратора, безусловное exactly-once во внешней FTN при аварии самого HPT/mailer. Нельзя подменять прочитанность глобальным JAM Read или JLR.

## Decisions

### 1. Явное назначение и физические базы

Добавить отключённый по умолчанию раздел `point_mail`: ingress_areas (эффективные HPT-теги), отдельный egress_area и points [{address, jam_base}]. jam_base относителен существующему корню JAM. Helper передаёт реальные Link/OurAKA, собственные Address, эффективные параметры netmail/маршрутов и PackNetMailOnScan для проверок. Адрес ящика — конкретный Link с point > 0, чей босс — собственный нодовый AKA сервера и совпадающий OurAKA; адрес не добавляется в Address. Не назначать ящик произвольному удалённому адресу или всем линкам автоматически.

У каждого адреса собственная JAM, содержащая входящие и исходящие копии; она **не регистрируется NetmailArea HPT**, чтобы pack не удалял/переписывал пользовательскую историю. Каталог получает отдельную доверенную роль point mailbox, хотя API kind остаётся NETMAIL. Стабильный непрозрачный ID связан с полным каноническим адресом, не физическим путём. Только соответствующий профиль получает API-доступ; owner_addresses не предоставляет доступ к чужому mailbox endpoint. Администратор по-прежнему имеет файловый доступ и прежний доступ к сырым HPT-областям — криптографической тайны от него нет.

Проверять отсутствие дублей адресов, конфликтов AKA/назначений, path/symlink/hardlink алиасов с эхами, чужими ящиками и транспортом. Новые пустые базы создаются отдельной командой provisioning, не при входе/RPC; существующая база без проверенной принадлежности не присваивается. Неизвестный/удалённый binding закрывает доступ прежним сессиям без удаления файлов или отметок.

Альтернативы: общее представление NetmailArea требует постоянной фильтрации каждого письма/счётчика и несёт риск транзитных утечек; отдельные HPT на сервере для каждого поинта технически возможны, но увеличивают число конфигов и процессов. Выбираем физические FFIDO-ящики и один управляемый мост к HPT.

### 2. Входящие и общий операторский цикл

HPT toss записывает netmail в разрешённые ingress JAM; чужой -a не используется. Цикл под одной exclusive coordination lease:

1. Восстановить незавершённые transfer/claim и проверить конфиг; при неразрешённом pending или недоказанной изоляции quarantine не запускать pack.
2. Выполнить HPT toss без встроенного/раннего netmail pack.
3. Разобрать эффективные адреса всех новых ingress-записей и выполнить адресный dedup. Для управляемого адресата durable claim блокирует исходную запись настоящим JAM Locked, затем пишет входящую копию в его ящик; источник не удаляется и не помечается «доставлено в сеть».
4. Обработать локальную доставку между двумя управляемыми поинтами и подготовить разрешённые исходящие в egress.
5. Только после устойчивого завершения предыдущих стадий выполнять HPT pack/нужный scan. Исходные claimed-письма остаются Locked; ящики в конфиг pack не входят.

Route nopack на точные управляемые адреса — дополнительная защита, не замена claim: эксперимент с приоритетными JAM-флагами показал обход маршрутизации. Общий wildcard для всех поинтов недопустим — обычные mailer-поинты продолжают получать пакеты.

Для shared ingress HPT dupeCheck del по MSGID может потерять письмо второму адресату. Поэтому включение требует dupeCheck off на выбранных ingress и address-aware dedup распределителя **до pack для всех их записей**, включая неуправляемых получателей. Валидные письма боссу/обычным поинтам/транзиту остаются в прежнем маршруте; подтверждённый дубль блокируется, но не исчезает. Нельзя отключить dupeCheck и оставить обычный неконтролируемый pack.

Две идентичности хранения: source-key (база/generation/номер/контрольный хеш) для повторного сканирования и delivery-key (полные origin+destination+MsgID с проверкой полезной нагрузки) для повторного toss. Один MSGID разным получателям — разные доставки. Отсутствующая/противоречивая адресация, нет MsgID или одинаковый delivery-key с другим текстом — quarantine с сохранением источника, не догадка по имени и не тихое удаление. Транспортные Via/статусы не меняют identity полезной нагрузки. Quarantine требует операторского разбора; после доказанной устойчивой блокировки этих записей допустим pack остальных. При неопределённом claim весь pack запрещён.

Расширить существующий wrapper операторским режимом полного цикла с аргументами subprocess без shell-интерполяции. Bare pack/scan с netmail для включённой интеграции запрещается. Вложенный wrapper не должен заново брать тот же lock: CLI распределителя получает проверенную унаследованную lease. При убийстве цикла следующий запуск восстанавливает pending прежде HPT. RPC и UI не запускают внешние команды. Прямой обход оператором wrapper находится вне гарантий и явно документируется.

### 3. Исходящие и надёжность переходов

RPC пишет одну исходящую копию в собственную JAM и транзакционно связывает commit операции с SQLite outbox-event. Подтверждение — копия и событие устойчивы; пользователь продолжит читать её после pack. Sender всегда из профиля; для явно назначенного Link-поинта разрешается его полный адрес, несмотря на несовпадение с нодовым AKA транспортной области. Этот узкий режим не ослабляет правила авторства в обычных HPT-областях владельца.

В цикле outbox-event создаёт ровно одну запись egress с тем же MsgID, сначала Locked. После устойчивого связывания с source operation и проверки payload запись делается доступной HPT. Использовать существующий PrepareAppend/JamWriter, расширив журнал переходов, а не копируя append. Индексы переходов SQLite и fsync заголовка позволяют определить состояния claim/append/bind/unlock после аварии. При неразрешимой неоднозначности блокировать экспорт и сохранять обе стороны; не повторять append наугад. Locks брать в фиксированном порядке.

Egress — отдельная JAM NetmailArea с маршрутом HPT и KeepTrsMail on; отсутствие KillSent в формируемом письме. Событие для получателя другого управляемого поинта вместо egress создаёт его входящую копию с тем же MsgID/REPLY. Отправителю остаётся одна исходящая, адресату — одна входящая; локальный repeat не создаёт outbound-пакет. Read/Local/direction не используются как доказательство принадлежности.

Повтор исходного RPC сохраняет прежние operation ID, payload hash и MsgID. Разные устройства используют независимые операции; повтор именно одной операции дедуплицируется. При аварии HPT между записью PKT и Sent нельзя обещать exactly-once внешней доставки: цикл фиксирует export uncertainty, не создаёт новую очередь/новый MsgID, требует сверки оператором. Подтверждение UI остаётся «сохранено локально».

### 4. Wire-корректность и исторические данные

Первый этап apply — сверить всю JamMessageAttribute с официальным JAM/установленным SMAPI: TypeLocal=0x00800000, TypeEcho=0x01000000, TypeNet=0x02000000, Locked=0x40000000. Проверить и остальные биты, а не только переименовать четыре. Независимый oracle читает запись SMAPI и проверяет сырые константы до HPT; существующие тесты, закрепляющие ошибочные значения, корректируются с объяснением. HPT pack сам нормализует часть полей, поэтому одного успешного экспорта недостаточно.

Не переинтерпретировать и не переписывать все старые биты автоматически. До live-включения — read-only аудит старых FFIDO-операций с provenance, backup и отдельная явно запрошенная адресная миграция при необходимости. Неопределённые старые pending/ошибочно типизированные записи не допускаются в новую очередь без разбора. Новые исходящие: корректные Local+Private+TypeNet, OADDRESS/DADDRESS/MSGID/REPLY/PID/CHRS CP866 2, Н → H; без AREA/SEEN-BY/PATH/эхового Origin. Входящий текст не нормализовать как новое исходящее.

### 5. API, ответы и два устройства

Расширить protobuf добавочными полями, сохраняя номера: Conference отмечает personal mailbox и возвращает последнее открытое письмо/монотонную revision; Message содержит direction из durable provenance (incoming/outgoing, legacy unspecified). Существующий kind NETMAIL сохраняется. Реальные пути, чужие адресные привязки и staging metadata клиенту не передаются. Все прямые RPC, якоря пагинации, totals/поиск/цепочки/история/закладки проверяют binding до чтения; никакой общей NetmailArea поинту не открывать.

Две действующие сессии одного адреса используют один серверный профиль и SQLite-состояние. GetMessage атомарно обновляет read/history/последнюю позицию; revision назначает сервер, а не часы устройства. Прочитанность объединяется, старый кеш не снимает отметки. Исходящая копия сразу прочитана отправителем. Resume, ручное обновление и возврат в почту читают актуальные данные; push и фоновые гарантии на спящем телефоне не вводятся.

Для продолжения со старого письма ListMessages получает добавочный anchor_message_id, ответ — фактический offset страницы в текущем фильтре/порядке. Проверять принадлежность якоря; удалённый anchor даёт контролируемый NOT_FOUND и возврат к списку без отметки другого письма. UI предлагает продолжить с последнего открытого, не восстанавливает scroll offset и не открывает письмо автоматически с лишним read-событием.

Входящий ответ по умолчанию направляется origin оригинала; ответ на собственное outgoing — его destination. Полный адрес обязателен; явное изменение адресата следует существующему контракту, но не меняет sender. Reply-родитель только в доступном ящике, межпользовательские локальные номера не переносятся; FTN REPLY связывает копии. Цитаты/навигация/uncertain retry сохраняются, публичная пересылка из ящика скрыта. Поздний ответ старой сессии и отказ очищают представление; приватный offline fallback не допускается.

Новые поля по умолчанию сохраняют прежний режим на старом сервере. При включении ящиков требуется согласованное обновление владельческих и поинтовых клиентов; старый клиент не должен считаться проверенным режимом почты. Обычная эховая работа не меняется.

## Risks / Trade-offs

- Изменение dupeCheck shared ingress влияет на транзит → включать только с полным address-aware dedup и общей lease; тестировать обычного поинта, босса, чужой транзит и дубли.
- Два файловых хранилища + SQLite не атомарны → durable переходы, проверка идентичности и crash-тесты каждого cut point, остановка pack при неопределённости.
- Ошибка атрибутов или приоритет обходит nopack → исправить wire-таблицу, Locked claim и порядок цикла, самостоятельный pack не поддерживать.
- Подмена имени/MSGID/адреса раскрывает почту → доверенное назначение, полный 4D, provenance и quarantine вместо эвристик.
- Новые поступления видны после операторского цикла, второму устройству после refresh/resume → показать время актуальности; не обещать мгновенный push или внешнюю доставку.
- Бэкапы/администратор видят сырую почту → граница между пользователями API, а не шифрование от владельца машины.

## Migration Plan

1. Воспроизвести research и исправить wire-константы в изолированных тестах; проверить эхи и владельческие режимы без массового изменения баз.
2. Реализовать выключенные по умолчанию binding/provisioning, ACL и durable bridge; затем контракт и UI.
3. Прогнать два клиента одного поинта и второго поинта, реальные HPT toss/pack, crash/retry/quarantine на временных базах.
4. Оператор отдельно готовит backup, ingress/egress, Route/KeepTrsMail/dupeCheck/PackNetMailOnScan и заменяет расписание на проверенный цикл; выполнять preflight до включения. Ни Address, ни live-toss автоматически не редактируются.
5. При откате сначала остановить цикл и отключить доступ/новые отправки, разобрать pending. Не снимать Locked и не удалять источники автоматически; возврат к традиционной доставке поинтам — отдельное операторское действие после сверки. Ящики и SQLite сохраняются.
