# Design

## Context

Мотивация и согласованный объём — в `proposal.md`; поведенческие критерии — в шести delta-спецификациях этого change.

Подтверждено исходниками и документацией:

- `apps/frontend/lib/api/channel_web.dart` уже использует `GrpcWebClientChannel.xhr`; `SessionStore` в `api/session_store.dart` не записывает Web-токены и пароли в защищённое хранилище. Однако текущие preferences подключения и SessionManager ориентированы на одно активное подключение; многопрофильный Web-state требует явного расширения, а не переиспользования единственного endpoint-ключа.
- `apps/backend/src/service/auth_service.cpp` проверяет HPT-пароль, сохраняет профиль по каноническому адресу и выдаёт сессии на 30 дней. `Configure` синхронизирует fingerprints эффективных credentials со SQLite. Новая привязка должна опираться на этот механизм, не создавать отдельную копию HPT ACL.
- Редактор и operation ID уже есть в `apps/frontend/lib/pages/message_screen.dart`. Сохранение долговременного черновика и восстановление неопределённой отправки — новые требования, не подтверждённые возможностями текущего редактора.
- `tools/gateway/run.py` создаёт TLS Envoy listener только на loopback, проверяет точный Origin и TLS upstream. Публичное развёртывание требует явной настройки внешнего listener/прокси и применения сертификатов после renewal; готовая production-конфигурация Let’s Encrypt в репозитории не установлена.
- `api-transport` сейчас разрешает отсутствие сессии только для входа. Поэтому требуется MODIFIED delta: безопасное pre-auth объявление возможностей и проверенный Telegram-вход должны стать явными исключениями. В `user-identity` также уточняются HPT-only формулировка входа и исключения из независимости сессий при отзыве привязки.

## Goals / Non-Goals

**Goals:** сохранить серверный FTN-профиль источником прав и имени; дать нескольким независимым backend проверять общего бота без передачи его секрета; обеспечить воспроизводимое поведение при смене профиля, потере связи и повторе отправки.

**Non-Goals:** новая регистрация поинтов, уведомления, центральное хранение привязок/почты, REST, новый state manager, редизайн, полноценный офлайн-клиент и UI управления Telegram в нативных клиентах. Публикация и изменение рабочего узла не выполняются автоматически в apply.

## Decisions

### 1. Независимые backend и один статический клиент

```text
Telegram bot --> Flutter Web [GitHub Pages]
                       |
                       +--> public backend catalog [same Pages]
                       |
                       +--> HTTPS Envoy --> TLS gRPC FFIDO --> JAM / SQLite
```

Бот — точка запуска; в первой версии ему не нужен постоянный обработчик уведомлений. Для каждого узла сохраняются его gateway, TLS, HPT и SQLite. Вместо центрального auth-broker backend сам проверяет Ed25519-подпись Telegram initData публичным ключом Telegram для настроенного bot_id. Секрет бота хранится только у оператора бота и не входит в клиент, каталог или конфиг сторонних узлов.

С первой проверки используется будущий основной бот в обычном Telegram (`test_environment: false`); после тестирования сохраняются тот же бот и bot_id. Изоляция обеспечивается отдельным тестовым backend/JAM/SQLite без рабочего FTN-export. Подключение рабочего узла требует отдельного поручения. Привязки хранятся на backend: на рабочем backend пользователь заново подтверждает привязку HPT-паролем; сохранение бота не переносит тестовые привязки, сессии или данные.

Проверка следует официальному алгоритму third-party validation: исходная строка, канонический data-check-string, подпись, production/test key и разрешённый bot_id. Строго отклоняются дубли ключей, повреждённые поля, чрезмерный размер, отсутствующий пользователь, неверная подпись и неприемлемое время. Предлагаемый предел свежести — 5 минут, допустимое опережение часов — 30 секунд; это технические значения по умолчанию для конфигурации и тестов. initData остаётся краткоживущим bearer-доказательством: TLS, исключение из логов и ограничение попыток обязательны. При устаревании пользователь переоткрывает Mini App; локальный user.id не заменяет доказательство.

### 2. Данные привязки и происхождение сессий

В SQLite каждого backend добавляется таблица связи с существующим profile_id: bot_id, telegram_user_id (64-битное целое), credential fingerprint и ревизия привязки. Ограничение UNIQUE(profile_id) сохраняет одного Telegram-владельца; индекс по bot_id/user_id позволяет вернуть только его профили. Один пользователь имеет любое допустимое текущими лимитами число профилей. Telegram username и имя не идентифицируют поинта и не меняют сохранённое FTN-имя.

Сессия получает происхождение `hpt` либо `telegram` и ссылку на ревизию привязки. Существующие строки мигрируют как HPT. Замена/удаление привязки и отзыв всех её сессий выполняются одной SQLite-транзакцией; валидация и создание сессии проверяют актуальность ревизии под той же координацией. Это закрывает гонку входа с отвязкой. Одновременная замена не оставляет две активные связи.

Привязка не имеет TTL; выдаваемые через неё сессии используют существующую политику срока. Изменение эффективного HPT credential fingerprint или удаление доступа после успешного применения конфигурации удаляет привязку и отзывает сессии. Это не обещает мгновенного отслеживания файлов HPT: действуют существующие правила загрузки/перезапуска. Откат к прежнему паролю не воскрешает удалённую связь.

### 3. Аддитивный gRPC-контракт

Предлагаемые имена новых RPC: `GetServerCapabilities`, `ListTelegramProfiles`, `LoginWithTelegram`, `BindTelegram`, `GetTelegramBinding`, `UnbindTelegram`. Конкретные новые номера protobuf-полей выбираются при apply после проверки актуального контракта; существующие номера и RPC не меняются.

- `GetServerCapabilities` доступен до входа и сообщает поддержку Telegram без профилей и секретов. Старый сервер отвечает UNIMPLEMENTED: UI оставляет HPT-вход. Недоступность сети не означает отсутствие возможности.
- `ListTelegramProfiles` принимает initData, возвращает только связанные с проверенным пользователем профили, не выдаёт бизнес-доступ или сессии всем профилям автоматически.
- `LoginWithTelegram` принимает initData и выбранный профиль и проверяет принадлежность, актуальность привязки и HPT; возвращает обычный LoginResponse.
- `BindTelegram` вызывается в действующей сессии поинта, повторно проверяет текущий HPT-пароль, initData и явное разрешение замены. Предварительный HPT-вход может создать серверный профиль уже настроенного поинта по существующему Login, но не выдаёт новый FTN-адрес. По умолчанию конфликт связи не заменяется молча; UI запрашивает подтверждение.
- `GetTelegramBinding`/`UnbindTelegram` относятся только к профилю действующей сессии. Для отвязки достаточно сессии и подтверждения; состояние другого профиля по переданному ID не раскрывается. В браузере доступны просмотр/отвязка, создание и замена предлагаются только в Telegram.

Список и вход без сессии защищаются доказательством Telegram; bind и управление — FFIDO-сессией, bind дополнительно паролем. Одинаковая семантика gRPC/gRPC-Web, ограничения размера/deadline/rate limiting и типизированные ошибки проверяются контрактными тестами. Нативные клиенты сохраняют прежний Login и transport; новые Telegram RPC не делают старые поля обязательными.

### 4. Каталог — граница доверия

Предлагаемое место исходника — `apps/frontend/web/backends.json`, опубликованный путь — `/ffido/backends.json`. Формат содержит schema version и записи `id`, `name`, `ftn_address`, `endpoint`. Клиент валидирует уникальность ID, HTTPS URL без credentials/query/fragment, структуру и размер каталога до замены сохранённой копии. Новые узлы проходят PR-review; произвольные endpoint в обеих Web-формах недоступны, нативный ввод не меняется.

Сохраняются только каталог, ранее добавленные узлы и выбор профиля. Новый клиент не рассылает initData по каталогу: пользователь выбирает узел вручную. На знакомом клиенте опрашиваются только добавленные разрешённые узлы, с независимыми ошибками. `startapp` разрешается только как ID каталога; секреты/адрес назначения RPC не извлекаются из произвольного URL запуска. До передачи пароля показаны домен и название.

Некорректный или недоступный каталог не заменяет последнюю корректную копию. При первом запуске без копии доступен только повтор загрузки. При успешном удалении узла его сессии в памяти перестают использоваться и операции блокируются; серверная привязка не удаляется. Черновики сохраняются для копирования/удаления.

Endpoint фиксируется вместе с локальным профилем. Смена endpoint при прежнем ID переводит узел в состояние «ожидает подтверждения переноса»: запросы приостановлены, старый токен не отправляется новому адресу, передача Telegram-доказательства начинается только после согласия. Не следуем перенаправлению на иной origin с секретами. Новый вход подтверждает профиль; старые данные не смешиваются с другим FTN-профилем. Автоматический перенос привязки/SQLite на другой сервер не предполагается.

### 5. Профили, сеансы и локальное состояние

Сохраняется текущая архитектура widgets/repositories/typed transport. Web-координатор ведёт независимый контекст `(catalog_id, accepted_endpoint, canonical_ftn_address)`; session epoch защищает от запоздавших ответов. Токены всех контекстов только в памяти страницы, пароль не сохраняется; initData также не записывается в постоянное хранилище. При смене Telegram-пользователя прежнее состояние не становится доступным новому аккаунту.

Обычный запуск выбирает последний профиль устройства, если он снова подтверждён. При отсутствии выбора открывается единственный доступный либо список. Ссылка ограничивает выбор заданным узлом; отсутствие привязки ведёт к HPT-входу. Узлы без capability работают с HPT-входом и без управления привязками.

«Завершить сеанс» отзывает текущую сессию и чистит данные только выбранного профиля. Локальный признак ручного выхода сохраняется без токена и блокирует автоматический вход до действия «Войти через Telegram», включая перезагрузку страницы. «Отвязать Telegram» отзывает все сессии этой связи на сервере, но не обычные HPT-сессии. «Забыть узел» локально очищает все его профили и удаляет узел из истории; привязки остаются. При недоступном сервере локальный выход выполняется, однако UI не утверждает, что удалённый отзыв состоялся. Очистка с черновиками требует предупреждения; остальные профили не меняются.

### 6. Черновик и неопределённая отправка

Локальное Web-хранилище содержит адресацию, тему, текст и контекст ответа в пространстве профиля; это содержимое почты, а не секрет аутентификации. До входа оно не отображается. Файлы, blob URL и байты вложений не сохраняются; после перезапуска нужен новый выбор. Закрытие страницы не равно явному выходу и не очищает черновик.

До изменяющего RPC сохраняются operation_id, точный замороженный запрос, expected_preview_digest при его наличии и состояние «результат неизвестен». Нельзя сохранять только редактируемый текст и после перезапуска отправлять изменённое письмо под прежним ID. После входа в тот же endpoint/профиль допускается только явная проверка/повтор по существующему механизму идемпотентности; новый публичный status RPC не вводится без необходимости. Полученный ранее результат подтверждает сохранение и закрывает черновик.

Окно идемпотентности, staging вложений и идентичность точного запроса проверяются по действующему контракту при реализации восстановления. Если сервер больше не может безопасно повторить запрос, показывается неопределённость с сохранением текста, а не автоматическая отправка с новым ID. Повторное прикрепление другого файла не считается продолжением прежней операции. Смена профиля не переносит такую операцию на другого отправителя.

Чтение новых данных и отправка требуют сети. Открытое письмо остаётся на экране, редактор сохраняет ввод, нет фоновой очереди и автопубликаций. Нативный офлайн-функционал не урезается.

### 7. Telegram adapter, файлы и размещение

Web adapter через штатный Dart JS interop подключает Telegram SDK и передаёт тему, viewport/safe area, BackButton, ready и closing confirmation в существующие Flutter-экраны. Браузерный adapter работает без Telegram. Flutter остаётся владельцем редактора/действий; нативные adapters не зависят от Telegram. Не добавляется сторонний state manager или обязательный непроверенный Telegram-пакет.

Сборка использует base href `/ffido/` и маршруты, открываемые на статическом Pages без серверных rewrites (по умолчанию hash routing). Каталог загружается отдельно от app bundle с сетевым обновлением и явным fallback к проверенной копии; service worker не должен навсегда закреплять устаревший список разрешённых узлов. Workflow готовится для review, но публикация выполняется только по отдельному запросу.

Pages содержит только статические файлы. Публичный HTTPS шлюз на стороне узла (предпочтительно 443) принимает origin `https://hashev.github.io` без пути, не origin Telegram. Существующий loopback default сохраняется; внешний listener/внешний TLS proxy выбирается явной deployment-настройкой. Let’s Encrypt подходит при полной цепочке, правильном SAN, renewal и применении обновлённого сертификата TLS-службой. Upstream остаётся TLS gRPC с CA/SAN validation. Способ безопасного reload фиксируется для реально выбранной службы; наличие файлов сертификата само по себе не доказывает reload.

UUE остаётся в существующем авторизованном API. Для скачивания используются существующие Web file adapters и при необходимости blob/save/open flow, без помещения bearer token в URL или публичного размещения личного файла. Выбор, скачивание и открытие проверяются отдельно на каждой обязательной платформе.

## Risks / Trade-offs

- [Компрометация Pages/каталога] → ручное review каталога, показ домена, подтверждение переноса. Origin `hashev.github.io` общий для проектов владельца: CORS не различает `/ffido/` и другой путь; доверие ко всем публикациям этого origin остаётся ограничением выбранного размещения.
- [Кража initData или XSS] → короткая свежесть, серверная проверка, TLS, отсутствие секретов в хранилище/логах, минимальная Web-интеграция. Постоянный локальный черновик не считается зашифрованным хранилищем.
- [Офлайн-копия каталога не знает об отзыве узла] → блокировка применяется после успешного обновления; fallback не объявляется актуальным каталогом. Это согласованный компромисс доступности.
- [Отзыв на другом устройстве не очищает его локальные байты дистанционно] → следующий защищённый запрос отклоняется, UI скрывает персональные данные и требует вход; серверный отзыв не обещает удаление файлов устройства.
- [WebView и UUE ведут себя по-разному] → обязательная реальная матрица Telegram Android/iOS/Desktop и Chrome/Safari/Firefox, без замены её одним Chrome smoke. Telegram Web пока без гарантии.
- [Истёкшая идемпотентность или staging] → контролируемое состояние неизвестного результата без автоматического нового письма.
- [Недоступны устройства/сертификаты/бот] → фиксировать непроверенные пункты; не считать выпуск готовым по одним unit tests.

## Migration Plan

1. Аддитивно расширить контракт и SQLite; существующие профили, credentials и сессии сохраняются, старые сессии помечаются HPT. Без настроенного bot_id Telegram capability выключена.
2. Реализовать backend и общий Web-клиент, каталог и подготовить Pages/gateway инструкции и workflow. Не включать реальные endpoints, секреты или базы тестов в Git автоматически.
3. Выполнить автоматические тесты и изолированную приёмку на будущем основном боте и отдельном тестовом backend/JAM/SQLite без рабочего HPT-export. Внешняя настройка, публикация и запуск требуют отдельного поручения.
4. Пройти полную согласованную матрицу. Только затем по отдельному разрешению добавить рабочий узел и выполнять реальные публикации.
5. Откат функции: отключить Telegram capability, отозвать Telegram-сессии, вернуть предыдущую статическую сборку; HPT-вход сохраняется. Не откатывать SQLite разрушением таблиц; запуск старого бинарного файла возможен только при подтверждённой совместимости версии схемы либо после штатного восстановления согласованного backup.

## Open Questions

Продуктовых блокеров нет. Имя будущего основного бота и его bot_id, публичный DNS тестового gateway, конкретная служба завершения TLS и доступные устройства задаются при подготовке тестовой среды; до их появления соответствующая приёмка остаётся непроверенной. Точные версии браузеров и Telegram записываются в отчёт прогона, не выводятся из исторических результатов.

Источники интеграционных контрактов: [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-for-third-party-use), [Flutter Web](https://docs.flutter.dev/platform-integration/web), [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Let’s Encrypt](https://letsencrypt.org/docs/integration-guide/).

### Уточнение UUE-экспорта после внешней приёмки 18.11.2026

В Telegram запрещён молчаливый fallback на anchor/blob, который хост может проигнорировать.
После получения авторизованных байтов клиент запрашивает отдельное нажатие для Web Share Files;
в системный диалог передаются только безопасное имя и байты файла, без URL, пароля и сессии.
Успешный Promise означает передачу системному меню, а не доказанную запись на диск.
AbortError означает отмену без success; отсутствие canShare/files, отказ и ошибки означают
конкретное сообщение с предложением обычного браузера. Нативный Telegram downloadFile
требует HTTPS-URL и не используется для приватного blob без отдельного download-контракта.
Обычный браузер сохраняет blob-download, но результат обозначен как запрос скачивания.
Нативный файловый writer возвращает подтверждённое сохранение либо отмену.
Все потребители (включая просмотр изображений) используют различимые результаты экспорта.
Эта локальная правка не меняет опубликованную сборку и требует внешней повторной приёмки.
