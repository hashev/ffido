# Proposal

## Why

Существующим поинтам нужен доступ к FFIDO из Telegram без установки отдельного клиента и повторного ввода HPT-пароля при каждом запуске. Одна Flutter Web-сборка должна работать в Mini App и обычном браузере, сохраняя независимость узлов и существующие права HPT.

## What Changes

- Один общий бот запускает Web-клиент; с первой проверки используется будущий основной бот, который сохраняется после тестирования. Проверка проводится на отдельном изолированном backend без выхода в FidoNet. Уведомления и выдача новых поинтов не входят в первую версию.
- Telegram-привязки существующих FTN-профилей хранятся на каждом backend. Один Telegram-аккаунт поддерживает несколько профилей, включая несколько на одном узле; один FTN-профиль связан только с одним Telegram-аккаунтом.
- Первичная привязка и её замена требуют HPT-пароля внутри Mini App; постоянная привязка выдаёт обычные ограниченные по сроку сессии после серверной проверки Telegram. Замена, отвязка и изменение HPT-доступа отзывают соответствующие сессии.
- Каталог проверенных узлов и клиент размещаются на GitHub Pages по адресу `https://hashev.github.io/ffido/`. Произвольные endpoint в этой Web-сборке недоступны. Новое устройство выбирает узел вручную, знакомое проверяет только ранее добавленные узлы.
- Добавляются выбор профиля, раздельные завершение сеанса, отвязка и локальное «Забыть узел», обработка удаления узла и подтверждение переноса endpoint.
- Существующие Flutter-экраны адаптируются к теме, размерам, отступам и кнопке «Назад» Telegram. Сохраняются чтение, поиск, цепочки, прочитанность, закладки, Netmail, публикации, ответы и UUE-вложения.
- Web-сессии остаются только в памяти. Локальные черновики и данные незавершённых отправок восстанавливаются после входа в тот же профиль; полноценный офлайн-режим, очередь и автоматическая повторная отправка отсутствуют.
- Узлы без Telegram-входа доступны по HPT-паролю. Добавление/замена привязки доступны в Telegram; просмотр и отвязка — также в браузере. UI управления в нативных клиентах отложен.

## Capabilities

### New Capabilities

- `telegram-identity`: проверка Telegram, многопрофильные привязки, обмен на сессии и отзыв.
- `backend-directory`: доверенный статический каталог, выбор узлов, перенос endpoint и локальная история.
- `web-workspace`: профили Web-клиента, локальные черновики и восстановление неопределённого результата отправки.

### Modified Capabilities

- `user-identity`: дополнительный доверенный вход, источник сессии и границы отзыва без изменения FTN-идентичности.
- `api-transport`: аддитивные RPC Telegram и объявление возможностей до входа с fallback к HPT.
- `platform-runtime`: одна Web-сборка для Telegram и браузера, интеграция Telegram, размещение и матрица приёмки.

## Impact

Затронуты `apps/frontend/` (API, SessionManager, профили, редактор, Web adapters), `apps/backend/` (auth, SQLite, gRPC service), `contracts/ffido/v1/ffido.proto` и штатно сгенерированные модели, `tools/gateway/`, тесты, документация и будущий workflow GitHub Pages. Backend/JAM/SQLite остаются на сервере узла; HTTPS шлюза использует доверенный сертификат, совместимый с Let’s Encrypt. Новые RPC не восстанавливают REST и не меняют wire-контракт старых операций. Публикация, настройка бота и развёртывание требуют отдельного запроса; этот change сейчас содержит только планирование.
