# Design

## Context

См. мотивацию в proposal.md. `MessageService::CreateMessage` получает имя автора из профиля, определяет получателя ответа по родительскому сообщению и формирует окончательный текст перед `PrepareAppend`. Клиент передаёт Unicode; пересылка включает исходное письмо в тело. JAM выполняет преобразование из UTF-8 в настроенную кодировку. Журнал отправки сравнивает хеш исходного запроса до формирования сообщения.

## Goals / Non-Goals

**Goals:** единая точка замены для всех путей публикации, сохранение доверенной идентичности автора, кодировки и семантики повторов.

**Non-Goals:** изменение исторических сообщений, профилей и черновиков; настройки отключения; изменение API, структуры JAM или механизма кодирования.

## Decisions

1. Выполнить замену четырёх окончательных полей `JamMessage` в `MessageService::CreateMessage` после выбора получателя и формирования тела, перед `PrepareAppend`. Это охватывает профиль, ответ и пересылку. Замена только в клиенте позволила бы обход через API; замена в общем JAM-кодеке затронула бы импортированные данные и другие способы записи.
2. Использовать точное преобразование UTF-8 U+041D → U+0048, без изменения регистра и похожих символов. Уже существующая проверка валидности UTF-8 сохраняется; нижний слой по-прежнему проверяет представимость остальных символов в CP866.
3. Сохранять хеш исходного запроса и порядок проверки журнала. Нормализуется только новое формируемое сообщение; завершённая операция возвращается как раньше. Хеширование нормализованных значений изменило бы контракт конфликтов ключей.
4. Подтвердить результат независимым чтением байтов JAM через `tests/support/jam_wire_record.hpp`, дополнительно проверить экспорт в пакет HPT на временной базе. Сравнение только декодированного текста не обнаружит симметричную ошибку кодека.

## Risks / Trade-offs

- Автоматическая замена меняет написание имени в новом письме → применять только точную согласованную пару символов и документировать отличие от сохранённого профиля.
- Ответ переопределяет получателя после чтения родителя → тестировать имя из родителя, включая родителя в UTF-8 при исходящей CP866.
- Повторная отправка может дублировать письмо при изменении журнала → не менять журнал и проверить повтор и конфликт исходного запроса.

## Migration Plan

После проверок собрать и перезапустить сервер обычным способом. Клиенты продолжают использовать прежний API. Миграция данных не требуется; откат бинарника прекращает замену в будущих письмах. Уже сохранённые письма автоматически не переписываются. Проверки записи выполняются только на временных базах, без отправки тестовых писем в реальные эхи.
