# Design

## Context

Мотивация и границы — в `proposal.md`. Редактор `_ComposerState` находится в `apps/frontend/lib/pages/message_screen.dart`: обычная отправка вызывает `MessageRepository.sendMessage`, UUE использует отдельный замороженный `UueDraft`. `forward_destination.dart` уже реализует серверный поиск, пагинацию, отбрасывание устаревших результатов и фильтрацию `AreaKind.echo && canPost`; его подход следует переиспользовать без попутного рефакторинга.

`CreateMessageRequest` в `contracts/ffido/v1/ffido.proto` адресует одну конференцию. `MessageService::CreateMessage` проверяет доступ, получает серверный профиль, сохраняет идемпотентную операцию с хешем payload, формирует MSGID и пишет одну JAM-базу. `storage::Operation` содержит одну область и её поколение; атомарной транзакции нескольких JAM-баз сейчас нет. Ответ разрешает локального родителя только в текущей области. Общий транспорт — gRPC/gRPC-Web, несмотря на историческое упоминание HTTP в контексте OpenSpec.

Изучены исходники GoldED+ в ревизии `1a251c6375081453a410bb8d647be120b8902de3`:

- [gecarb.cpp, DoCrosspost](https://github.com/golded-plus/golded-plus/blob/1a251c6375081453a410bb8d647be120b8902de3/golded3/gecarb.cpp): распознавание XC/XP, исключение исходной эхи и дублей, режим CC_NAMES с Originally in и отдельной Crossposted in на каждую дополнительную эху.
- [gclang.cpp](https://github.com/golded-plus/golded-plus/blob/1a251c6375081453a410bb8d647be120b8902de3/golded3/gclang.cpp): точные строки `* Originally in %s` и `* Crossposted in %s`.
- [gccfgg.cpp](https://github.com/golded-plus/golded-plus/blob/1a251c6375081453a410bb8d647be120b8902de3/golded3/gccfgg.cpp): CC_NAMES используется по умолчанию.

Переносится видимый формат CC_NAMES. Текстовые команды, маски и скрытые назначения GoldED не переносятся.

## Goals / Non-Goals

**Goals:** сервер управляет составом группы и формированием блока; все копии имеют воспроизводимый текст, самостоятельный MSGID и подтверждённое состояние. Повтор восстанавливает ту же операцию без дублей после потери ответа или перезапуска.

**Non-Goals:** распределённая транзакция с откатом уже опубликованных писем, автоматическая отправка клиентом очереди отдельных CreateMessage, персистентные клиентские черновики, изменение UUE и маршрутизации HPT.

## Decisions

### 1. Выбор дополнительных адресатов

Добавить экран множественного выбора рядом с `forward_destination.dart`, использующий `ConferenceRepository.searchConferences`. Независимый от выдачи набор выбранных ID хранится до подтверждения. Основная эха видна отдельно, недоступна для снятия и не входит в дополнительные адресаты. Поиск использует существующие debounce/version/epoch/cancellation-подходы; пагинация продолжается даже если после фильтрации страница пуста. Неподдерживаемые области исключаются явно.

Редактор получает меню «⋯», сводку выбранных эх и отдельный неизменяемый предпросмотр блока. Отмена выбора не меняет черновик. При смене основной эхи пересылки удалить её из дополнительных; прежняя основная не становится дополнительной автоматически. При нуле дополнительных эх использовать прежний CreateMessage. Возможность доступна для новых сообщений, ответов и пересылок с итоговой основной областью типа echo. Здесь «редактирование» означает составление до отправки; изменение опубликованных писем не добавляется.

Альтернатива — правка XC-строк в теле — хуже согласуется с галочками и смешивает текст с управляющими данными. Взаимоисключение UUE и кросспостинга проверять до изменения данных, с пояснением пользователю.

### 2. Отдельный групповой RPC

Добавить `CreateCrosspost` с запросом: основная конференция, operation_id, дополнительные ID, тема, текст, получатель и необязательный родитель основной эхи. Ответ содержит общий признак complete и подтверждённые MessageReference/MSGID по эхам; незавершённые назначения имеют безопасную типизированную диагностику. Валидация до первой записи возвращает обычный gRPC-статус; сбой после публикации части возвращает частичный ответ, если транспорт ещё доступен. Потеря ответа трактуется как неопределённый результат.

Проверять от 1 до 20 дополнительных уникальных ID, без исходной эхи; превышение — INVALID_ARGUMENT. Это ограничение первой версии для размера блока и времени одного RPC. ID разрешать через каталог, для блока брать канонические имена эх, не пути и не описания. Дополнительные эхи сортировать по каноническому имени без учёта регистра, затем по ID; порядок входного массива не влияет на идентичность операции.

Новый RPC сохраняет семантику CreateMessage и явно возвращает UNIMPLEMENTED на старом сервере. Добавление только repeated-поля в CreateMessage опасно: старый сервер может проигнорировать его и сохранить одну копию как полный успех. Клиент не выполняет fallback; обновление сервера предшествует клиенту. Транспортные интерфейсы native/Web и fake-реализации тестов обновляются вместе; Dart генерируется штатным скриптом.

### 3. Формирование текста и ответа на сервере

Сервер добавляет блок после проверки канонического состава и до пользовательского текста, оставляя пустую строку. Функция форматирования в Dart служит только предпросмотру, сервер остаётся источником истины. Для RU.ONE + RU.TWO + RU.THREE:

```text
* Originally in RU.ONE
* Crossposted in RU.THREE
* Crossposted in RU.TWO

Текст письма
```

Не разбирать XC/XP или произвольные строки атрибуции внутри текста; цитаты не удалять. При повторе блок не накапливается, поскольку замороженный payload содержит только пользовательский текст. Обычная нормализация, кодировка каждой JAM-базы и tearline/Origin выполняются существующим writer-путём. Предварительно проверить представимость и лимиты всех итоговых копий без мутации JAM, используя существующий validate/prepare-подход.

Получателя ответа разрешить один раз из основной эхи по существующим правилам. Основная копия сохраняет REPLY и локальные связи; дополнительные получают тот же разрешённый адресат, без REPLY и локальных связей. Каждой копии назначается отдельный заранее сохранённый MSGID. Общий MSGID был бы опасен для дедупликации FTN и смешивал бы идентичность разных публикаций.

### 4. Устойчивая группа поверх существующих одиночных операций

Добавить запись группы и её назначений в SQLite через существующий механизм миграций. Запись фиксирует пользователя, внешний operation_id, хеш нормализованного запроса, снимок профиля/получателя, основную эху, канонический набор с поколениями баз, стабильные внутренние ключи/MSGID. Прогресс каждой копии определяется по существующей устойчивой дочерней операции JAM, без отдельного дублирующего флага группы. Пространство ключей групп и внутренних операций отделить от пользовательских ключей обычной отправки; проверить ограничение существующих ключей 128 байт. Не менять глобальную уникальность внешнего operation_id существующих одиночных операций.

Порядок: проверить всю группу; устойчиво зафиксировать план; сохранять основную копию, затем остальные по каноническому порядку, используя прежние intent/fsync/recovery и блокировку одной JAM-базы; при формировании результата сверять прогресс с дочерними операциями. Хеш включает исходную эху, нормализованный набор, исходные текстовые поля и родителя, но не operation_id. Снимок производных полей предотвращает изменение уже начатой группы при смене профиля. Группа сериализуется по пользователю/ключу; общая глобальная блокировка всех баз не вводится.

Если процесс завершится после фиксации дочерней операции, восстановление сверяет её состояние и возвращает прежнюю копию; отдельной записи прогресса группы нет, поэтому окна рассогласования двух флагов не возникает. Нельзя заново создавать сообщение только по отсутствию флага группы. Перед возобновлением и выдачей результатов повторно проверить права; перед новой копией проверить право постинга и поколение базы. Изменение поколения, quarantine или неопределённый хвост блокируют продолжение без пересоздания сохранённых копий. При отзыве прав не раскрывать идентификаторы запрещённых сообщений; клиент сохраняет неопределённость и не считает группу завершённой.

Альтернатива — несколько независимых клиентских отправок — не фиксирует весь набор и плохо переносит перезапуск/потерю ответа. Общий откат JAM-баз не выбирается: HPT уже мог увидеть сохранённую копию.

### 5. Состояния редактора

До отправки изменение полей/набора создаёт новый operation_id. При отправке фиксируются payload и набор; повтор использует их целиком. Полный успех закрывает редактор с подтверждением локального сохранения всей группы; частичный показывает подтверждённое число копий и повтор, неопределённый не придумывает счётчик. Отказ валидации до любых записей разрешает исправить черновик; после частичного/неопределённого результата изменения блокируются. При закрытии предупреждать, что копии могли сохраниться, и не обещать автоматическое возобновление после перезапуска клиента. Смена сессии следует существующей защите epoch и не переносит данные другому пользователю.

## Risks / Trade-offs

- Частичные публикации видны до завершения всей группы → явный прогресс, устойчивый план и повтор без дублей; атомарность всех JAM не обещается.
- Отзыв прав между проверками → перепроверка перед новой записью и результатом повтора; сохранённые копии не удаляются.
- Смена JAM-поколения или quarantine → остановка продолжения и понятная диагностика; никакой записи в заменённую базу по старому плану.
- Длинный блок/разная кодировка → предварительная проверка всех копий и лимит 20 дополнительных эх.
- Формат блока реализуется в двух языках → одинаковые эталонные тесты; серверный текст авторитетен.
- Перезапуск клиента теряет текущий черновик → сохранённые сервером данные остаются, устойчивые клиентские черновики не входят в объём.

## Migration Plan

1. Добавить обратно совместимые таблицы SQLite и новый RPC, сохранив старые CreateMessage и UUE; миграция не трогает существующие JAM-письма.
2. Проверить восстановление групп и обычных операций, затем обновить сервер.
3. Обновить клиент и generated Dart. Старый клиент продолжает одиночную отправку; новый на старом сервере показывает UNIMPLEMENTED без ложного успеха.
4. При откате клиента группы остаются в метаданных. Перед откатом сервера завершить или сверить незавершённые группы; не удалять записи/копии и не откатывать таблицы разрушительно. Старый бинарник не должен обслуживать незавершённые новые группы как обычные операции.
