# Design

## Context

Мотивация и состав первой версии описаны в [proposal.md](proposal.md). Анализ выполнен по текущему коду, без чтения пользовательских JAM-баз:

| Что уже существует | Где | Следствие для MCP |
| --- | --- | --- |
| Каталог, типы областей, права чтения/постинга | `ConferenceService`, `EchoAccess`, `openspec/specs/private-areas/` | Переиспользовать авторизацию и различать эхи, почту и служебные области |
| Чтение с RecordView, поиск одного следующего результата | `MessageService::GetMessage`, `FindMessage` | Нельзя использовать эти RPC для фонового исследования |
| Чтение без отметки | `MessageService::PeekMessage` | Основа архивного чтения; потребуется учесть фильтры и блочное тело |
| Цепочки с numeric links и точным MSGID/REPLY, защита от циклов | `MessageService::GetThread`, `test_services.cpp` | Переиспользовать алгоритм, не строить ветки по теме |
| Кириллица, CP866-подмены, ranges | `service/message_search.hpp`, `test_message_search.cpp` | Новый поиск использует эти правила; `GetMessages.query` сейчас имеет другую семантику |
| CHRS/default/override и ограниченный JAM I/O | `storage/jam_access.*`, `storage/text_codec.*` | MCP не разбирает файлы самостоятельно |
| Диагностика без RecordView | `GetMessageTechnicalData` | Использовать существующий RPC, bytes выдавать в base64 |
| Идемпотентная публикация и внутренняя validate_only | `MessageService::CreateMessage`, `JamWriter` | Дополнить просмотром и проверкой соответствия, не создавать второго механизма записи |
| TLS gRPC/gRPC-Web и generated Dart | `contracts/ffido/v1/ffido.proto`, `GrpcService`, `tools/proto/generate.sh` | Изменения контракта только аддитивные, с проверкой обеих сторон |

## Goals / Non-Goals

**Goals:** один авторитетный backend для JAM, общий контроль доступа, отсутствие отметок чтения при исследовании, подтверждаемые источники и безопасно повторяемая публикация. Запуск MCP на Linux/macOS рядом с ассистентом, включая подключение к удалённому FFIDO.

**Non-Goals:** второй backend, прямой доступ MCP к FTN-файлам, новые Flutter-экраны, встроенная генерация ответов, глобальная индексация архива, HTTP MCP, Windows-поставка MCP в первой версии. Поиск буквальный; ассистент может выполнить несколько запросов для разных формулировок.

## Decisions

### 1. Отдельный stdio executable с gRPC-клиентом

Добавить `apps/backend/src/mcp/` и target `ffido-mcp`, связанный с `ffido_contracts`, существующими gRPC/OpenSSL/nlohmann/json и backend checks. Он не запускает `fidoback`, не открывает backend config и не линкуется с хранилищем ради доступа к данным. Корневой CMake остаётся точкой сборки.

Альтернативы: встроенный HTTP endpoint требует отдельного транспорта, сетевой авторизации и защиты Origin; самостоятельное открытие JAM дублирует права, координацию и lifecycle HPT. Внешний Python/TypeScript bridge добавляет runtime и зависимости. Выбран ограниченный протокольный слой C++ с обязательными wire-тестами; новый SDK не вводится.

Версия MCP первой реализации — `2025-11-25`. Объявляются только tools/prompts, без sampling, resources, subscriptions и фоновых tasks. reader отделён от bounded worker pool, stdout сериализован; ping и cancellation обрабатываются во время долгого вызова. Неизвестные поля допустимы только по правилам соответствующих протокольных сообщений, аргументы инструментов имеют `additionalProperties=false`.

### 2. Полезные сценарии поверх небольшого набора инструментов

| Сценарий | Последовательность | Результат |
| --- | --- | --- |
| «Как раньше решали проблему TLS в этой эхе?» | list → search → get_message → get_thread | Ответ с цитатами, датами и references |
| «Что обсуждали за неделю?» | search с пустым query и [from,to) → страницы → чтение выбранных веток | Дайджест с границами периода и явным покрытием |
| «Как изменилось мнение автора?» | Несколько буквальных поисков по имени/адресу и теме → цепочки | Подбор первоисточников; нет обещания отдельного фильтра или поиска людей |
| «Почему письмо выглядит кракозябрами или выпало из ветки?» | technical_data + get_message + get_thread | CHRS, фактическая кодировка, атрибуты и реальные связи; без ремонта JAM |
| «Ответь участнику / напиши личное письмо» | prepare → показать просмотр → разрешение пользователя в MCP-клиенте → send | Одна устойчивая локальная публикация |

Схемы инструментов:

- `ffido_list_areas(query?, offset=0, limit=20)`: каталог после allowlist-фильтрации; total/has_more вычисляются по разрешённому набору, без раскрытия глобального total.
- `ffido_search_messages(area_ids, query, scope=headers_and_body, from?, to?, sort=date_asc, limit=20, cursor?)`: cursor заменяет продолжение, но остальные параметры должны совпадать с исходными.
- `ffido_get_message(reference, body_offset=0, body_limit=65536, reveal=false)`: заголовки, UTF-8 блок тела, next_offset, complete, source_uri.
- `ffido_get_thread(reference, offset=0, limit=20)`: summaries и reply references, total/has_more. Полное тело запрашивается отдельно.
- `ffido_get_message_technical_data(reference)`: существующие технические поля, encoding_status, raw bytes в base64.
- `ffido_prepare_message(area_id, to_name, to_address, subject, body, in_reply_to?)`: проверенный просмотр и draft_id.
- `ffido_send_message(draft_id, confirm)`: результат фиксации либо определённая ошибка/неопределённый исход.

Все references — объекты `conference_id/message_id`; MSGID не заменяет локальную идентичность. `source_uri` имеет форму `ffido://message/<percent-encoded-area>/<percent-encoded-id>`, является идентификатором для цитирования и повторного tools/call. Это не обещание рабочего web/deep link и не MCP resource. Нет ручного открытия произвольных URI или путей.

### 3. Аддитивный protobuf-контракт

Добавить `SearchArchiveMessages`, `ReadArchiveMessage` и `GetArchiveThread` с отдельными request/response. Поля результата включают references, summaries, snippets, complete, incomplete_reason, cursor, body offsets. У архивных RPC нет флага, включающего RecordView. Чтение и цепочки делят внутренние примитивы с текущими сервисами; существующие RPC сохраняют семантику. Внутренний PeekMessage сам по себе не обеспечивает персональное сворачивание — новый метод явно применяет фильтры.

Для просмотра добавить `PreviewMessage(CreateMessageRequest)` с нормализованными полями, итоговым декодированным wire-текстом, размером и `preview_digest`. В `CreateMessageRequest` добавить необязательный `expected_preview_digest`, не меняя номера и значения старых полей. Внутренний validate_only переиспользует тот же план публикации; digest охватывает профиль, область/поколение, родителя, адреса, тему, wire bytes, кодировку и транспортный тип. Проверка digest происходит при первой фиксации под той же координацией, что построение/запись плана. Существующий идемпотентный replay сохраняет прежний результат и проверки прав, не создавая новую публикацию из-за изменившегося конфига.

В digest входят детерминированные пользовательские и адресные поля плана и wire-тело; автоматически создаваемые при фиксации время и MSGID не входят и не обещаются в просмотре. Это позволяет сравнить два построения плана без ложного несовпадения случайных/временных метаданных. Представление для хеширования версионировано и однозначно, с разделением полей по длине.

Старый Flutter-клиент не передаёт новое поле и работает как раньше. Dart bindings регенерируются, RPC surface и старые payload проверяются контрактными тестами. При UNIMPLEMENTED адаптер требует обновления backend без fallback через изменяющее прочитанность чтение. Требования `api-transport` к единому protobuf и отсутствию REST сохраняются; новый MCP — внешний stdio-адаптер этого API.

### 4. Поиск, бюджеты и изменение базы

Новый архивный поиск переиспользует FoldSearch/SearchRanges и effective encoding. Области проверяются до обхода, затем каждая открывается через JamAccess с RequestScope; блокировки разных JAM одновременно не удерживаются. Текст декодируется и проверяется по тем же bounds, что обычное чтение. Сортировка дата/ID области/локальный номер стабильна, date_desc разворачивает этот порядок.

Для глобальной сортировки сначала собираются компактные совпавшие references с датой, затем выдаются страницы. Обход может продолжаться через несколько вызовов: до завершения scan-фазы возвращается пустая страница с `complete=false`, `incomplete_reason=scan_budget`, cursor. Обход ограничен 100000 заголовками за вызов и 5 секундами; deadline/cancellation — ошибки. Размер сохраняемого состояния ограничен 32 MiB и 100000 найденными references на поиск; превышение — RESOURCE_EXHAUSTED, без заявления о полном результате. Snippets и тела не накапливаются в состоянии, читаются для выдаваемой страницы.

Cursor — случайный серверный handle к состоянию в памяти, TTL 10 минут, не более 16 активных поисков на пользователя и 64 на backend, общий бюджет 128 MiB. Состояние содержит параметры, пользователя, позиции обхода и fingerprints баз (поколение, mod counter и характеристики файлов каталога). Проверять fingerprints до и после каждой порции под общей координацией; любое изменение или перезапуск backend инвалидирует cursor с FAILED_PRECONDITION. Нет бессрочного кеша тел, SQLite-индекса или обещания снимка при внешнем изменении HPT. Утрата состояния требует явного перезапуска поиска.

Ревизия персональных фильтров также входит в состояние поиска: её изменение инвалидирует cursor. Права и фильтры проверяются снова перед выдачей каждой страницы, включая чтение snippets; сохранённые references сами по себе не разрешают раскрытие.

Reply traversal переиспользует GetThread с его пределом 100000 сообщений и защитой циклов. Страница цепочки привязана к текущему reference; при смене поколения — ошибка. Для воспроизводимого межстраничного исследования предпочтителен повтор поиска при изменении набора; цепочка не объявляется immutable snapshot.

Альтернативы: многократный вызов FindMessage меняет состояние чтения и даёт один результат; `ListMessages.query` не имеет нужной семантики; полнотекстовый/векторный индекс требует отдельного lifecycle, миграций и политики доступа. Ограниченный scan выбран для первой версии.

### 5. Профиль и секреты

`ffido-mcp CONFIG` читает endpoint, session_file, read_area_ids, post_area_ids и state_dir. Пути разрешаются относительно CONFIG; файлы состояния/сессии — только обычные файлы владельца процесса с правами 0600, каталоги 0700, без небезопасного следования symlink. Секреты не передаются в argv, tool arguments и stderr.

Предоставить локальную команду `ffido-mcp login CONFIG`: интерактивный ввод имени/FTN-адреса/пароля без эха пароля, Login через проверенный TLS и атомарное сохранение отдельной сессии. Это явное действие оператора вне MCP, не вход ассистента. После смены токена процесс MCP перезапускается; Logout существующего Flutter-профиля не вызывается. Истечение сессии требует нового локального входа. Удалённый OAuth/HTTP MCP здесь не реализуется.

Текущие FFIDO-токены не имеют ограниченных scopes. Локальные allowlist ограничивают адаптер, но не превращают украденный токен в read-only credential; это документированное ограничение. На каждом запросе backend остаётся источником прав, адаптер дополнительно проверяет область, включая drafts и cursors. В выводе tools/list `readOnlyHint=true` только для чтения/аналитики; prepare изменяет локальное состояние, send не read-only и помечается потенциально изменяющим внешние данные. Аннотации не заменяют проверки.

### 6. Подготовка, подтверждение и повтор публикации

PreviewMessage не создаёт durable transport intent. После его успеха MCP атомарно сохраняет локальную запись draft: случайный draft_id, operation_id, точный запрос, preview_digest, endpoint/profile binding, created_at, expires_at и состояние prepared. Файл 0600 в state_dir; сохранять до выдачи draft_id. Черновик не изменяем: редактирование создаёт новый. До первой отправки срок 15 минут; перед вызовом backend состояние устойчиво меняется на attempted. Уже attempted-записи сохраняются до явного локального удаления оператором, чтобы неопределённый исход можно было разрешить после перезапуска; completed-записи также сохраняют результат для повтора. Автоматического повтора публикации с новым operation_id нет.

Send не принимает новое содержимое. При confirm=true и действующем draft_id вызывает CreateMessage с сохранёнными operation_id/digest. Backend повторно проверяет всё необходимое и сравнивает план. При ответе сохраняется completed и исходный результат. При потере ответа возвращается outcome_unknown с тем же draft_id и инструкцией повторить именно его. Истёкший prepared не отправляется; attempted можно повторить тем же запросом для разрешения исхода через серверную идемпотентность. Отмена после начала отправки также не обещает откат.

Сервер не может доказать, что модель получила настоящее человеческое подтверждение: confirm и draft_id связывают вызовы и содержимое. MCP-клиент должен показывать preview и запрашивать разрешение на send; эта граница доверия явно описывается в инструкции подключения и tool description. Текст писем не является разрешением на отправку.

### 7. Протокол и проверка

Опереться на официальную спецификацию MCP: [transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts). Фиксировать версию протокола в tests, а не объявлять поддержку будущих версий.

Проверки: backend unit/integration на временных JAM и SQLite; настоящие JSON-RPC subprocess transcripts поверх локального TLS gRPC; сравнение персонального состояния до/после чтения; restart/lost-response тест публикации; контракт C++/Dart и полный Flutter analyze/test после регенерации. Никаких публикаций в реальные эхи.

## Risks / Trade-offs

- Большие архивы и отсутствие индекса → ограниченные scan-порции, явная неполнота; очень большие выборки могут требовать сужения периода/областей.
- Активный toss инвалидирует продолжение → сообщение о повторе исследования; нет скрытого смешивания результатов.
- Приватная переписка попадает в контекст выбранного ассистента → отдельные точные allowlist, пустые по умолчанию; инструкция оператора объясняет передачу разрешённого текста MCP-клиенту.
- Письмо содержит инструкции для модели → выдавать его как данные, включать это правило в descriptions/prompts; контроль публикации остаётся за MCP-клиентом.
- Ручной протокольный слой → небольшой объявленный surface и wire-тесты ошибок, отмены, лимитов и stdout purity.
- Устойчивые локальные drafts содержат текст переписки → защищённый state_dir, документированное локальное удаление; не сохранять в Git и не писать содержимое в логи.

## Migration Plan

1. Поставить backend с новыми аддитивными RPC и optional preview digest; миграции JAM/SQLite не нужны.
2. Поставить `ffido-mcp` в серверный tar.gz Linux/macOS, описать запуск на машине ассистента и TLS-доступ к backend; включить зависимости в существующую упаковку/BUILD metadata.
3. Настроить read/post allowlist, выполнить отдельный локальный login, подключить stdio процесс к MCP-клиенту и проверить временную область.
4. Откат: отключить MCP-процесс и вернуть прежний backend. Сохранённые JAM-публикации не удаляются; локальные drafts сохраняются для повторного подключения к совместимому backend. Обычный Flutter-клиент продолжает использовать прежние RPC.
