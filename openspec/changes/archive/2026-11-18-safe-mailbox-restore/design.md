# Design

## Context

Основание — docs/deployment/amster2-miniapp/rehearsal-20261118.md. В point_mailbox.cpp Identity и JamCatalog::Build сравнивают device/inode компонентов JAM с mailbox_bindings; защита корректно запрещает распакованную копию. ProvisionMailbox не предназначен для перепривязки существующих баз. CreateSQLiteStore::Init автоматически мигрирует до текущей схемы, поэтому его нельзя использовать для подготовки rollback schema11.

Поколения также присутствуют в read_status, reading_positions, operations, mail_provenance, mail_transfers и bulk_read_operations. bookmarks/history привязаны к conference_id; их сохранность всё равно требует проверки через пользовательские сценарии. Исправление только mailbox_bindings недостаточно. Текущий удалённый manage.py и диагностический SQL в build/ не являются штатным recovery API.

## Goals / Non-Goals

**Goals:** явная offline-команда с dry-run/apply, атомарным восстановлением проверенной идентичности, совместимость schema11/12, полный manifest backup и воспроизводимая изолированная приёмка.

**Non-Goals:** автоматическое доверие новым inode при startup, ремонт повреждённых сообщений, восстановление неопределённого FTN-экспорта, production deploy, изменение RPC/FE, обновление активного maintenance cron на amster2.

## Decisions

### Доверенный снимок и отдельный проверенный план

Предлагаемый интерфейс ffido-admin: mailbox-restore check/apply с config, snapshot manifest и отдельно переданным expected digest; apply дополнительно получает digest проверенного плана. Точные флаги следуют существующему CLI. Manifest не содержит паролей/текстов писем: пути, хеши, schema, address/base и прежние физические поколения. Приватность сохраняется даже без текстов писем.

SHA-256 не доказывает авторство сам по себе: оператор получает доверенный digest из отдельно сохранённой записи завершённого snapshot. Manifest в восстанавливаемой директории не служит единственным корнем доверия. Новый снимок использует версионированный формат; старый архив не объявляется завершённым задним числом. Для репетиции старые данные и явно перечисленные статические дополнения сначала превращаются в отдельный полный sandbox snapshot под locks, без чтения live-зависимостей во время restore.

### Offline restore без автоматической миграции

Отдельный storage-путь открывает существующую SQLite без CREATE и без Init, допускает ровно schema11/12 и валидирует ожидаемую структуру. Восстановление schema11 не создаёт Telegram-таблиц. Изменение привязок не меняет публичный wire-контракт и не требует изменений native/Web клиента.

### Границы блокировок и атомарности

Переиспользовать BackendInstanceLock и coordination lock с существующим порядком захвата; дополнительно управляющая процедура исключает maintenance, HPT и mailer. Не создавать production lock во время dry-run чтения копии. Apply проверяет всё снова под locks, фиксирует FD/идентичности проверенных файлов с O_NOFOLLOW, отвергает hardlinks, traversal, alias ящиков и смену адреса. Перед транзакцией создаётся согласованная приватная SQLite backup; ошибка backup не допускает apply.

Одна BEGIN IMMEDIATE транзакция обновляет разрешённые физические поля и проверенное соответствие физического и логического поколения; не меняет JAM, HPT-пароли, токены, пользовательские идентификаторы или логические receipt. Проверки FK/integrity обязательны. Сбой до commit откатывает всё; fsync/receipt и повтор должны различать прежнее и уже применённое состояние без повторного преобразования. Неизвестный исход commit разрешается проверкой текущего состояния, не очисткой журналов.

### Generation и операции

Manifest перечисляет все активные JAM-базы снимка, а не только ящики. Для точного содержимого строится однозначное соответствие старого и нового физического поколения; только такое соответствие используется runtime. Исторические поколения не угадываются; затрагиваемые ссылки без доказуемого соответствия блокируют apply. У подтверждённых операций сохраняются operation_id, payload_hash, MsgID, номера сообщений, направления и логические receipt. Тест повтора исходного запроса обязателен: перенос физической ссылки не должен менять идемпотентность.

Первая версия отказывает при pending operations, незавершённых transfers/outbox или export state != clean. Их recovery не запускается автоматически. Это ограничение безопаснее перепривязки незавершённого журнала к иной базе; оно должно быть видно до начала применения и не обходиться изменением SQL-флагов.

### Backup в репозитории, не скрытый патч удалённого manage.py

Добавить инструменты manifest/snapshot в scripts/ с unittest, переиспользуя доступные HPT/config adapters вместо парсинга includes случайными regex. Состав включает msgbase, state, f/spool/dupebase/flags/fileboxes, config/includes, intab/outtab, corrections manifest, TLS/session key, deployment и updater state. Не рекурсировать backups внутрь backup; дополнительные пути разрешаются явно и проверяются на containment/подмену. Пустые обязательные runtime-директории описываются в manifest отдельно.

Supervisor остаётся владельцем остановки/возобновления писателей. Snapshot helper не запускает fido/jamnntpd в finally. Ротация должна сохранять referenced/special snapshots и не считать частичный архив завершённым. На amster2 проверяется только sandbox-интеграция новых инструментов; изменение рабочего ops/manage.py и cron откладывается до отдельного разрешения.

## Risks / Trade-offs

- Большой объём полного хеширования → ограниченный streaming I/O, контроль места и времени; отсутствие пропущенных файлов важнее скорости.
- Generation в receipt и payload → адресные тесты всех потребителей, отказ при неоднозначности, запрет изменения логической идемпотентности.
- Ручное объявление писателей остановленными недостаточно → реальные locks, проверяемое supervisor-состояние и повторная сверка manifest.
- Старые backups неполны → отдельный provenance дополнений и новый sandbox snapshot; исходные архивы неизменны.
- Schema11 rollback → restore-утилита новой версии применяется offline и завершается до запуска rollback-образа v1.0.27 с restore-support.

## Migration Plan

1. Реализовать и проверить CLI/storage/backup на искусственных fixtures, включая отказы и crash/retry.
2. Собрать новые backend/tosser из зафиксированного manifest; проверить общий BUILD identity и HPT runtime.
3. На amster2 из сохранённых приватных копий подготовить полный sandbox snapshot. Рабочие mounts и сеть не подключать.
4. Восстановить schema11 штатной командой, запустить rollback-образ v1.0.27 с restore-support, проверить личные данные; отдельно выполнить 11→12 и restore schema12 новым образом. Все проверки через network=none.
5. Обновить отчёт и production_rollback_ready только при успешной приёмке; stopped containers и приватные snapshots сохранить для review. Production update/firewall/Pages не выполняются.

## Уточнение после исследования и решения пользователя 18.11.2026

Пользователь разрешил расширить change на UUE/crosspost receipt и FTN-ключи и подготовить отдельный rollback-образ на базе v1.0.27 с поддержкой восстановления.

Generation является частью неизменяемого payload_hash и source_key. Поэтому вместо переписывания frozen запросов, receipt и всех пользовательских строк сохраняется логическое поколение снимка. Offline restore атомарно обновляет физические mailbox_bindings и таблицу restored_generations: относительная база, проверенное физическое поколение назначения, исходное логическое поколение. Runtime обязан проверить физическую идентичность до использования логического поколения; несовпадение блокирует startup. JamAccess и recovery JamWriter используют одно и то же проверенное логическое поколение. Это сохраняет read_status, позиции, SQL receipt, UUE message IDs, crosspost payload hash и FTN source_key без преобразований. Обычный backend без restore-support для полного rollback больше не используется.

Дополнительные restore_receipts фиксируются в той же SQLite-транзакции и позволяют отличить подтверждённый повтор от изменённого состояния. Номер user_version остаётся 11/12; новые служебные таблицы не меняют gRPC/FE. Snapshot включает существующие служебные таблицы для повторного backup/restore. Для schema11 rollback собирается отдельная пара backend/tosser из точного v1.0.27 с минимальными изменениями каталога/JamAccess/JamWriter и загрузки таблицы соответствий, без Telegram-миграции.

Проверки должны подтвердить не только readiness, но сохранение UUE/crosspost repeats и FTN source_key, а также отказ runtime при подмене physical generation. Runtime не доверяет произвольной старой generation: соответствие создаётся только manifest-verified offline-командой под locks.
