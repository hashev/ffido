# api-transport Specification

## Purpose

Обеспечивает предсказуемую обработку ответов REST-сервера и сохранение диагностики ошибок для клиентских сценариев.

## Requirements

### Requirement: Успешные ответы
Клиент SHALL принимать типизированные protobuf-ответы версионированного gRPC API, сохранять Unicode-текст без искажений и успешно обрабатывать пустой ответ операции без результата.

#### Scenario: Нет тела ответа
- **WHEN** операция отметки прочитанного или удаления закладки возвращает успешный пустой protobuf-ответ
- **THEN** клиент завершает операцию без ошибки формата

#### Scenario: Русский текст без charset
- **WHEN** сервер возвращает русский текст через gRPC или gRPC-Web
- **THEN** клиент отображает его без искажений

### Requirement: Диагностика ошибок
Клиент SHALL сохранять gRPC-статус и имя RPC; различать отсутствие авторизации, запрет доступа, отсутствие ресурса, валидацию, недоступность, deadline, отмену и внутренний сбой. Ошибки полей SHALL передаваться типизированно; секреты и внутренние пути SHALL отсутствовать в публичной диагностике.

#### Scenario: Ошибка авторизации
- **WHEN** сервер возвращает UNAUTHENTICATED или PERMISSION_DENIED
- **THEN** клиент показывает соответствующую ошибку доступа и не скрывает её кешем

#### Scenario: Ошибки полей
- **WHEN** сервер отклоняет поля запроса с INVALID_ARGUMENT
- **THEN** клиент сохраняет сообщения для каждого отклонённого поля

#### Scenario: HTML вместо JSON ошибки
- **WHEN** gRPC-Web шлюз недоступен или возвращает HTML вместо протокольного ответа
- **THEN** клиент сообщает контролируемую транспортную ошибку без исключения разбора в интерфейсе

#### Scenario: Неизвестный серверный статус
- **WHEN** сервер или шлюз возвращает неизвестный клиенту статус
- **THEN** клиент сообщает контролируемую ошибку с доступным исходным кодом и именем RPC

#### Scenario: Некорректное успешное тело
- **WHEN** успешный протокольный ответ содержит повреждённые protobuf-данные
- **THEN** клиент сообщает контролируемую ошибку формата ответа

#### Scenario: Отмена и deadline
- **WHEN** вызов отменён или истёк deadline
- **THEN** клиент различает эти причины и сохраняет имя RPC

### Requirement: Единый контракт и полная замена REST
Система SHALL предоставлять один версионированный protobuf-контракт для C++ и Dart с одинаковой семантикой gRPC и gRPC-Web. REST и legacy API SHALL отсутствовать после миграции.

#### Scenario: Согласованные клиенты
- **WHEN** нативный и Web-клиент вызывают одну операцию с одинаковыми данными и пользователем
- **THEN** результаты и бизнес-ошибки совпадают

#### Scenario: Старый маршрут
- **WHEN** клиент обращается к прежнему REST или legacy endpoint
- **THEN** операция не выполняется через старый API

### Requirement: Ограничение вызовов
Система SHALL ограничивать размер запросов, ответов и страниц, время ожидания и число одновременно выполняемых операций. Читающие вызовы SHALL иметь ограниченные повторы только при временной недоступности; изменяющие вызовы SHALL повторяться только с обеспеченной идемпотентностью.

#### Scenario: Превышение лимита
- **WHEN** запрос превышает допустимый размер или число операций превышает серверный лимит
- **THEN** сервер возвращает RESOURCE_EXHAUSTED без изменения данных

#### Scenario: Некорректная пагинация
- **WHEN** offset отрицателен, limit вне диапазона 1–100 или сортировка неизвестна
- **THEN** сервер возвращает INVALID_ARGUMENT

### Requirement: Жизненный цикл сессии
Общий protobuf API SHALL предоставлять вход по имени, FTN-адресу и паролю, восстановление сохранённой сессии и выход с одинаковым поведением gRPC и gRPC-Web. Только вход SHALL допускать отсутствие сессии; бизнес-операции SHALL оставаться защищёнными. Вход SHALL возвращать подтверждённый профиль, секрет сессии и срок действия.

#### Scenario: Вход из интернета
- **WHEN** Android и нативный клиент ноутбука подключаются к публичному HTTPS-адресу FFIDO с доверенным сертификатом и верными данными
- **THEN** оба получают отдельные сессии одного профиля через существующий gRPC-транспорт

#### Scenario: Восстановление
- **WHEN** клиент передаёт сохранённую действующую сессию после перезапуска
- **THEN** сервер подтверждает профиль и срок действия без повторной передачи пароля HPT

#### Scenario: Неверный пароль
- **WHEN** пароль неверен или адрес отсутствует
- **THEN** сервер возвращает одинаковую публичную ошибку UNAUTHENTICATED без раскрытия конфигурации

#### Scenario: Ограничение попыток
- **WHEN** превышен установленный лимит попыток входа для адреса или источника
- **THEN** сервер возвращает RESOURCE_EXHAUSTED без создания сессии

#### Scenario: Выход без сети
- **WHEN** сервер недоступен при выходе
- **THEN** клиент удаляет локальную сессию и кеш, сообщает о недоступности серверного отзыва и не восстанавливает сессию автоматически

#### Scenario: Браузер
- **WHEN** Web-клиент входит через настроенный gRPC-Web шлюз
- **THEN** он получает тот же профиль и ошибки, а секрет сессии хранится только в памяти текущего запуска
