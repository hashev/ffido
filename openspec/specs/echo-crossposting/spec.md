# echo-crossposting Specification

## Purpose

Определяет выбор нескольких эх и отправку текстового письма с видимой атрибуцией кросспостинга, контролем доступа и безопасным продолжением частично завершённой публикации.

## Requirements

### Requirement: Выбор эх из редактора
Редактор текстового письма в эху MUST предоставлять меню «⋯» с пунктом «Кросспостинг». Список MUST поддерживать поиск и галочки для нескольких дополнительных эх. Исходная эха MUST оставаться обязательной, исключаться из дополнительных адресатов и явно отображаться. Выбор MUST применяться только после подтверждения.

#### Scenario: Выбор нескольких адресатов
- **WHEN** пользователь создаёт письмо, ответ или пересылку в эху и отмечает две дополнительные эхи
- **THEN** после подтверждения редактор показывает исходную эху и обе выбранные эхи
- **AND** повторное открытие списка сохраняет галочки; снятие всех галочек возвращает обычную отправку

#### Scenario: Отмена выбора
- **WHEN** пользователь изменяет галочки и закрывает список без подтверждения
- **THEN** редактор сохраняет прежний набор адресатов

#### Scenario: Смена назначения пересылки
- **WHEN** пользователь меняет основную эху пересылки
- **THEN** новая основная эха исключается из дополнительных адресатов, остальные выбранные эхи сохраняются

### Requirement: Поиск и доступность эх
Список SHALL показывать только эхи с правом публикации и поддерживаемым хранилищем. Поиск и загрузка следующих страниц MUST сохранять выбранные ID, исключать дубли и игнорировать устаревшие ответы. Смена сессии MUST закрывать выбор без переноса данных в новую сессию.

#### Scenario: Выбор вне поисковой выдачи
- **WHEN** пользователь выбирает эху, меняет запрос и выбирает другую на следующей странице
- **THEN** обе галочки сохраняются независимо от текущей выдачи

#### Scenario: Ошибка загрузки
- **WHEN** загрузка страницы завершается ошибкой
- **THEN** список показывает ошибку и повтор с текущим фильтром, сохраняя выбор

#### Scenario: Недоступные области
- **WHEN** в каталоге есть Netmail, локальные, служебные, неподдерживаемые области или эхи без права публикации
- **THEN** они не предлагаются для кросспостинга

### Requirement: Только текстовый кросспостинг
Кросспостинг SHALL поддерживаться только при отправке текста в эхи. Клиент MUST предотвращать одновременный выбор дополнительных эх и прикрепление UUE-файла с понятным пояснением без удаления введённых данных. Сервер MUST отклонять недопустимый тип области или вложение в групповой операции.

#### Scenario: Уже прикреплён файл
- **WHEN** пользователь открывает меню редактора с UUE-вложением
- **THEN** кросспостинг недоступен с пояснением о поддержке только текста

#### Scenario: Уже выбраны дополнительные эхи
- **WHEN** пользователь пытается прикрепить файл при выбранном кросспостинге
- **THEN** клиент предлагает сначала снять выбор эх и не изменяет текст или адресатов автоматически

### Requirement: Видимый блок по формату GoldED
Каждая копия MUST начинаться общим блоком: `* Originally in <исходная эха>`, затем по строке `* Crossposted in <эха>` для каждого дополнительного адресата. Блок MUST отделяться от пользовательского текста пустой строкой, использовать канонические имена эх без дублей и одинаковый порядок во всех копиях. При обычной отправке блок MUST не добавляться.

#### Scenario: Исходная эха и две копии
- **WHEN** письмо из RU.ONE отправляется также в RU.TWO и RU.THREE
- **THEN** все три копии содержат блок с Originally in RU.ONE и Crossposted in RU.THREE, затем Crossposted in RU.TWO в алфавитном порядке
- **AND** пользовательский текст следует после пустой строки, а серверный tearline и Origin остаются в конце письма

#### Scenario: Предпросмотр и повтор
- **WHEN** пользователь меняет выбор до отправки либо повторяет ту же отправку
- **THEN** редактор показывает актуальный неизменяемый предпросмотр блока отдельно от редактируемого текста, а сервер добавляет ровно один блок текущей операции
- **AND** существующие цитаты и строки XC/XP пользовательского текста остаются текстом и не создают адресатов

### Requirement: Проверка всей группы перед записью
Сервер MUST до первой записи проверить исходную и все дополнительные эхи, права, родителя ответа, размеры и представимость итоговых копий. Набор MUST содержать от 1 до 20 дополнительных уникальных эх без основной. Сервер MUST возвращать ошибку без публикации при невалидном исходном запросе; права MUST повторно проверяться перед каждой новой записью и выдачей результата повтора.

#### Scenario: Отозвано право или превышен лимит
- **WHEN** до начала отправки одна эха недоступна, повторяется в наборе, совпадает с основной либо дополнительных эх больше 20
- **THEN** ни одна копия не сохраняется, клиент получает ошибку доступа или валидации без раскрытия запрещённых данных

#### Scenario: Итоговый текст не помещается
- **WHEN** добавление блока превышает лимит JAM или текст нельзя сохранить в кодировке одной из эх
- **THEN** операция отклоняется до записи первой копии

### Requirement: Идентичность и связь ответа
Копии SHALL иметь отдельные стабильные FTN MSGID и одинаковые тему, отправителя, получателя и пользовательский текст. При ответе связь с родителем и локальные номера цепочки SHALL сохраняться только в основной эхе; дополнительные копии MUST не ссылаться локальными номерами на сообщения другой базы.

#### Scenario: Ответ в несколько эх
- **WHEN** пользователь отвечает на письмо в RU.ONE и выбирает RU.TWO
- **THEN** копия RU.ONE сохраняет связь ответа, RU.TWO публикуется без REPLY и локальных reply links; получатель обеих копий соответствует ответу

### Requirement: Устойчивое продолжение групповой отправки
Группа MUST иметь изолированный по пользователю operation_id и неизменяемый состав/содержимое. Повтор MUST возвращать прежние сохранённые копии и продолжать оставшиеся без дублей, включая после перезапуска сервера. Изменённый payload с прежним ключом MUST отклоняться. Полный успех MUST означать устойчивое локальное сохранение всех копий, без обещания доставки в FidoNet.

#### Scenario: Сбой после второй копии
- **WHEN** две из трёх копий сохранены, затем процесс завершается
- **THEN** повтор той же группы после восстановления сохраняет только третью копию с прежними идентификаторами первых двух

#### Scenario: Конкурентный повтор и изменённый набор
- **WHEN** одинаковая группа отправляется одновременно либо с прежним ключом передан другой набор/текст
- **THEN** одинаковые вызовы не создают дубли, а изменённый payload получает ALREADY_EXISTS

### Requirement: Частичный и неопределённый результат
Клиент MUST различать полное сохранение, частичное сохранение и неизвестный результат. Пока операция может быть частично сохранена, её текст, получатель и адресаты MUST оставаться замороженными; повтор MUST использовать тот же ключ и payload. Редактор MUST не закрываться автоматически до полного успеха, а закрытие с незавершённой отправкой MUST предупреждать о возможных сохранённых копиях.

#### Scenario: Потеря ответа или частичное сохранение
- **WHEN** ответ сервера потерян либо подтверждены только некоторые копии
- **THEN** редактор сохраняет замороженные данные и предлагает повтор, не сообщает об успехе всей группы и не начинает новую операцию автоматически

#### Scenario: Старый сервер
- **WHEN** сервер не поддерживает групповой RPC
- **THEN** клиент сообщает об отсутствии поддержки, сохраняет черновик и не заменяет групповую отправку одиночной или серией независимых отправок
