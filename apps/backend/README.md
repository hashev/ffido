# Backend FFIDO

C++23 backend использует только `ffido.v1.Ffido` gRPC API из
`contracts/ffido/v1/ffido.proto`. REST, static-file serving и JWT удалены.
Все 13 RPC требуют `authorization: Bearer <opaque-token>` по TLS; имя,
профиль и FTN-адрес назначаются локальным администратором. Все активные
пользователи имеют одинаковый доступ к разрешённым JAM-конференциям и
отдельные закладки, историю и прочитанность.

## Сборка и проверки

Из корня монорепозитория:

```sh
cmake -S . -B build/backend -DCMAKE_BUILD_TYPE=Debug
cmake --build build/backend --parallel 4
ctest --test-dir build/backend --output-on-failure --parallel 4
tools/proto/generate.sh --check
```

Зависимости централизованы в `cmake/deps.cmake`. Требуются gRPC 1.84.0,
Protobuf/protoc 36.2.0, OpenSSL, iconv, CMake, C++23 compiler и Python 3.
Версии Dart plugin и клиентских runtimes зафиксированы в `tools/proto/`
и `apps/frontend/pubspec.yaml`. Backend core, contracts и executable
собираются раздельно. Общая документация проверок: [docs/testing.md](../../docs/testing.md).

## Настройка и запуск

Скопируйте `config.example.json` в локальный, исключённый из Git `config.json`.
Пути трактуются относительно конфигурационного файла. Нужны существующие
JAM-базы, каталог для SQLite и TLS certificate/private key; сервер не создаёт
FTN-базы и не использует автоматически личные пути разработчика.

```sh
build/backend/apps/backend/fidoback /absolute/path/config.json
```

Альтернатива — переменная `FIDOBACK_CONFIG`. Без явной конфигурации или TLS
сервер завершается с ошибкой. Ошибка bind также даёт ненулевой exit code.
SIGINT/SIGTERM обрабатываются через `sigwait`, без логирования из signal handler.
Перед открытием SQLite берётся instance lock `<metadata_path>.lock`; файл
нельзя удалять при работающем backend. Рабочая модель — один backend и
локальный диск Linux/macOS рядом с HPT с включённым SMAPI sharing.

`ftn.areacfg_path` задаёт список разрешённых HPT-style `EchoArea`/`EchoAreaDefaults`.
ID конференции берётся из name, путь — из filename, а не из входного RPC ID.
Допускаются только JAM внутри `jam_base_path`; Passthrough/Squish исключены,
симлинки и traversal отклоняются. Используйте самостоятельный разрешающий
список без Include, макросов и условных EchoArea: неподдерживаемые конструкции
отклоняются целиком, чтобы не разрешать неверные базы. Пример строки:

```text
EchoArea RU.TEST messages/ru-test -b Jam -d "Тестовая конференция"
```

Настройки `server.thread_num` (1–256) ограничивают concurrent RPC и pollers;
`rpc_timeout_ms` (1–60000) ограничивает серверный бюджет запроса,
`shutdown_timeout_ms` (1–60000) — graceful shutdown. Размер входного RPC
ограничен 2 MiB, ответа — 4 MiB, metadata — 8 KiB; gRPC resource quota — 64 MiB.
Thread graph ограничен 100000 nodes, суммарное содержимое страницы thread —
3 MiB; превышение возвращает RESOURCE_EXHAUSTED. Для больших сообщений
уменьшите размер страницы. Лимиты формата JAM описаны ниже.

## Отправка и персональные данные

CreateMessage требует стабильный `operation_id` для повторов. Совпадающий
payload возвращает прежний результат; другой payload с тем же ID даёт
ALREADY_EXISTS. Sender берётся из серверного профиля; обычный ответ адресуется
автору родителя в той же конференции. Успех означает `SAVED_LOCALLY`, а не
доставку в FidoNet. Запись публикуется после durable operation intent и fsync;
незавершённые операции проверяются при запуске. Неизвестный хвост переводит
базу в quarantine без удаления чужих данных.

GetMessage обновляет личную прочитанность и историю; MarkRead не меняет
историю. `.jlr` не используется для персональной прочитанности приложения.
Новый SQLite key содержит user/conference/generation/message. Миграция
сохраняет **все** старые отметки в `read_status_legacy_backup` и начинает
прочитанность заново, сохраняя закладки/историю. Повтор миграции не удаляет
новые отметки. Перед рабочей миграцией нужна согласованная backup при
остановленных backend/HPT. Pack/replacement требует окна обслуживания;
online переписывание прежнего inode не поддерживается.

### Проверки HPT/SMAPI на искусственной базе

Протокол первого байта `.jhr` проверяется отдельным процессом установленной SMAPI через `scripts/check_smapi_locks.py`. Команды компиляции helper, подтверждённые версии Linux/macOS и ограничения описаны в [документации проверок](../../docs/testing.md). Эти проверки не используют рабочие FTN-пути; writer/recovery дополнительно проверяются fault/restart тестами.

### Ограниченный разбор и fuzz JAM

Парсер использует little-endian поля, сохраняет физические слоты `.jdx` и проверяет
границы до выделения памяти: тело ≤1 MiB, subfields ≤64 KiB, индекс ≤1 000 000
слотов, смещения и длины файлов в пределах 32-bit JAM. Конвертация текста
ограничена 4 MiB; неправильная кодировка и lossy conversion отклоняются.
`CHRS` переопределяет `ftn.default_encoding`; preview сохраняет целые codepoints.

Для libFuzzer нужен Clang с установленной библиотекой libFuzzer. Apple Clang
из текущего Xcode её не содержит; проверенный Linux-прогон использует Clang 19.

```sh
CC=clang-19 CXX=clang++-19 cmake -S . -B build/backend-fuzz \
  -DCMAKE_BUILD_TYPE=Debug -DFIDOBACK_ENABLE_ASAN=ON -DFIDOBACK_BUILD_FUZZER=ON
cmake --build build/backend-fuzz --target jam_parser_fuzz --parallel 4
python3 scripts/jam_fuzz_corpus.py build/jam-fuzz-corpus
build/backend-fuzz/apps/backend/jam_parser_fuzz build/jam-fuzz-corpus \
  -runs=10000 -max_len=2097152 -timeout=2 -rss_limit_mb=512
```

Команды выполняются из корня проекта. Corpus синтетический, рабочие FTN-базы не
используются. Harness создаёт отдельный временный каталог для каждого input,
ограничивает размер input 2 MiB и читает максимум четыре выбранных сообщения.
10 000 итераций ASan/UBSan на amster2 завершились без crash/UB, за 5 секунд.
Это ограниченный прогон, а не доказательство отсутствия всех ошибок.

### Локальное управление сессиями

Пользователи входят по данным линка HPT; команд выдачи токенов больше нет.
Служебные секреты сессий не показываются пользователю. Для отзыва всех сессий
профиля остановите backend и выполните из корня репозитория:

```sh
build/backend/apps/backend/ffido-admin revoke-user /path/to/metadata.db 'ftn:2:5015/1.2'
```

У перенесённых пользователей сохраняется прежний user_id. Локальный ключ
`auth.session_key_path` создаётся автоматически (32 случайных байта, права 0600);
каталог должен существовать. Нельзя копировать его в Git. При потере/замене ключа,
изменении пароля HPT или удалении линка прежние сессии отзываются при старте.
Сессия действует 30 суток; выход отзывает только сессию текущего устройства.
Перед миграцией остановите backend и сохраните резервную копию SQLite. Профили
с одинаковыми каноническими FTN-адресами требуют явного разрешения конфликта
администратором: автоматического слияния личных данных нет.

### Обязательный wrapper HPT

Все HPT-команды, работающие с этими JAM, запускаются через wrapper с **той же**
FFIDO-конфигурацией:

```sh
python3 scripts/run_hpt.py --config /absolute/path/config.json -- /path/to/hpt -c /path/to/hpt.cfg scan
```

`ftn.coordination_lock` обязателен. Wrapper удерживает exclusive flock на весь
процесс HPT; backend удерживает отдельные shared leases вокруг JAM open/read/
write/recovery, затем first-byte lock конкретной базы. Прямой запуск HPT в
обход wrapper не поддерживается: установленная SMAPI может писать кешированный
base header на close вне byte lock. Wrapper и backend должны иметь доступ к
одному lock-файлу (обычно один Unix user). Файл нельзя удалять или заменять,
пока работают процессы. Относительный coordination path разрешается относительно
config.json одинаково в Python и backend. `--timeout` ограничивает ожидание
wrapper (по умолчанию 30 секунд); при timeout HPT не запускается.

## HPT scan и high-water

В установленной SMAPI преобразование high-water может пропускать сообщения при
BaseMsgNum != 1. Проверенный экспорт использует `hpt scan -w -a RU.TEST`: `-w`
перечитывает сообщения без high-water; уже отправленные сообщения HPT исключает
по атрибуту Sent. Запускайте весь процесс через `scripts/run_hpt.py --config CONFIG --`
и тот же coordination_lock, что у backend. Round-trip проверяется
`FFIDO_TEST_HPT=/absolute/path/hpt ctest --test-dir build/backend -R ProcessTest.HptRoundTrip --output-on-failure`
на искусственных базах UTF-8/cp866; рабочие FTN-базы в тест не передают.

## Учётные данные HPT

Для сборки новой авторизации установите совместимые с вашим HPT библиотеки
`libfidoconfig`, `libhusky` и их заголовки. Укажите префикс установки:

```sh
cmake -S . -B build/backend -DCMAKE_BUILD_TYPE=Debug -DFFIDO_HUSKY_ROOT=/path/to/husky/prefix
cmake --build build/backend --parallel 4
```

Команды выполняются из корня монорепозитория. `ffido-hpt-auth` устанавливается
рядом с `fidoback`. Он читает HPT отдельным процессом с ограниченным каналом
результата и таймаутом; диагностика парсера не попадает в журналы FFIDO.
Виртуальные линки собственных AKA, автоматически созданные парсером, не дают
доступа к FFIDO. Реальные линки используют эффективный `SessionPwd`, при его
отсутствии — `Password`; явно пустой пароль не заменяется общим и не допускает
входа. Include и условия обрабатывает штатный парсер Husky.

В `config.json` добавьте `auth.hpt_config_path` (основной файл HPT) и
`auth.session_key_path` (отдельный локальный ключ сессий). Относительные пути
разрешаются от каталога `config.json`. После изменения паролей перезапустите
FFIDO. Нельзя подставлять HPT config в `ftn.areacfg_path`: там остаётся отдельный
разрешающий список JAM-конференций. Пароли, ключ и рабочий config не публикуются.

## Права поинтов на эхи

FFIDO использует эффективные подписки линка HPT: экспорт линку (`aexport`)
разрешает чтение, импорт от линка (`import`) — постинг. `ReadOnly` запрещает
постинг, `WriteOnly` запрещает чтение; маски, исключения, Include и defaults
обрабатывает libfidoconfig. Для обычного пользователя отсутствие подписки запрещает оба действия.
Явно назначенный через `auth.owner_addresses` владелец получает чтение и постинг всех
согласованных JAM-эх узла независимо от собственной подписки. Это не добавляет
адрес узла в HPT EchoArea и не меняет экспорт, импорт или подписки поинтов.
Физические ограничения записи JAM и изоляция чужих персональных mailbox сохраняются.
В конфигурации HPT эха должна быть связана с тем же JAM, что в каталоге FFIDO:
имя сравнивается без ASCII-регистра, путь должен указывать на ту же базу.
Несогласованный путь останавливает запуск; эха без соответствия недоступна.
Относительный путь EchoArea HPT разрешается от рабочего каталога процесса,
как в самом HPT. Запускайте FFIDO и HPT с одинаковым рабочим каталогом либо
используйте абсолютные пути (или макрос `[configdir]`) в HPT. Относительные пути
самого FFIDO config.json по-прежнему разрешаются от каталога этого файла.

Пример для синтетического линка `2:1/2` (Link/AKA задаются заранее):

```text
EchoArea RU.TEST /absolute/path/file -b JAM 2:1/2
ReadOnly 2:1/2 RU.TEST
```

Это позволяет читать RU.TEST, но не публиковать в неё. Без ReadOnly подписка
разрешает оба действия. После изменения подписок/прав перезапустите FFIDO:
новый снимок применяется также к существующим сессиям. SQLite-прочитанность,
история и закладки сохраняются; скрытые записи не выдаются до возврата прав.
JAM `.jlr` не изменяется. HPT по-прежнему запускается через общий wrapper.

В API конференция содержит `can_read` и `can_post`. Режим только постинга
возвращает метаданные без статистики писем и позволяет новую публикацию,
но не чтение или ответ родителю. Обновляйте сервер и Flutter-клиент совместно;
прежний клиент защищён сервером, но не отображает новые режимы корректно.

### Вход владельца поинтовой установки

Если собственный `Address` HPT — поинт (например, `2:5015/120.1`), отдельный
локальный Link не нужен. FFIDO находит его босса `2:5015/120` с соответствующим
`OurAKA 2:5015/120.1` и проверяет эффективный `SessionPwd`, иначе `Password`.
Пустой SessionPwd не заменяется Password. Другой аплинк не подходит; неоднозначное
соответствие останавливает загрузку. Собственный нодовый AKA автоматически
такого входа не получает.

У такого входа доступны чтение и постинг локальных JAM-эх с эффективным AKA
этого поинта. Профиль и адрес отправителя остаются `.1`, а не адресом босса.
Если для собственного адреса уже существует явный реальный Link, его пароль
и ACL имеют приоритет: этот режим не расширяет его права. Изменение пароля
босса или удаление соответствия отзывает сессии поинта после перезапуска.

### Старые сообщения с CHRS IBMPC

Для устаревшего неоднозначного `CHRS: IBMPC` используется настроенный
`ftn.default_encoding` (в локальном русском окружении — CP866). Явные
поддерживаемые CHRS сохраняют приоритет, неизвестные явные кодировки
и конфликтующие CHRS остаются ошибкой. Каталог конференций вычисляется
по заголовкам JAM без декодирования текстов, поэтому кодировка одного
старого письма не блокирует каталог. Чтение не переписывает исходные базы.

### Кодировка публикаций клиента в JAM

Flutter и protobuf передают текст как Unicode. Перед записью сервер преобразует
тело, тему и имена автора/получателя в `ftn.default_encoding` из config.json.
Для CP866 в существующей секции `ftn` задайте:

```json
"default_encoding": "cp866"
```

В `.jdt` сохраняются байты CP866, в `.jhr` — текстовые подполя в CP866 и
`CHRS: CP866 2`. Адреса и FTN-кладжи остаются ASCII. Новый ответ использует
кодировку сервера, а не CHRS родителя; чтение старых UTF-8-писем не меняет
настройку последующих публикаций. После изменения конфигурации нужен перезапуск.

Если символ не представим в CP866 (например, эмодзи), отправка возвращает
ошибку валидации до записи JAM; транслитерации непредставимых символов и автоматического
перехода на UTF-8 нет. Клиент оставляет черновик для исправления.

Это подтверждают `GrpcTest.Cp866*` и процессный HPT round-trip: тесты сравнивают
сырые байты с фиксированным эталоном, а не только читают собственную запись
тем же кодеком. Другие явно настроенные кодировки остаются поддерживаемыми.

При публикации сервер заменяет **все** заглавные кириллические `Н` (U+041D)
на латинские `H` (U+0048): `НН H н` → `HH H н`. Это действует для текста,
цитат и пересылок, темы, имени автора из профиля и имени получателя, включая
получателя ответа из исходного письма. Строчная `н` и остальные символы
сохраняются. Замена выполняется перед кодированием в JAM; в CP866 латинская
`H` записывается байтом `0x48`. Профиль, исходный черновик и старые сообщения
не переписываются. Повтор операции сверяется по исходному запросу: изменение
`Н` на `H` с прежним ключом отправки считается конфликтом.

### Дополнительные области HPT и владелец

FFIDO читает эффективную конфигурацию через libfidoconfig, включая Include и её defaults.

| HPT | Тип в FFIDO | Действия владельца с JAM |
| --- | --- | --- |
| EchoArea | Эхи | Прежние права линков HPT |
| NetmailArea / NetArea | Личная почта | Чтение, создание и ответ |
| LocalArea (включая carbon) | Локальные | Чтение и локальная запись |
| BadArea / DupeArea | Служебные | Только чтение |
| RobotsArea | Роль указанной NetmailArea | Только чтение, также через физические алиасы |

DupeHistoryDir и CarbonCopy не создают отдельной конференции. Поддерживается только JAM;
Squish, MSG и passthrough приватных областей показываются как неподдерживаемые, со статистикой «неизвестно».
Конвертации и создания баз нет. Пути должны входить в `ftn.jam_base_path`, без симлинков;
при необходимости оператор явно меняет корень. Отсутствующая/повреждённая JAM — ошибка, а не Squish.
Публичная эха и приватная область не могут указывать на одни физические файлы.
Смешанные Local/Netmail-алиасы одной базы доступны только для чтения, чтобы локальная запись не попала в pack через другое имя.

`auth.owner_addresses` — явный список канонических FTN-адресов, по умолчанию `[]`.
Например, `"owner_addresses": ["2:1/2.1"]` допустимо только для уже существующей HPT-идентичности
с непустым паролем. Список не создаёт учётные записи. Номер поинта, имя и OurAKA не назначают владельца.
Для владельца нужен отдельный непубличный пароль: знание его FTN-адреса и пароля позволяет войти под ним.
После изменения списка перезапустите сервер: прежние сессии сразу используют новую политику.
Обновляйте владельческий клиент и сервер совместно до включения списка владельцев.

Netmail требует конкретного имени и полного FTN-адреса адресата; автор всегда берётся из
аутентифицированного профиля и должен совпадать с эффективным AKA области. При несовместимости
сервер отказывает, не подменяя адрес. Ответ без адреса исходного автора также отклоняется.
Netmail сохраняется с Local/TypeNet/Private и адресами, LocalArea — с Local/TypeLocal;
эховые AREA/SEEN-BY/PATH и Origin к ним не добавляются. CP866, Н → H и журнал идемпотентности общие.
Успех означает локальное сохранение, не доставку. Служебные области не запускают роботов/переобработку.

Экспорт netmail выполняет оператор командой `hpt pack` через `scripts/run_hpt.py`;
требуется настроенный Route, иначе HPT может закончить с кодом 0 без экспорта.
Сканирование эх — отдельный `hpt scan`; LocalArea не экспортируется. RPC не запускает эти команды.
Полный lifecycle HPT/SMAPI должен оставаться под общей блокировкой. Не включайте pack в живой toss.
Пример проверки и команды на временных базах: [ftn-check](../../docs/ftn-check.md).
Варианты будущих ящиков поинтов: [отдельный этап](../../docs/point-mailbox-design.md).

### Совместимость атрибутов JAM с HPT/SMAPI

Таблица `JamMessageAttribute` сверена с `smapi/api_jam.h`: TypeLocal = `0x00800000`,
TypeEcho = `0x01000000`, TypeNet = `0x02000000`, Locked = `0x40000000`.
Исправлены также биты ReceiptRequest/ConfirmRequest и последующие атрибуты.
Прежние тесты повторяли ошибочные числовые значения TypeNet/TypeLocal; теперь они
проверяют правильные сырые заголовки, а отдельный исполняемый тест, связанный с настоящей
SMAPI, независимо сверяет все 29 констант и читает письма до/после HPT pack/scan.
Успешный pack сам по себе недостаточен: HPT может нормализовать тип сообщения.
Проверяются новое Netmail, ответ на входящее от SMAPI, адреса, REPLY, Sent,
экспорт Echo и отсутствие экспорта LocalArea. Для запуска HPT-проверки задайте `FFIDO_TEST_HPT`.
Старые сообщения при чтении не переписываются; исправление действует на новые записи.
Массовое исправление ранее записанных атрибутов требует отдельного решения.

Для сборки проверок нужны заголовки и библиотека SMAPI той же установки Husky/HPT.
Если установка не содержит требуемый `msgapi.h` файл `version.h`, укажите каталог
заголовков соответствующей версии исходников SMAPI при конфигурации CMake:
`-DFFIDO_SMAPI_VERSION_INCLUDE=/path/to/smapi/smapi`.

### Персональный Netmail поинтов

`point_mail` выключен по умолчанию. При включении каждый явно назначенный Link-поинт
своего нодового AKA получает отдельную JAM и непрозрачный mailbox ID. Вход не создаёт баз.
`ffido-admin provision-mailboxes CONFIG` создаёт только новые файлы и сохраняет
принадлежность всех трёх inode; существующие непривязанные, подменённые и алиасные
файлы отклоняются. Это режим инфраструктуры босса с собственным нодовым Address:
сервер с единственным собственным AKA-поинтом не становится боссом других поинтов.

Ящик доступен только профилю назначенного адреса. Owner-роль не открывает чужой
mailbox endpoint; прежний владельческий доступ к сырым областям HPT остаётся отдельным.
Файловый администратор хоста может читать JAM: шифрования от него нет. Две сессии
одного адреса разделяют ящик, прочитанность, закладки, историю и последнюю позицию,
при этом logout одного устройства не завершает другое.

Личные JAM не регистрируются в HPT. HPT получает отдельную egress NetmailArea;
другая область служит ingress. Координатор `MailBridge` сохраняет source-key,
адресный delivery-key, хеши и стадии в SQLite, захватывает входящее настоящим Locked,
записывает копию через прежний JamWriter и сохраняет исходник. Все записи выбранного
shared ingress проходят адресный dedup до pack, включая обычный транзит. Повтор MsgID
разным адресатам разрешён; коллизия содержимого или неоднозначная адресация изолируется.
Входящий текст не подвергается Н → H повторно.

Исходящая копия, provenance, read-отметка и outbox-event подтверждаются согласованным
журналируемым commit до ответа RPC. Egress-копия с тем же MsgID сначала Locked,
после устойчивого связывания разрешается pack. Локальному адресату FFIDO создаётся
входящая копия без outbound; self-mail оставляет отдельные исходящую и входящую записи
с независимой прочитанностью. Личный ответ на outgoing адресуется destination,
на incoming — origin; направление берётся из durable provenance. Успех означает
локальное сохранение, не доставку. Исходящая пользовательская история после pack остаётся.

Для включённой интеграции wrapper принимает только полный цикл либо операторские
status/reconciliation. Отдельные команды HPT через него запрещены, в том числе aliases
и запуск с неявным набором операций. Цикл: recovery → toss → dispatch/local/outbox →
проверка готовности → pack → необязательный scan. Одна exclusive lease наследуется
дочерними процессами и проверяется по inode/режиму; RPC внешние команды не запускает.
Прямой запуск HPT в обход wrapper вне гарантий интеграции.

Прерывание pack сохраняет неопределённость экспорта и запрещает автоматический повтор.
SQLite `mail_export_log` хранит begin/complete/uncertain/reconciled. Оператор сверяет
пакеты и Sent в транспортной базе; только после сверки явно подтверждает reconciliation.
Это не создаёт очередь или MsgID заново и не обещает exactly-once внешней доставки.
Команды, временный пример, backup и rollback: [ftn-check](../../docs/ftn-check.md).

**Миграция:** SQLite schema 6 добавляет физические bindings, schema 7 — переходы,
provenance/outbox, позиции чтения и журнал экспорта. В operations уникальность MsgID
разделяется по copy_scope, сохраняя прежнее ограничение для обычных отправок и разрешая
контролируемые копии транспорта/адресата. Существующие JAM не переписываются.
Перед развёртыванием нового бинарника, даже с выключенным `point_mail`, нужен
согласованный backup SQLite. Старый backend со schema 5 новую БД не откроет;
откат бинарника требует восстановления согласованного снимка metadata.

Контракт расширен добавочными полями personal_mailbox/direction/позиции и anchor/factual offset.
Для почтового режима обновляются сервер и клиенты вместе. При отсутствии новых полей
клиент сохраняет прежний режим. Прочитанность и позиция лежат в SQLite, JAM Read/JLR
не используются. Сервер назначает revision при фиксации чтения; клиент обновляет почту
при resume/refresh/возврате к списку, отбрасывает старые ревизии и ответы прежних сессий.
Приватного offline fallback нет; черновики, scroll offset и push не синхронизируются.

### Массовая отметка эхи прочитанной

Дополнительный RPC `MarkConferenceRead(conference_id, operation_id)` отмечает снимок
всех живых сообщений читаемой JAM EchoArea только для текущего пользователя.
Постинг не требуется. Netmail, Local и служебные области отклоняются.
Ответ содержит marked_count (новые отметки), snapshot_count и generation. Старые RPC
и номера полей сохранены; старые клиенты продолжают работать. Новый клиент при
UNIMPLEMENTED сообщает о неподдерживаемом сервере без поштучного обхода писем.

Ключ операции — 1–128 ASCII букв, цифр, `_`/`-`; его следует сохранять при потере
ответа. Повтор подтверждённого ключа возвращает прежний результат даже после
рестарта или замены поколения, не отмечая последующие поступления. Другая эха с
тем же пользовательским ключом возвращает ALREADY_EXISTS. При отсутствии commit
повтор делает новый снимок первой успешной фиксации. ACL проверяется и на повторах.

Миграция SQLite 7 → 8 добавляет bulk_read_operations. Отметки и receipt фиксируются
одной транзакцией; история/reading_positions, JAM Read/JLR и содержимое баз не меняются.
Перед запуском нового backend нужен согласованный backup metadata.db с WAL либо
checkpoint при остановленном сервере. Прежний backend схемы 7 не открывает схему 8:
для rollback сохраните новую БД и восстановите совместимый backup, не удаляйте
таблицу/не понижайте user_version наугад. Никакого автоматического запуска на live.

### Пути тоссера в контейнере

Необязательный `ftn.path_mappings` — массив правил `{"from":"/home/fido","to":"/home/yurik/fido"}`.
По умолчанию массив пуст и действует прежний режим отдельного каталога `ftn.areacfg_path`.
Оба префикса абсолютные, без `.`/`..` и NUL. Совпадение проверяется по компонентам;
выбирается самый длинный префикс, правило применяется один раз. Повторный `from` запрещён.
Пути `auth.hpt_config_path`, `ftn.areacfg_path`, `jam_base_path`, `coordination_lock`,
SQLite, ключей и сертификатов задаются в файловой системе процесса FFIDO и не отображаются.
Отображаются только пути, прочитанные из конфигурации тоссера.

Для отображения `include` нужен helper с адаптером открытия конфигов. Он сохраняет
макросы, условия и ACL самой libfidoconfig; конфиги тоссера не переписываются.
Используйте исходники **той же установленной версии** Husky: проверенная ревизия
`huskyproject/fidoconf` — `62c963a6f078905660f2c0b3a6929383823190c5`.
CMake проверяет SHA-256 `src/cfg.c` и применяет `cmake/patches/fidoconfig-open.patch`
к копии в build-каталоге. Изменённый модуль связывается только с helper и статической
`libfidoconfig.a`; системная установка не изменяется. Остальные библиотеки Husky
и заголовки должны соответствовать этой ревизии.

```sh
cmake -S . -B build/backend -DCMAKE_BUILD_TYPE=Debug \
  -DFFIDO_HUSKY_ROOT=/path/to/husky/install \
  -DFFIDO_FIDOCONFIG_LIBRARY=/path/to/husky/install/lib/libfidoconfig.a \
  -DFFIDO_FIDOCONFIG_SOURCE=/path/to/matching/fidoconf
cmake --build build/backend --parallel 4
ctest --test-dir build/backend --output-on-failure -R 'HptAuth|PathMapping|PointMailbox.*Mapped'
```

Без адаптера обычная конфигурация работает как прежде, а непустой mapping
даёт явную ошибку с требованием пересобрать helper. Лимиты mapped-загрузки:
128 правил, 64 KiB JSON правил, глубина include 32, до 1024 подключений,
16 MiB суммарных размеров конфигов; действуют прежние timeout и лимит вывода helper.
Активный цикл include, недоступный файл или превышение лимита останавливает загрузку.
Относительные include сохраняют семантику рабочего каталога HPT; FFIDO не подменяет
её разрешением относительно подключающего файла.

При непустом mapping каталог берётся из всей активной HPT-конфигурации, включая
её defaults и опции (`-p` и другие). `ftn.areacfg_path` должен быть локальным путём
одного из активных include — соответствие проверяется по физическому файлу.
Файл вне активных include вызывает отказ. Эхи без прав не становятся доступными;
личные/служебные области сохраняют owner-политику. JAM остаются внутри
`jam_base_path`, с прежними проверками симлинков и физической идентичности.

Фрагмент `config.json` для FFIDO на хосте amster2 (добавьте остальные обязательные
параметры из config.example.json):

```json
{
  "auth": { "hpt_config_path": "/home/yurik/fido/hpt.cfg" },
  "ftn": {
    "areacfg_path": "/home/yurik/fido/areas.cfg",
    "jam_base_path": "/home/yurik/fido/msgbase",
    "coordination_lock": "/home/yurik/fido/ffido/hpt.lock",
    "default_encoding": "KOI8-R",
    "path_mappings": [
      { "from": "/home/fido", "to": "/home/yurik/fido" }
    ]
  }
}
```

`default_encoding` сохраняет прежний смысл: кодировка новых публикаций и резервная
кодировка чтения при отсутствии CHRS или старом IBMPC. Явный CHRS письма имеет
приоритет. Для amster2 задайте `KOI8-R`, локально оставьте `cp866` (значение по
умолчанию). KOI8-R-публикации получают `CHRS: KOI8-R 2`, включая ответы на CP866/UTF-8.
Непредставимые символы дают ошибку без записи; исторические базы не перекодируются.
Кодировка JAM не задаёт автоматически кодировку конфигов HPT или паролей.

Создайте каталог lock с правами для UID/GID FFIDO и тоссера. При mount
`/home/yurik/fido:/home/fido` один файл виден как
`/home/yurik/fido/ffido/hpt.lock` и `/home/fido/ffido/hpt.lock`.
Не заменяйте lock-файл при работающих процессах. Все toss/pack/scan должны использовать
одну общую lease; отдельные lock-файлы с одинаковыми именами не обеспечивают координацию.
Для отключённого `point_mail` пример синхронного запуска с хоста:

```sh
python3 scripts/run_hpt.py --config /path/to/ffido/config.json --timeout 60 -- \
  docker compose -f /home/yurik/fido/docker-compose.yaml exec -T fido \
  /usr/local/bin/hpt -c /home/fido/hpt.cfg scan -w
```

Путь к HPT внутри образа проверьте для своего развёртывания. Wrapper удерживает
хостовый lock до завершения команды. Не используйте `exec -d`: Docker exec не
передаёт inherited lease fd и при обрыве управляющей команды не гарантирует
завершение HPT. Такие обрывы требуют остановки/проверки оставшегося HPT перед
возобновлением FFIDO. Полный `--cycle` с point_mail запускайте в одной среде,
где доступны HPT и ffido-admin с прежним наследованием lease; прозрачный
cross-container `--cycle` не поддерживается. Изменение mount само по себе не
подключает посторонние cron-задачи тоссера к wrapper.

При проверке адаптера используйте `PointMailboxProvisionMapped` и
`PointMailboxCycleMapped`: первый проверяет перевод логических путей и коллизии
ящиков, второй повторяет полный HPT-цикл в общей среде с включённым mapping.

## Управляемое обновление установленного сервера

Команды `fidoback --version`, `fidoback update check`, `update download`,
`update apply` и `update rollback` работают до обычного startup. `check/download`
не открывают JAM и рабочую SQLite. Обычный `fidoback CONFIG` не скачивает обновления.
Все компоненты сервера и библиотеки заменяются одним комплектом.

Для updater нужен Python 3.10+ с зависимостями из поставляемого
`share/ffido/update/requirements.txt`. Создайте отдельное окружение вне каталогов
версий и добавьте его в PATH оператора перед выполнением команд:

```sh
python3 -m venv /opt/ffido/update-runtime
/opt/ffido/update-runtime/bin/python -m pip install -r /opt/ffido/current/share/ffido/update/requirements.txt
export PATH="/opt/ffido/update-runtime/bin:$PATH"
/opt/ffido/current/bin/fidoback update check
/opt/ffido/current/bin/fidoback update download --install-root /opt/ffido
```

Первый переход с ручной установки выполняется при остановленных экземплярах
сервера. Сохраните согласованную backup с HPT по прежней инструкции. Подготовьте
`/opt/ffido/releases/vX.Y.Z/` и распакуйте туда полный текущий серверный пакет,
убрав только внешний каталог архива; `bin`, `lib`, `share`, `BUILD.json` должны
находиться непосредственно в каталоге версии. Создайте относительную ссылку
`/opt/ffido/current -> releases/vX.Y.Z`. Конфигурация, TLS, JAM, SQLite и session key
должны остаться вне `releases/`. Updater отказывает при неизвестном layout.

Установкой владеет оператор обновления, каталог не должен быть доступен группе
или остальным пользователям на запись. Для непривилегированного пользователя
службы заранее создайте `/opt/ffido/.running.lock` с правами 0600 и владельцем
этого пользователя; файл доступен оператору обновления. Не удаляйте lock при работе.
Служба использует путь `/opt/ffido/current/bin/fidoback /etc/ffido/config.json`.

Foreground: завершите сервер по SIGTERM, выполните apply, запустите новый сервер
прежней командой и проверьте его. Для systemd последовательность такая:

```sh
sudo systemctl stop ffido.service
/opt/ffido/current/bin/fidoback update apply --install-root /opt/ffido --config /etc/ffido/config.json
sudo systemctl start ffido.service
/opt/ffido/current/bin/fidoback --check-ready 127.0.0.1:8080 /etc/ffido/tls/ca.pem fido.example.org
```

На macOS аналогично: `launchctl bootout` своего plist, apply, затем
`launchctl bootstrap` того же plist и `--check-ready`. Updater не угадывает label
службы и не вызывает sudo. Запуск и остановку выполняйте с прежними пользователем,
правами и путями; server daemon не получает полномочий обновлять установку.

`--check-ready HOST:PORT CA_FILE TLS_SERVER_NAME` проверяет TLS и существующий
неизменяющий gRPC-запрос с deadline. Неверное имя или CA дают ненулевой результат.

Для отката остановите службу, выполните `update rollback --install-root ... --config ...`,
затем запустите и проверьте её. Откат разрешён только к подписанному сохранённому
полному комплекту с совместимой схемой. Для bootstrap-версии без подписанного
манифеста автоматический rollback недоступен: сохраните её и согласованную backup
для ручного восстановления. Новые версии не мигрируют неизвестные форматы:
несовместимая schema требует отдельной процедуры, а не принудительного downgrade.

Производственный ключ обновлений должен быть настроен по
[руководству выпуска](../../docs/github-publication.md). Пустой trust store не даёт
права устанавливать неподтверждённый пакет. В Docker native apply запрещён;
используйте host-команду из [инструкции Docker](../../docs/docker.md).

### Текстовый кросспостинг

`CreateCrosspost` принимает основную `CreateMessageRequest` и от 1 до 20
дополнительных уникальных ID эх. Основная эха обязательна и не повторяется
в дополнительных. Все области должны разрешать публикацию и поддерживать JAM;
при ответе требуется чтение основной эхи. UUE через этот RPC не отправляется.
До первой записи сервер проверяет всю группу, итоговые размеры и кодировки.
Каждая копия начинается блоком GoldED+ `* Originally in …` и отдельными
`* Crossposted in …`, затем пустой строкой и пользовательским текстом.
Каждая копия имеет собственный MSGID; REPLY и локальные связи ответа остаются
только в основной эхе.

Ответ содержит `complete`, `total`, `saved` и `pending_code` (gRPC-код первой
незавершённой копии). Только `complete=true` подтверждает устойчивое локальное
сохранение всей группы; сетевую доставку в FidoNet он не подтверждает. Часть
копий может быть видна до завершения группы. При потере ответа повторяют тот
же запрос с прежним `operation_id`; изменение текста или состава с прежним
ключом даёт ALREADY_EXISTS. Порядок дополнительных ID на идентичность не влияет.
Права перепроверяются при повторе; при запрете идентификаторы закрытых копий
не возвращаются.

SQLite-миграция 10 добавляет `crosspost_groups` с неизменяемым планом: снимок
профиля/получателя, поколения баз, внутренние ключи и MSGID. Прогресс берётся
из устойчивых дочерних операций JAM, поэтому сбой между commit копии и ответом
не создаёт дубль. Ключи дочерних операций начинаются с `@crosspost-`, недопустимого
для внешних ключей одиночной отправки. При смене поколения или quarantine
группа останавливается; сохранённые копии не удаляются и не пересоздаются.

Обновление: сначала сервер, затем клиент. Старые клиенты продолжают пользоваться
CreateMessage/UUE; новый клиент на старом сервере получает UNIMPLEMENTED без
одиночного fallback. Перед откатом сервера завершите или сверьте незавершённые
группы; сохраняйте таблицы SQLite и уже записанные JAM-письма. Старый сервер
не открывает схему 10: откат требует резервной копии метаданных и согласованной
операторской сверки, а не ручного уменьшения user_version.
