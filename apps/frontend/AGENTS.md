# FE: Flutter / Dart

Эти правила дополняют корневой `AGENTS.md` для `apps/frontend/`, включая тесты и платформенные каталоги. Общие контракты и спецификации остаются в корне монорепозитория.

## Контекст и код

- До правок читайте `README.md` этого приложения, `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, затронутые экраны, repositories, API transport и тесты. Выбирайте SDK, закреплённый текущими README/CI/dependency lock; не понижайте ограничения `environment.sdk` ради глобального Dart.
- Сохраняйте существующее разделение widgets/pages, repositories, models и typed API transport. Не добавляйте новый state manager, service locator или архитектурный слой без необходимости. Виджеты не должны напрямую работать с JAM/SQLite/HPT или обходить транспортный слой.
- Используйте подходящие навыки официального `dart-flutter` плагина: widget/integration tests, layout, navigation, localization и другие — по задаче. Сверяйте их рецепты с установленным SDK и принятыми решениями проекта; навык не разрешает менять архитектуру и зависимости попутно.
- Соблюдайте null safety и `flutter_lints`; предпочитайте явные типизированные модели и небольшие понятные виджеты. Не скрывайте ошибки через `dynamic`, произвольные `!`, casts, `ignore_for_file` или ослабление analyzer. Используйте `const` и неизменяемость, когда это соответствует реальному состоянию.
- Сохраняйте владение состоянием: отменяйте RPC/подписки и освобождайте controllers/focus nodes в принятом lifecycle. После `await` проверяйте актуальность `mounted`, session epoch и запроса, когда это необходимо; не применяйте ответы старой сессии к новому пользователю/серверу. Не выполняйте сетевые вызовы как побочный эффект повторного `build`.
- Сохраняйте правила отмены, deadlines, пагинации, cache scope и capability fallback. Не выдавайте ошибку сети за пустые данные или успешную запись. При неизвестном результате отправки сохраняйте текст и operation ID, повторяйте ту же операцию согласно действующему контракту.
- Секреты храните только существующим защищённым механизмом; SharedPreferences не подходит для паролей и токенов. Не отключайте TLS и не смешивайте native gRPC с Web gRPC-Web. Для платформенных различий используйте принятые adapters/conditional imports.
- Для UI сохраняйте доступность, Semantics, фокус, клавиатуру, текстовое масштабирование и адаптивные размеры. Покрывайте loading/error/empty/success и сохранение пользовательского ввода. Не меняйте терминологию и локализацию посторонних экранов.
- Источник wire-моделей — `../../contracts/ffido/v1/ffido.proto`. Не редактируйте и не форматируйте `lib/api/generated/`; используйте `../../tools/proto/generate.sh` из корня по общим правилам.

## Обязательная MCP-диагностика при отладке FE

1. Найдите доступные инструменты Dart/Flutter MCP; проверьте, что сервер использует нужный SDK и корень `apps/frontend`, а не другой Flutter-проект. Для анализа/тестов настройте project roots через поддерживаемый сервером механизм. Если подходящих инструментов нет, явно сообщите ограничение и используйте CLI.
2. Для analyzer/type/symbol ошибок используйте реально доступные `analyze_files`, `resolve_workspace_symbol`, `hover`, `signature_help` или эквиваленты из списка сервера. Устраните причину; не применяйте массовый `dart_fix` без просмотра затронутых изменений.
3. Для runtime/UI-бага обнаружьте нужное приложение (`list_running_apps`), подключитесь к его Dart Tooling Daemon, прочитайте runtime errors и logs, исследуйте widget tree/выбор виджета. Используйте фактически доступные инструменты (`get_runtime_errors`, `get_app_logs`, `get_widget_tree` и другие), а не предполагаемый API.
4. Воспроизведите пользовательский сценарий на тестовых данных. При доступном Flutter Driver выполняйте реальные действия и проверяйте состояние; для невоспроизводимого окружения добавьте unit/widget test через внедряемый transport. Не считайте один screenshot или отсутствие exceptions доказательством правильного поведения.
5. После изменения исполняемого Dart-кода под `lib/` примените hot reload через MCP для widget/build и простых методов. Для `main`, `initState`, global/static state и фундаментальной логики используйте hot restart. Пропускайте это для комментариев, whitespace, generated-кода и изменений вне `lib/` (включая tests). Работайте только с нужным тестовым приложением; при отсутствии процесса сообщите, что runtime-проверка не выполнена.
6. Повторите сценарий, проверьте новые runtime errors и закрепите регрессию постоянным тестом. Изменения native plugins, platform code и зависимостей могут требовать полной пересборки; hot reload их не проверяет. MCP не заменяет analyze, тесты и нужную платформенную сборку.

## Проверки и рабочие каталоги

Из `apps/frontend` с закреплённым Flutter SDK:

```sh
flutter pub get --enforce-lockfile
flutter analyze --no-pub
flutter test --no-pub
```

- Сначала запускайте затронутые тесты (`flutter test --no-pub test/<путь>`), затем полный набор при изменении общего API/state/navigation. Для UI добавляйте widget tests, для изолированной логики unit tests; для сетевого поведения transport/API tests. Проверяйте ошибки, отмену, disposal и смену сессии, когда они затронуты.
- Из корня: `python3 scripts/check_dart.py --check` проверяет handwritten Dart, исключая generated-код. Форматируйте только изменённые handwritten-файлы с проектным `dart format`; не запускайте массовую перезапись ради одной правки.
- При изменениях общего protobuf выполните генерацию/проверку и контрактные тесты FE/BE по корневой инструкции. Тесты `ApiClient` должны сохранять реальные RPC к изолированному серверу; одних mocks для проверки wire-контракта недостаточно.
- Для изменений платформенных интеграций и dependencies выполняйте штатную сборку затронутой платформы. Web: `flutter build web --release --no-pub`; native: `flutter build apk --release`, `flutter build macos --release` или команда целевой платформы по README. После `integration_test` не добавляйте `--no-pub` к native release build: требуется восстановить production plugin registration.
- Для multi-device/secure storage используйте `python3 scripts/check_two_devices.py --android emulator-5554` из корня, только при подготовленной среде по README. Не утверждайте, что тест на одной платформе проверил остальные; укажите недоступные устройства и SDK.
