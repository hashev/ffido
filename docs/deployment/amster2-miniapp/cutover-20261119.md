## Пауза автоматики и фиксация образов

В окне оператор удерживает EX flock `/home/yurik/fido/ffido/maintenance.lock`
в отдельном управляющем процессе до окончания проверки. На Linux держать его через
read-only FD с EX flock, чтобы supervisor сам не считался writable FD писателем.
Занятый lock означает ожидание,
а не удаление lock-файла. Сначала дождаться уже работающего maintenance action.

Под lock сохранить актуальный `crontab -l` в приватный журнал и закомментировать
только точную строку `/home/yurik/fido/ffido/manage.sh update`, добавив причину
`telegram-main cutover; local unsigned image pair; manual resume only`.
Проверить, что найдена ровно одна строка, остальные задания сохранены.
Не менять чужие задания, не отключать cron целиком и не подделывать JAM active marker.
Poll/renew/rotation под этим же maintenance lock пропустят окно; после его освобождения
их обычное расписание сохраняется. Прямые ручные update/apply/rebuild_worker запрещены
на весь период работы локальной неподписанной пары.

После завершённого backup атомарно установить `backend.pinned.json` как
`/home/yurik/fido/ffido/updates/image-override.json`, сохранив прежний файл в backup.
Это канонический путь, который уже читает manage.py; временного третьего -f недостаточно.
Сохранить режим 0640 и UID/GID 1000. Проверить разрешённые image через Compose config
и image inspect, не печатая полную effective config. Файл .env пока не использовать
для пересборки: пары уже построены и проверены. После запуска сохранить настоящий
BUILD.json нового backend в deployed-identity и отдельную запись с обоими image ID,
причиной паузы и ссылкой на backup. Не объявлять это подписанным stable-релизом.
`update-transaction` отметить complete только после успеха обеих служб; при ошибке
держать окно/автоматику на паузе, не оставлять phase=rebuild-worker.

Возобновление автоматического update — отдельная будущая операция после появления
совместимого официального релиза и проверки его миграции/worker. Сам факт завершения
переключения не разрешает раскомментировать update.

## Остановка писателей и полный backup

Сохранить остановленные сервисы/их исходные image ID и время старта. Под maintenance
lock остановить сначала ffido-tosser, затем fido/jamnntpd и ffido с достаточным timeout.
Не применять kill -9 и не продолжать после timeout. Дождаться завершения HPT/export,
проверить отсутствие процессов писателей и свободные metadata.db.lock/hpt.lock.
Ни snapshot helper, ни restore не управляют службами сами.

SQLite после остановки должна быть checkpointed. Если остался WAL, под координационными
locks выполнить штатный SQLite checkpoint(TRUNCATE) с проверкой busy=0, integrity_check
и foreign_key_check. Не удалять WAL/SHM вручную. При pending/uncertain операциях — STOP,
не ремонтировать их SQL-запросами. Snapshot helper отвергнет ненулевые sidecars.

`manage.sh backup` НЕ использовать: он автоматически запускает писателей, а состав
старого архива неполон. Использовать подготовленный `ffido-node-backup` из candidate.
Источник — остановленный настоящий узел, без legacy override. Назначение — новая
приватная директория ВНЕ `/home/yurik/fido`, на диске с достаточным местом.

Важная координация: внешний процесс уже держит maintenance.lock. Helper нельзя
заставлять повторно захватывать тот же flock через другой FD: он закономерно откажет.
Для helper заранее создать обычный приватный файл `ffido/cutover.snapshot.lock` и
передать `--maintenance-lock ffido/cutover.snapshot.lock`; настоящий maintenance.lock
всё время удерживает внешний supervisor. Этот дополнительный lock войдёт в manifest.
Если supervisor потерян, подготовку снимка прекратить, службы не запускать.

Параметры helper:

```text
snapshot --root /source --destination /backup/current
--helper /opt/ffido/bin/ffido-hpt-auth
--map /home/fido=/source --map /srv/fido=/source
--map /var/lib/ffido=/source/ffido/state
--map /etc/ffido/tls=/source/ffido/tls
--maintenance-lock ffido/cutover.snapshot.lock
--include ffido/tls --include logs --include nodelist
--include ffido/manage.sh --include ffido/mcp
```

Контейнер: точный candidate ID, entrypoint `/opt/ffido/bin/ffido-node-backup`,
`--network none --pid host --user 1000:1000 --ulimit nofile=8192:8192`, без портов.
Root mount `/home/yurik/fido:/source` допускает открытие lock-файлов; runtime aliases
этого ЖЕ источника `/home/fido`, `/srv/fido`, `/var/lib/ffido` (state),
`/etc/ffido/tls` — read-only. Mount только приватного backup parent как `/backup`.
Это административный helper, не запуск backend с рабочими volumes.
Проверка FD в контейнере не заменяет контроль остановленных host-писателей.

Обязательный inventory helper включает всю JAM с JLR, state с session key,
HPT/includes/intab/outtab, config/corrections, f/spool/dupebase/flags/fileboxes,
Compose/.env/binkd.cfg/t.sh, ops/updater/updates, ACME, identity/transaction.
Сверить дополнительные активные скрипты и внешние зависимости перед снимком.
Crontab/firewall/image archive manifests сохранять отдельно в приватном журнале окна.
Отсутствие зависимости — отказ, а не создание пустой очереди.

Успех: complete snapshot.json + snapshot.tar.gz, записанный отдельно SHA-256 manifest,
повторный `verify --root /backup/current --manifest /backup/current/snapshot.json
--expected-digest SHA256`. Проверить свободное место. В отдельную директорию распаковать
архив с сохранением прав; запустить rollback `mailbox-restore ROOT MANIFEST SHA check`,
затем `apply PLAN_SHA`; минимальный nofile — число файлов + 32 (8192 увеличить при необходимости).
Пробная копия имеет network=none, никакие production aliases ей не давать.
Проверить schema11 и readiness rollback на копии. Не отправлять сообщений.
Не запускать рабочее обновление, пока новый полный снимок не прошёл это восстановление.

## Результат этой подготовки

Созданы локальные pins и процедура. SSH-проверка read-only подтвердила конфигурацию,
образы, здоровье, DNS/TLS и отсутствие допуска9443. Проверки этой подготовки: оба pinned override прошли `docker compose config --images`
на исходном рабочем Compose. Gateway Compose прошёл `config --quiet`. Envoy из
закреплённого образа прошёл `--mode validate` в network=none без listener, с существующими
тестовыми cert/key на read-only mount и рабочим CA; production key не выпускался.
`python3 -m unittest discover -s tools/gateway -p test_run.py` — 2/2;
`git diff --check` — успешно. Эти проверки не заменяют запуск production HTTPS.
Свежий backup/restore, пауза cron, выпуск production сертификата, запуск служб,
правила9443, публикация и mail cycle НЕ выполнены. Готовность к рабочему переключению
пока false: необходимы место, production HTTPS с продлением и свежий backup в окне.
