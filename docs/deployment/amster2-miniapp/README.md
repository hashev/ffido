## Целевая схема

```text
Pages https://hashev.github.io/ffido/ + тот же @f120n5015z2_bot
  ├─ amster2-miniapp-test → https://f120n5015z2.ddns.net:8443 → test :18080
  └─ amster2-main         → https://f120n5015z2.ddns.net:9443 → main :8080
```

Новый рабочий gateway — отдельный контейнер с host network. :9443 свободен;
применение потребует отдельного допуска TCP 9443 в persistent AMSTER-INPUT и его
активных правилах. Для host network правило Docker DNAT не требуется. Не менять
:8443, :443 и существующий доступ native на :8080. Шаблон слушает IPv4 0.0.0.0;
IPv6/AAAA сейчас не заявляется: при добавлении AAAA отдельно обеспечить listener,
firewall и внешний IPv6-тест. Новая A-запись не нужна. Перед применением перепроверить
DNS, отсутствие чужого listener и состояние DDNS.

Upstream gateway: `v1002682.hosted-by-vdsina.com:8080`, локальное разрешение
через extra_hosts на 127.0.0.1. Это сохраняет SNI и строгую проверку SAN/CA
существующего backend-сертификата, избегая петли через публичный IP. Не заменять
TLS upstream на plaintext и не отключать verification. Проверить из namespace
нового контейнера, что name → loopback и backend TLS действительно доступен.

CORS/RBAC: ровно `https://hashev.github.io`, без /ffido/ и завершающего слеша,
POST/OPTIONS, authorization и gRPC-Web заголовки. Этот origin общий для всех
Pages-проектов владельца; он не является средством аутентификации. Авторизация
остается в backend. Admin listener и access log с metadata не включать.

## HTTPS и продление

Для рабочего :9443 нужен сертификат SAN f120n5015z2.ddns.net. Номер порта в
сертификат не входит. Тестовый сертификат этого имени уже действует до
16.02.2027 06:45:56 UTC, но его private key и ACME-state не копировать из теста
как постоянную зависимость production. План: отдельный production Certbot account/
lineage в /srv/ffido-miniapp-main/acme и отдельные private keys; выпуск только после
разрешения. Не нужен доступ к DNS TXT при standalone HTTP-01 на уже доступном :80.
Если условия изменятся, сначала пересмотреть challenge, не менять DNS автоматически.

Сериализовать все HTTP-01 выдачи/renewal с существующим production manage renew
одним /home/yurik/fido/ffido/maintenance.lock, от согласованного владельца. Одного
разнесения cron по минутам недостаточно. Сейчас manage renew обслуживает только
v1002682.hosted-by-vdsina.com и перезапускает только ffido. Новый домен/порт gateway
не получит автоматическое продление от этого hook. Для отдельного production
lineage нужно отдельное задание (например 03:43/15:43 MSK) под тем же lock с retry
при занятости. Тестовые ручные ACME-вызовы также должны соблюдать этот lock.

Hook после действительного renewal обязан проверить SAN, срок, fullchain и пару
ключ/сертификат, атомарно установить файлы в certs/public, обеспечить права чтения
UID/GID gateway (ключ не world-readable), валидировать Envoy, перезапустить только
ffido-miniapp-main-gateway и новым TLS-соединением проверить serial/expiry.
При неуспехе вернуть прежние файлы и поднять прежний gateway; отправить оператору
ошибку. Доступ к ACME account/key только владельцу. На будущем этапе обязательны
renew --dry-run и проверка применения отдельного сертификата; сейчас не выполнялись.

Изменение CA backend (сейчас ISRG Root X1) требует обновления trust bundle и
проверки TLS upstream. Не принимать новый issuer отключением проверки.

идентичность точных исходников Mini App и всех включаемых изменений. Локальный
QA-образ sha256:52bc609243d4b1bc01fb852f5553207e96c0333ec0453656796b3939b5ad3190
имеет label revision 3926989e518efb9607df739f7f3c1288c7a0b31e и version
telegram-mini-app-qa: **не считать его проверенным production-релизом только по

изменения; нужен review manifest исходников/образа и повторяемая сборка. Registry
release либо отдельный локальный pin — отдельный выбор перед применением; текущая

На изолированной копии репрезентативных данных проверить миграцию 11→12,

До окна обслуживания скачать/собрать кандидат, worker и gateway, сохранить старые
образы и убедиться в их доступности для отката. Не запускать кандидат с production

### 2. Согласовать окно и заблокировать автоматизацию

Записать baseline: running image IDs/RepoDigests, Compose config, crontab,
update-state, BUILD identity, hashes, очереди/флаги и service status без секретов.
Удерживать maintenance.lock в течение изменения; остановить новые управляющие
cron-задания/ручные операции, дождаться уже начатых. Не останавливать весь cron
хоста. До возобновления обновлений закрепить выбранный образ и совместимый worker
в каноническом updater/Compose state. Простого временного override недостаточно:
следующий manage update/rebuild_worker может вернуть stable image. Нужен явный
pause автоматического apply на весь период candidate, с сохранением причины и
порядка восстановления (не подделывать marker совместимости JAM). Подготовить
это изменение maintenance-автоматизации отдельно, до production startup.

Остановить ffido-tosser (дать активному journaled циклу завершиться), fido/BinkD,
jamnntpd и ffido. Проверить отсутствие остальных JAM/SQLite-писателей и открытых
HPT-процессов, получить coordination lock после остановки. Если stop/lock неуспешны,
прекратить процедуру. Нельзя продолжать с частичным снимком.

### 3. Единый backup и проверка восстановления

Текущий manage.sh backup не использовать как единственный cutover-примитив:
его snapshot() снова запускает fido/jamnntpd, а backup затем backend/tosser.
Кроме того, набор архива не охватывает весь updater/transport state. Подготовить
контролируемую процедуру остановленного снимка под maintenance и coordination
lock, не вызывая эти auto-start ветки.

В закрытый каталог 0700 включить согласованно:

- JAM целиком msgbase, включая .jhr/.jdt/.jdx/.jlr и mailbox поинтов;
- ffido/state целиком: metadata.db, существующие WAL/SHM, session.key, uploads и
  журналы операций; не копировать только основной SQLite-файл работающего WAL;
- f/ inbound/outbound/tmp, spool (включая intab/outtab), dupebase, flags, ffido/fileboxes и прочие реальные
  spool/filebox пути после проверки HPT/BinkD includes; не архивировать только JAM;
- hpt.cfg, links.cfg, owner.cfg, route.cfg, areas.cfg, binkd.cfg, t.sh, .env,
  docker-compose.yaml, FFIDO-README.md и все их фактические includes;
- ffido/config.json, tls, acme/config, credentials, ops, updater и updates,
  deployed-identity.json, update-transaction.json и активные локальные overlay/
  verification manifests, на которые ссылается конфигурация;
- crontab, firewall baseline, сведения о старых образах и их отдельные docker-save
  архивы (без включения backups в саму backup), новый gateway/ACME-state если уже создан.

Сохранять uid/gid/modes/symlinks, архивы с ключами 0600. Рассчитать свободное место
с учётом полного архива, распакованной проверочной копии и сохранения обеих версий
образов; 27 GiB сейчас — наблюдение, не доказательство достаточности будущего окна.
Проверить gzip/tar, SHA-256, обязательные файлы и пробное восстановление в отдельную
закрытую директорию; SQLite quick_check и schema=11 на восстановленной копии.
Не выполнять тестовый startup над основными путями. Закрепить копию приватным
JSON-манифестом со ссылкой из ffido/ops: ротация сохраняет referenced и специальные
копии; проверить её dry-run. Отдельная защищённая off-host копия желательна до
применения, её перенос потребует разрешённого места хранения.

### 4. Обновить при закрытом внешнем gateway

На этом этапе источники писателей остаются остановленными, :9443 ещё закрыт,
каталог не опубликован. После завершения снимка освободить coordination lock перед
startup backend: он должен получать его сам; maintenance lock и запрет прочих
писателей сохраняются. Слить auth-фрагмент в актуальный config, сохранив все
рабочие path mappings, encoding corrections, point_mail и session key. Применить
проверенный pinned backend override **последним** после имеющихся Compose-файлов;
backend и предварительно построенный tosser выбирают согласованные образы.
Запустить сначала только backend, проверить TLS readiness, schema=12, capabilities
с bot_id 9052986615 и отсутствие startup/migration ошибок. Не запускать два backend
с одной SQLite/JAM и не подменять рабочие данные тестовыми.

Собрать effective configuration/identity, синхронизировать .env,
deployed-identity.json и managed state для worker без запуска mail cycle.
Функция rebuild_worker сейчас запускает tosser сама: не вызывать её до завершения
окна проверки. Проверить worker identity на копии. Сначала проверить на закрытом
endpoint разрешённые чтения/вход существующего профиля; пароль только приватно.
Создание Telegram-привязки — отдельное подтверждённое действие, не автоматический
перенос тестовых SQLite/bindings. Бот и bot_id сохраняются, BotFather менять не нужно.

Подготовить отдельный сертификат, runtime gateway config и права mounts, выполнить
Envoy --mode validate, затем запустить gateway. Пока firewall закрыт, проверить с
самого хоста SNI/SAN/chain, TLS upstream, binary/text gRPC-Web, allowed-origin
preflight, denial foreign/null/missing origin и unauthenticated RPC. Обычный
HTTP GET / не является gRPC health-check. Не выводить initData/пароли/токены.

### 5. Открыть endpoint и добавить каталог последним

Только после отдельного разрешения изменить persistent и активный firewall для
9443; проверить извне HTTPS и gRPC-Web/CORS. Не менять политикам Docker/NAT другие
сервисы. Сохранить и проверить тестовый :8443. Затем отдельно опубликовать запись
amster2-main через действующий Pages workflow/ветку с review каталога; сохранить
предыдущий Pages commit для отката. Не заменять ID или endpoint тестового узла:
клиент должен добавить новый узел вручную, тестовые сессии не переносятся.
Публикация каталога — отдельный момент открытия production для пользователей.

Проверить рабочий HPT-вход, Telegram bind после согласия и переоткрытие, права и
чтение личного ящика без отправки. Авторизация развёртывания сама по себе не
разрешает тестовую отправку в рабочую FidoNet. Любое пробное письмо требует
отдельного согласования текста/адресата; manual cycle/pack/poll ради проверки не запускать.

Когда принято решение продолжать обычную работу узла, возобновить прежние
fido/jamnntpd/tosser и планировщики, проверить identity и обычную health/queue
динамику без принудительного FTN-экспорта. Зафиксировать момент возобновления
писателей: после него простой восстановительный rollback к старому снимку запрещён.
Android/iOS остаются непроверенными по решению пользователя; не объявлять полную
платформенную готовность. Отслеживать expiry обоих gateway, readiness и ошибки auth.

## Откат

Триггеры: ошибки миграции/SQLite, ACL/изоляции ящиков, несовпадение worker identity,
нестабильная readiness, TLS/CORS или повторяющиеся сбои Telegram-входа.

1. **Только gateway/каталог, рабочие данные уже используются.** Остановить новый
   gateway/закрыть его 9443 и вернуть предыдущий Pages-каталог/commit, сохранив
   тестовую запись. Cached каталог может жить у клиентов: его удаления недостаточно
   для отзыва доступа. Отозвать выданные production Web/Telegram-сессии и отключить
   Telegram capability штатным механизмом, если нужен именно отзыв, сохранив
   данные и новый совместимый backend. Не восстанавливать старый snapshot.
2. **Backend ещё не принимал новые рабочие записи, writers не возобновлялись.**
   Остановить новый gateway и backend, сохранить приватный аварийный снимок schema12
   для расследования. Под теми же locks восстановить **единый** согласованный снимок
   schema11 + JAM + spool/state/config/keys, прежние Compose/.env/updater identity и
   старые backend/tosser image pins. Проверить владельцев, permissions, lock-файлы,
   SQLite quick_check; освободить coordination lock перед startup backend и проверить
   readiness, затем возвращать writers/cron. Не накладывать
   старые файлы поверх новых WAL/SHM: восстановить каталог целиком, сохранив новую
   версию отдельно. Один старый image против schema12 — недопустимый откат.
3. **После новых писем/FTN-обмена/пользовательских изменений.** Зафиксировать
   текущее состояние и остановить проблемный доступ; согласовать forward-fix или
   адресную сверку изменений. Восстановление всей старой JAM/SQLite/spool может
   потерять принятую почту и повторно отправить уже экспортированное. Автоматический
   restore и replay здесь запрещены. Старый native endpoint можно сохранить на
   исправленном совместимом backend, отдельно отключив Mini App.

После любого отката восстановить согласованные cron/update pin и renewal hooks,
проверить как старый native TLS :8080, так и независимый тест :8443. Не удалять
pre-upgrade и аварийную backup до завершения разбора и принятого срока хранения.

## Проверки этой подготовки и оставшиеся условия

Фактически выполнены: SSH-обследование только на чтение, генерация JSON текущим
wrapper, структурные проверки listener/upstream/CORS/catalog и локальная проверка
Envoy на временных сертификатах (см. validation.md). Базы и пользовательские
данные не копировались. Восстановление, миграция production-копии, новый образ/
worker, ACME issuance/renewal, запуск gateway, открытие 9443 и публикация каталога
**не выполнялись**. Эти этапы требуют следующего отдельного разрешения.

До применения требуется согласовать точный immutable кандидат и окно простоя;
профиль для production bind выбирается пользователем, без выдачи новых поинтов.
Рабочий код приложения в этой подготовке не изменялся.

Штатное восстановление ящиков и отдельный rollback v1.0.27 с restore-support описаны
в [отчёте safe-mailbox-restore](safe-mailbox-restore-20261118.md). Он отдельно фиксирует
новую репетицию; прежний исторический отчёт с ручной диагностической перепривязкой
не является доказательством штатного восстановления.
