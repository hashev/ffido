## Найденные препятствия для рабочего обновления

### 1. Maintenance backup не содержит всех зависимостей

В архиве отсутствовали `spool/outkoi8alt` и `spool/outaltkoi8`, на которые ссылаются
HPT intab/outtab. Оба прежний и новый HPT helper отказывались читать конфигурацию
до добавления этих файлов. Отсутствовал также manifest по
ftn.jam_message_encoding_corrections_path. Эти **статические** зависимости скопированы
с действующего узла только в закрытую копию и хешированы отдельно в
copy-preparation.json; журналы и сообщения с текущего узла не подмешивались.
Для sandbox также созданы пустые logs/dupebase/nodelist.

Следующий cutover-backup должен включать spool/таблицы перекодировки и все
зависимости активной конфигурации, включая verification/corrections manifest.
Существующие серверные backup-скрипты в этой задаче не исправлялись.

### 2. Привязки персональных ящиков зависят от inode

Mailbox identity включает st_dev/st_ino для .jhr/.jdt/.jdx плюс поля JAM header.
Распаковка меняет inode, а SQLite хранит прежние generation/files. Защитная
проверка backend корректно отклоняет такое несоответствие; она не должна отключаться.

Нужна отдельная штатная, проверяемая процедура восстановления: остановленные
писатели и locks, manifest доверенного снимка, проверка адресов/путей/всех JAM
компонентов/хешей/схемы, отказ при hardlink/symlink/подмене/чужом ящике, атомарное
обновление только разрешённой физической идентичности с сохранением исходной БД.
Отдельно проверить ссылки generation в личных отметках/истории и незавершённых
операциях: равенство строк не доказывает семантику их восстановления на новых inode.

В существующем provisioning нет режима «доверять распакованной копии»: при
несовпадении он отказывает. Диагностический SQL из build/ не является такой
процедурой и не должен применяться к production. До её реализации/проверки
**production_rollback_ready=false**; развёртывание основного узла не выполнять.
