### DEF-001 — управление закладками недоступно

- **Сборка/платформа:** указаны в паспорте, macOS.
- **Предусловия:** вход A, открыты главная, конференция или раздел «Закладки».
- **Шаги:** найти действие добавления конференции; открыть закладки; найти действие удаления.
- **Ожидалось:** пользователь может добавить и удалить закладку.
- **Факт:** есть экран просмотра, но действия управления отсутствуют. По исходному коду `toggleBookmark` определён только в репозитории и не вызывается интерфейсом.
- **Повторяемость:** во всех просмотренных экранах; API add/list/remove отдельно работает, состояние A/B изолировано.
- **Обходной путь:** штатного GUI-способа не найдено. RPC-проверка не считается пользовательским обходным путём.
- **Доказательства:** `evidence/gui-notes.md`, поля bookmark_* в `evidence/rpc-assertions.json`.

### DEF-002 — история не обновляется при переходе после чтения

1. Запустить новый клиент, войти A.
2. Прочитать несколько сообщений NINO.046.LOCAL.
3. Вернуться и открыть «История».
4. Нажать кнопку обновления истории.

**Ожидалось:** уже при переходе видна прочитанная конференция. **Факт:** сначала «История просмотров пуста», после обновления появляется NINO.046.LOCAL. RPC подтверждает существование записи. Повторное чтение не создаёт дублей на сервере. Дополнительно главная показывает старый unread до обновления; это наблюдение, а не отдельно исследованный дефект.

**Повторяемость:** один полный цикл в свежей сессии; после повторного входа история загружается корректно. **Обходной путь:** обновить вручную. **Доказательства:** `evidence/gui-notes.md`, `snapshot-a.json`, `rpc-assertions.json`.

### DEF-003 — адрес получателя ответа пропадает после HPT

1. В NINO.046.LOCAL открыть исходное сообщение #104 «С американским гражданством все понятно» от Dmitry Protasoff.
2. От A сохранить обычный ответ #105 и «Ответить всем» #108.
3. Открыть обычный ответ: «К: Dmitry Protasoff <2:5001/100.1>»; адрес в форме обоих ответов тот же.
4. Запустить HPT через `scripts/run_hpt.py` с **тестовыми** config.json / hpt-copy.cfg, `scan -w -a nino.046.local`.
5. Повторно прочитать ответы, включая #108 в GUI.

**Ожидалось:** явно сохранённый адрес получателя остаётся доступен после совместной работы с HPT. **Факт:** у обоих экспортированных ответов RPC возвращает пустой `to_address`, GUI — «К: Dmitry Protasoff (адрес не указан)». `from_address`, имя, тема, тело и `in_reply_to` сохранились. Сообщение #116 с явным адресом, созданное после scan и ещё не экспортированное, показывает адрес корректно.

**Повторяемость:** 2 экспортированных ответа из 2. Причина удаления поля внутри HPT/SMAPI ещё не установлена; сам факт до/после подтверждён. Это проблема сохранения метаданных при совместной работе, а не доказанное повреждение всего JAM-файла. После обнаружения дополнительные отправки прекращены.

**Приоритет:** высокий. **Обходной путь:** надёжного не подтверждено; не выводить адрес получателя из MSGID автора. **Доказательства:** GUI-наблюдения до/после в `evidence/gui-notes.md`; `evidence/snapshot-a.json`, `evidence/rpc-assertions.json` (`reply_and_reply_all_address: false`); `hpt/logs/hpt.log`.

### Подтверждение исправления DEF-003

Установленная SMAPI в `ConvertXmsgToJamHdr` создаёт OADDRESS/DADDRESS только для не-echo. Когда HPT обновляет эхописьмо, эти поля исчезают. FFIDO теперь берёт отсутствующий адрес из durable `header_append` подтверждённой операции при точном совпадении **conference + generation + message_number + FTN MsgID**. Адрес JAM остаётся приоритетным. Неизвестные/незавершённые записи, другая идентичность и неправильные адреса не используются. Повреждённый журнал даёт контролируемую ошибку. Схема SQLite остаётся v4, миграция не требуется.

| Запись нового QA | Адрес API после HPT и restart | DADDRESS в JAM после HPT |
|---|---|---|
| #105, ответ старому автору | `2:5001/100.1` | Отсутствует |
| #106, отдельный явный получатель | `2:5015/120` | Отсутствует |
| #107, ответ во время HPT | `2:5015/120.1` | Отсутствует |

Старые #105/#108 из первого QA-прогона также восстановили `2:5001/100.1`; хеши всех 8 JAM-файлов этого тестового каталога при чтении не изменились. Утраченное DADDRESS не переписывается в файлы. После pack/замены файла/перенумерации резервное значение автоматически на новую идентичность не переносится; такой сценарий остаётся отдельной проверкой.
