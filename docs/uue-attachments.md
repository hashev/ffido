# UUE-вложения

## Совместимость кодека

Реализовано в изменении `uue-file-attachments`: отправка в эхи и Netmail, сборка частей, сохранение и предпросмотр изображений.

Поддерживается классический UUE: `begin <mode> <filename>`, строки до 45 исходных байтов, нулевое значение space/backtick, нулевая строка и `end`. CR, LF и CRLF допустимы. Исходные сообщения не переписываются. Бинарные байты не проходят текстовую нормализацию CP866/Н → H.

| Пример | Проверка |
|---|---|
| GoldED-подобный одиночный блок | Все 256 значений байта; независимый CPython binascii |
| Классический поток в нескольких письмах `[n/N]` | Явно упорядоченные части, один begin/end |
| `section <число> end…` и `sum -r/size <число>/<число> section…` | Только известные разделители вне полезных строк; это не проверка опубликованной суммы |
| Неизвестный split, MIME/base64, XXencode, yEnc | Не декодируются как классический UUE |

Образцы в `apps/backend/tests/fixtures/uue/` сгенерированы независимо от FFIDO посредством CPython `binascii`, без чужой переписки. Это синтетические совместимые образцы, не запись реального сеанса GoldED. Тест `UueFixtureOracle` проверяет их отдельно. Сборщик кодека принимает уже выбранные и упорядоченные тела; авторизация и идентичность передачи проверяются сервисом, не этим низкоуровневым кодеком.

Исследованные первичные источники: [GoldED editor](https://github.com/golded-plus/golded-plus/blob/master/golded3/geedit2.cpp), [encoder](https://github.com/golded-plus/golded-plus/blob/master/goldlib/uulib/uuencode.cpp), [section decoder](https://github.com/golded-plus/golded-plus/blob/master/goldlib/uulib/uunconc.cpp). Не заявляется универсальная совместимость со всеми историческими multipart-диалектами.

Структурная корректность старого UUE без размера/хеша не доказывает целостность файла. Неверные длины, алфавит, padding и отсутствующее окончание не исправляются автоматически. Ошибочный блок остаётся доступен как исходный текст, а не как подтверждённый файл.

## FFIDO-UUE v1

Добавочный FTN-kludge без SOH и перевода строки:

```text
FFIDO-UUE: 1 <transfer-id> <part>/<total> <decoded-size> <sha256> <filename>
```

`transfer-id` — 32 строчных hex-символа, `sha256` — 64. Целые десятичные поля без ведущих нулей (кроме размера 0); номера от 1 до total, по умолчанию не более 128 частей. Размер — размер исходного файла, по умолчанию до 1048576 байт. SHA-256 относится ко всему исходному файлу, не к UUE-тексту. Все части одной передачи повторяют эти значения; идентичность не даёт авторизации без проверки области/источника/назначения.

Имя: безопасное UTF-8, percent-encoding каждого байта кроме ASCII букв, цифр, `.`, `-`, `_`; hex escape строчные, канонические (например, пробел `%20`, знак процента `%25`). Избыточные escapes для разрешённых ASCII отклоняются. Сериализованная строка не более 1024 байт. Для `begin` используется отдельное безопасное ASCII-имя. Такой ASCII wire не меняется при CP866 и замене Н → H. Неизвестная версия не интерпретируется как v1.

Системное сохранение использует очищенное имя без каталогов, управляющих/зарезервированных символов и специальных имён Windows. Из UUE не применяются права доступа. Длина очищенного имени ограничена с сохранением границы UTF-8. Контрольная сумма расширения проверяет совпадение байтов, но не является цифровой подписью отправителя.

## Добавочный API

В `contracts/ffido/v1/ffido.proto` добавлены `GetUueLimits`, `SearchUueParts`, `AssembleUue`, `GetUueChunk`, `UploadUueChunk`, `CommitUue`, `GetUueSendStatus`. Поиск возвращает поколение и ограниченный cursor по номеру сообщения; source reference включает обычный непрозрачный ID сообщения и индекс блока. Порции bytes имеют offset и серверный предел, не публичный URL. Существующие поля/номера и CreateMessage не менялись.

Контракт, серверные обработчики и клиентский транспорт подключены. При UNIMPLEMENTED от старого сервера клиент отключает UUE-возможности без потери обычного чтения и авторизации. Проверка совместимости есть в клиентских RPC-тестах.

## Уточнение правила старого multipart

Тест `Uue.LegacyNumberingCannotProveTransferMembership` воспроизводит смешивание: две передачи одного источника с одинаковым `same.bin` и темами `[1/2]`, `[2/2]`; получены первая часть первой передачи и вторая часть второй. Результат структурно корректен, но не совпадает ни с одним исходным файлом. Нумерация/один begin/end без идентификатора или суммы недостаточны для доказательства принадлежности. По уточнённому выбору пользователя нумерованный multipart собирается автоматически по отправителю, основе темы и общему числу частей в одной области/поколении, с совпадающими адресатом и направлением Netmail. Карточка постоянно показывает «Контрольной суммы нет; возможно смешивание частей разных передач». Это принятый риск, а не подтверждение целостности; ручной выбор состава остаётся доступен. Передачи FFIDO-UUE с идентификатором и SHA-256 собираются автоматически.

## Серверное чтение и кеш

`SearchUueParts` сканирует до 100 сообщений и примерно 4 МиБ текстов за запрос, возвращает следующий номер и поколение. Индекс производный, в памяти: до 512 записей с TTL 5 минут. Каталог конференций не вызывает UUE-декодирование. Поиск и сборка используют чтение без отметки прочитанности, истории и изменения позиции.

`AssembleUue` проверяет одну область, FTN-источник, адресата и направление, ссылки на блоки. Части FFIDO сортируются по номеру; одинаковые дубли допустимы, разные байты одного номера — конфликт. При `explicit_order=false` старые нумерованные части проверяются по группе и сортируются по номеру; готовый результат имеет `checksum_verified=false` и диагностическое предупреждение о возможном смешивании. `explicit_order=true` сохраняет выбранный вручную порядок и позволяет собрать ненумерованные части; FFIDO-UUE всегда проверяет метаданные и хеш. Неполнота, конфликт и повреждение возвращаются отдельными состояниями без готового файла.

Кеш декодированных файлов закрыт для другого user id: до 8 МиБ на пользователя, 64 МиБ на сервер и 256 файлов, TTL 5 минут. Каждый `GetUueChunk` повторно проверяет права и отпечаток всех исходных сообщений; изменение/удаление части сбрасывает кеш. Порция не более 64 КиБ. После перезапуска или истечения TTL клиент повторяет поиск и сборку из доступных JAM, без зависимости от другого устройства.

## Настройка и устойчивая отправка

Секция `uue` в `apps/backend/config.example.json` содержит серверные лимиты. Значения по умолчанию: файл 1048576 байт; тело части 32768; до 128 частей; порция 65536; квота staging/кеша 8 МиБ на пользователя и 64 МиБ суммарно; незавершённая загрузка хранится сутки. Ограничения проверяются совместно; жёсткие пределы: файл 16 МиБ, 1024 части, тело части 256 КиБ, порция 64 КиБ. Для увеличения файла нужно согласованно увеличить число частей и квоты. Изображения: 16 млн пикселей, 8192 по стороне по умолчанию.

SQLite schema 9 добавляет `uue_uploads`. Staging исходных байтов и immutable manifest хранятся в той же durable SQLite, без новых произвольных файловых путей. Производный индекс чтения остаётся восстанавливаемым кешем в памяти. Миграция с schema 8 сохраняет профили, прочитанность и историю. Понижение версии автоматически не выполняется: перед обновлением нужна обычная резервная копия метаданных; откат — совместимый backend либо резервная копия после остановки отправок. JAM не мигрирует.

Повтор порции с теми же offset/bytes допустим, конфликтующие байты или метаданные — ошибка. Commit сначала проверяет весь файл, текст, адреса, сериализацию CP866 и размеры частей; затем устойчиво сохраняет MsgID, operation id, поколение, отправителя, адресата и тела всех частей. Каждый append использует существующий восстановимый JAM writer и HPT coordination lock. Частичный результат имеет `partial`, число подтверждённых частей и команду повторить ту же операцию; локальный `completed` не обещает доставку в FTN. Изменение исходного запроса с тем же ключом — конфликт, даже если Н/H после нормализации совпадут. Уже опубликованные части не удаляются автоматически.

Проверки восстановления прерывают Write/Sync на каждом этапе первого и второго append, затем продолжают передачу новым экземпляром сервиса. Дополнительно проверены потерянный успешный ответ, отзыв доступа после первой части, изменение поколения и блокировка HPT. Рабочий HPT-конфиг и реальные JAM для этих тестов не используются.

## Как отправить и получить файл

1. Откройте доступную для записи эху либо Netmail и нажмите «Новое сообщение». В Netmail заполните имя и полный FTN-адрес получателя.
2. Заполните тему и текст, нажмите «Прикрепить файл UUE». Выберите один файл: редактор покажет имя, размер и приблизительное число писем. Кнопка удаления убирает файл до начала отправки, текст сохраняется.
3. Нажмите «Отправить». Сервер рассчитывает окончательное число частей с учётом оформления. Текст размещается в первой части; слишком длинный текст или превышение лимитов отклоняются до первой публикации.
4. При частичном результате или потерянном подтверждении используйте «Повторить отправку» в том же редакторе. Файл, текст и ключ операции фиксируются до результата; не создавайте новую отправку для продолжения старой. Закрытый редактор пока не восстанавливает незавершённый черновик автоматически.
5. «Сообщение сохранено локально» означает устойчивую запись всех частей на сервере. Доставку и маршрутизацию продолжает обычный HPT, это сообщение не подтверждает получение адресатом.

При чтении карточка располагается на месте UUE-блока. FFIDO-UUE собирается автоматически с проверкой SHA-256. Старый нумерованный multipart также собирается автоматически, но с постоянным предупреждением о возможном смешивании. Если часть пришла позже, нажмите «Найти части». Чтобы исправить состав готовой или неполной группы либо собрать ненумерованные части, нажмите «Выбрать части», проверьте флажки и порядок («Выше»/«Ниже»), затем подтвердите ручную сборку. Структурно корректный старый файл без хеша имеет соответствующую пометку. Недостающие части, конфликт дублей или повреждение не дают сохранить неполный файл. «Показать исходный UUE» возвращает исходный текст без изменения JAM.

«Сохранить файл» каждый раз проверяет доступ и получает байты с сервера заново. Desktop использует системный диалог, Android — создание документа, iOS — экспорт документа, Web — браузерную загрузку. Отмена не показывается как успех. Web подтверждает только передачу браузеру: завершение записи на диск ему недоступно. Приложение не запускает сохранённый файл и не распаковывает архивы.

PNG/JPEG/GIF/WebP определяются по содержимому, включая файлы с расширением `.bin`. Предпросмотр ограничен размерами изображения и показывает только первый кадр GIF/WebP. Если изображение повреждено либо слишком велико, остаётся карточка сохранения. Обычный ответ содержит видимую редактируемую цитату; бинарный файл без нового выбора не прикрепляется. Пересылка переносит видимый текст, без скрытого повторного вложения.

Кнопки снабжены подписями/tooltip, поддерживают фокус и отключаются на время операции. Карточки проверены на ширине 390 пикселей. При смене сессии содержимое карточки очищается; другой клиент того же аккаунта может заново найти части на сервере. Поиск частей не меняет их прочитанность и историю.

## Воспроизводимые проверки

Из корня репозитория после сборки backend:

```sh
python3 scripts/check_uue.py --hpt /Users/yurik/ftn/usr/bin/hpt
```

Путь указывает только на бинарник HPT. Скрипт создаёт новый временный каталог, собственные HPT-конфиги, TLS и JAM двух поинтов с синтетическими адресами `2:1/2.1`/`.2`; рабочий `/Users/yurik/ftn` не используется как конфигурация или база. Проверяются отправка multipart в эху/Netmail, HPT scan/toss/pack, входящий внешний FFIDO-UUE и старый multipart без метаданных (бинарный файл и изображение, приход частей в обратном порядке), независимый `binascii`, изоляция другого поинта и повторная сборка новым клиентом без локального кеша. `--keep` оставляет только временный стенд и печатает его расположение; `tool/uue_preview.dart` — отдельная QA-точка входа для этого стенда, не обычный запуск приложения.

Приёмка macOS 19.10.2026 на отдельном временном стенде:

- Два независимых экземпляра с профилями `uue1`/`uue2`; синтетическое PNG `.bin` 13 140 байт отправлено в 6 письмах, отображено внутри письма обоими клиентами и сохранено системным диалогом. SHA-256 сохранённой копии совпал.
- Ответ вторым профилем создал одно обычное письмо с цитатой без нового FFIDO-UUE вложения.
- Бинарный файл 51 200 байт со всеми значениями байта отправлен в Netmail в 20 частях. Временный сервер аварийно остановлен после подтверждения первой части, затем запущен заново. Повтор той же операции завершил ровно 20 разных частей без дублей.
- После цикла HPT второй поинт получил личную передачу, заново собрал и сохранил файл. Сохранённые байты совпали, SHA-256 `747ffb66d9569fce70d8e9910230ed6cca8d52100286d9e86aa03ebdbb4f69d1`.
- Отрицательный доступ чужого поинта к личному attachment проверен API и серверными тестами; общая эха доступна обоим по правилам линков.

Release-сборки macOS, Android и Web проверены; нативные gRPC и браузерный gRPC-Web прошли общий smoke с UUE chunk/assembly/upload. Android export проверен сборкой и adapter-тестами, без физического устройства. Сборка iOS недоступна на этом Mac: отсутствует требуемый iOS SDK 26.5; системный export picker iOS не проверен в runtime. Windows/Linux на этом хосте не собирались. Эти ограничения не являются результатами успешного платформенного теста.

Итоговая проверка реализации: 333/333 CTest с доступным HPT, 227 Flutter-тестов (2 существующих пропуска), `flutter analyze` без замечаний, Dart format, clang-format/clang-tidy и проверка генерации protobuf прошли. OpenSpec прошёл строгую валидацию.

Уточнение автоматической legacy-сборки проверено 19.10.2026: HPT доставил нумерованные части без FFIDO-UUE в обратном порядке, новый клиент восстановил бинарный файл и PNG без подтверждения состава. В macOS открыта часть 8/8 изображения 13 140 байт: preview появился автоматически, предупреждение осталось видимым; ручной состав доступен и после сборки. Системное сохранение дало побайтное совпадение с исходником. Backend-тест воспроизводит структурно корректное смешивание двух передач одного отправителя: результат доступен с предупреждением и `checksum_verified=false`; пропуски и конфликтующие дубли по-прежнему блокируют готовность. Проверка SHA-256 для FFIDO-UUE не ослаблена.
