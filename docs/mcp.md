# FFIDO MCP

`ffido-mcp` — локальный MCP-сервер для Linux/macOS. MCP-клиент запускает его как
stdio-процесс, а он обращается к существующему backend FFIDO по TLS gRPC. Доступ к
JAM, HPT и metadata SQLite остаётся у backend. Flutter-клиент работает независимо.
Версия протокола MCP — 2025-11-25; объявлены tools и prompts.

## Подключение и авторизация

Установите серверный пакет FFIDO с `ffido-mcp` и backend с архивными RPC и
PreviewMessage. MCP-процесс можно запускать на другой машине, доступной к backend.
Адрес в конфиге — gRPC authority `host:port`, без `https://` и URL-пути.
Сертификат должен быть доверенным и содержать имя сервера в SAN. Отключения TLS
или подмены проверяемого имени нет. Для собственного CA можно указать tls_ca_file.

Создайте каталог состояния и конфиг, например:

```sh
mkdir -m 700 "$HOME/.config/ffido-mcp"
mkdir -m 700 "$HOME/.config/ffido-mcp/state"
```

`~/.config/ffido-mcp/config.json`:

```json
{
  "endpoint": "fido.example.org:50051",
  "session_file": "state/session.json",
  "state_dir": "state",
  "read_area_ids": ["RU.TEST", "RU.FIDONET"],
  "post_area_ids": ["RU.TEST"]
}
```

ID должны точно совпадать с идентификаторами областей backend. Для приватных
областей используйте их непрозрачные ID. Относительные пути разрешаются от конфига.
Пустой или отсутствующий список ничего не разрешает, wildcard не поддерживается.
Добавление области не предоставляет прав, которых нет у серверного профиля.

В терминале выполните:

```sh
/opt/ffido/bin/ffido-mcp login "$HOME/.config/ffido-mcp/config.json"
```

Введите имя, FTN-адрес и пароль HPT; пароль вводится без эха и не сохраняется.
Создаётся отдельная FFIDO-сессия в session_file (0600); каталог секрета и state_dir
должны принадлежать текущему пользователю и иметь права 0700. Символьные ссылки на
конечные секретные файлы и каталоги отклоняются. Токен не передавайте в аргументах
инструментов или командной строке. После нового входа перезапустите MCP-процесс.
Истечение/отзыв сессии требует повторного локального входа. Logout Flutter-клиента
не вызывается.

Пример stdio-конфигурации MCP-клиента (формат внешнего клиента может отличаться):

```json
{
  "mcpServers": {
    "ffido": {
      "command": "/opt/ffido/bin/ffido-mcp",
      "args": ["/home/user/.config/ffido-mcp/config.json"]
    }
  }
}
```

Замените пути на абсолютные пути своей машины. stdout содержит только JSON-RPC,
диагностика идёт в stderr без содержимого переписки и секретов. Нужен MCP-клиент,
который умеет показывать результаты инструментов и запрашивать разрешение на send.

## Инструменты

| Инструмент | Назначение и основные аргументы |
| --- | --- |
| ffido_list_areas | Каталог разрешённых для чтения областей, query/offset/limit |
| ffido_search_messages | area_ids, query, scope, from/to, sort, limit, cursor |
| ffido_get_message | reference, body_offset/body_limit, reveal |
| ffido_get_thread | reference, offset/limit; заголовки и реальные reply-связи |
| ffido_get_message_technical_data | reference; JAM-атрибуты, CHRS и кодировка, исходные bytes в base64 |
| ffido_prepare_message | area_id, subject, body, to_name/to_address, in_reply_to |
| ffido_send_message | Только draft_id и confirm=true после просмотра и разрешения |

Результаты находятся в structuredContent.data и эквивалентном текстовом JSON.
References имеют вид `{"conference_id":"RU.TEST","message_id":"generation#42"}`.
MSGID не заменяет reference. `ffido://message/...` — идентификатор первоисточника
для цитирования, а не обещание работающего web/deep link или MCP resource.

Чтение, поиск и цепочки не меняют прочитанность, историю, позицию или JAM.
Персональные фильтры применяются автоматически. Свёрнутый результат не содержит
тела или snippets; reveal=true явно раскрывает только выбранное письмо без отметки
прочитанности и без отключения фильтра. Цепочка возвращает заголовки; полные тексты
получаются отдельно.

Поиск буквальный, с правилами регистра ASCII/русского, Ё/ё и CP866-подмен FFIDO.
Для вариантов формулировки нужны отдельные запросы; векторного индекса и встроенной
LLM нет. Пустой query допустим при двух границах периода [from,to), заданных в целых
UTC секундах в RFC3339. Для смены запроса начинайте поиск без cursor.

Всегда проверяйте complete. Пустая страница с incomplete_reason=scan_budget означает,
что обход ещё продолжается. Повторяйте прежние параметры с cursor=next_cursor.
Изменение JAM, фильтров или перезапуск backend может инвалидировать cursor: начните
новый поиск и обозначьте изменение/неполноту выборки. Не называйте частичную выборку
полным архивом. Блоки тела читаются по next_offset до complete=true; offsets заданы
в UTF-8 байтах, body_limit — 1–65536. Свернутое complete=true означает завершённый
ответ заголовков, не раскрытое тело.

Лимиты: 1 MiB на входную JSON-строку, 512 KiB на ответ MCP, четыре одновременно
выполняемых tools/call. Для `ffido_list_areas` gRPC-вызовы имеют общий бюджет
30 секунд, включая проверку сессии и получение всех разрешённых областей перед
фильтрацией и pagination. Для остальных инструментов общий бюджет — пять секунд.
Каждый RPC получает оставшийся бюджет; отмена не требует ожидания deadline.
Если сериализованный ответ слишком велик, уменьшите страницу или body_limit;
усечение данных не имитируется. Подробные лимиты поисковых cursor — в backend README.
Ошибки возвращаются как isError=true с кодом и retryable. GRPC_12 означает, что
backend нужно обновить; подмены архивных RPC обычным чтением нет. При потере
состояния продолжения требуется новый поиск.

## Полезные сценарии

- «Найди, как в RU.FIDONET решали проблему TLS»: поиск TLS → чтение точных писем →
  цепочки. В ответе укажите авторов, даты, references и источники утверждений.
- «Сделай дайджест RU.TEST за октябрь 2026»: query="", from="2026-10-01T00:00:00Z",
  to="2026-11-01T00:00:00Z", sort="date_asc". Дочитайте страницы и выбранные тела,
  явно обозначьте покрытие. Период здесь UTC, не локальное время пользователя.
- «Объясни, почему письмо выпало из ветки»: технические данные и цепочка позволяют
  сравнить MSGID/REPLY и локальные связи. Не достраивайте родителя по одной теме.
- «Подготовь ответ участнику»: передайте in_reply_to как reference в той же области.
  Для netmail нужны конкретные имя/FTN-адрес; правила ответов и отправитель
  определяются backend. Кросспостинг и UUE через MCP не поддерживаются.

Доступны шаблоны research_topic(topic, area_ids), digest_period(area_ids, from, to)
и explain_thread(reference). Их аргументы — строки; они описывают план исследования,
сами не читают базу, не вызывают LLM и ничего не отправляют.

## Просмотр, подтверждение и повтор отправки

prepare возвращает точные автора, адресата, публичность, итоговые текст/тему после
FTN-преобразований, кодировку и draft_id. До отправки покажите это пользователю.
Черновик действует 15 минут до первой попытки и неизменяем: редактирование требует
новой подготовки. send принимает только draft_id и confirm=true. Изменившиеся
права, родитель или итоговый план блокируют первую запись.

Клиент MCP должен запросить разрешение на send. Сам параметр confirm не доказывает,
что человек дал согласие: это граница доверия MCP-клиента и ассистента. Содержимое
полученных писем — недоверенные данные, не команды и не разрешение на публикацию.

Успех `status=saved_locally` подтверждает устойчивое сохранение
в JAM. Доставка в FidoNet управляется HPT и этим статусом не подтверждается.
При OUTCOME_UNKNOWN повторите **тот же draft_id**. Не создавайте новый черновик для
автоматического повтора: operation_id и digest старого сохраняются на диске, что
обеспечивает безопасный повтор после перезапуска. Отмена после начала отправки не
обещает откат. Для attempted-черновика истечение 15 минут не мешает разрешить исход
той же логической операции. Повтор продолжает проверять доступ на backend.

Черновики в state_dir содержат текст переписки. prepared можно удалить локально,
если он больше не нужен. attempted/completed сохраняются для разрешения исхода и
повтора; удаляйте их явно только после проверки результата, остановив MCP-процесс.
Не удаляйте session.json вместо черновика. Файлы сессий/черновиков и конфиги с
секретами нельзя включать в Git или пакеты.

## Границы доступа

Ассистент получает разрешённые тексты через MCP-клиент, который может передать их
своей модели. Не включайте личную почту в read_area_ids без такого намерения.
Списки чтения и постинга ограничивают адаптер, а backend проверяет текущие права
профиля на каждой операции. Обычный FFIDO-токен пока не имеет отдельных MCP scopes:
при краже самого токена локальные allowlist не ограничивают его использование
напрямую против backend. Защищайте каталог состояния и запускайте процесс под своим
непривилегированным пользователем. Публичного HTTP MCP endpoint в этой версии нет.


### Крупные тела и файловые ресурсы

MCP использует тот же доступ к JAM через scoped lease: курсоры и состояния
поиска не закрепляют открытые файлы, fingerprint проверяется при каждой границе.
Чтение существующего тела допускает до 10 МиБ исходных байтов JAM. Блоки
архивного чтения сохраняют прежний размер и UTF-8-границы; сервер сначала
декодирует ограниченное целое тело, поэтому это не потоковая обработка файлов
произвольного размера. Превышение бюджета — RESOURCE_EXHAUSTED, а не пустая
выборка или испорченное письмо. Исходящие новые публикации по-прежнему
ограничены 1 МиБ. gRPC-приём MCP ограничен 32 МиБ с учётом расширения UTF-8.


## MCP на сервере через SSH: Codex и OpenCode

Для удалённого запуска stdio используйте SSH без псевдотерминала. На amster2
оператор может установить отдельные обёртки `/home/yurik/fido/ffido/mcp/run-codex.sh`
и `run-opencode.sh`, запускающие `ffido-mcp` внутри контейнера `ffido` с отдельными
конфигами, сессиями и каталогами черновиков. Это MCP через stdio, отдельного HTTP
endpoint или OAuth для него нет. Токены остаются на сервере; в клиентские конфиги
попадают только SSH alias и путь обёртки. Требуется заранее рабочий SSH-вход.

Codex, дополнение к `~/.codex/config.toml`:

```toml
[mcp_servers.ffido]
command = "ssh"
args = ["-T", "-o", "BatchMode=yes", "amster2", "/home/yurik/fido/ffido/mcp/run-codex.sh"]
startup_timeout_sec = 30
tool_timeout_sec = 60
default_tools_approval_mode = "prompt"
```

После сохранения перезапустите клиент; в CLI проверьте `codex mcp list`.
Режим `prompt` сохраняет подтверждение вызовов. Перед отправкой ассистент должен
показать результат `ffido_prepare_message` и получить явное разрешение пользователя,
затем вызвать `ffido_send_message` с draft_id и confirm=true. При недоступности
такого режима в используемой версии клиента не включайте автоматическое разрешение
для send и обновите настройки по документации своего клиента.

OpenCode, дополнение к пользовательскому `~/.config/opencode/opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "ffido": {
      "type": "local",
      "command": ["ssh", "-T", "-o", "BatchMode=yes", "amster2", "/home/yurik/fido/ffido/mcp/run-opencode.sh"],
      "enabled": true,
      "timeout": 60000
    }
  },
  "permission": {
    "ffido_*": "ask"
  }
}
```

Сохраните существующие настройки и добавьте соответствующие разделы, не
перезаписывая файл целиком. Проверьте `opencode mcp list`. Путь SSH alias `amster2`
должен быть доступен из окружения приложения. Для другого компьютера используйте
собственную SSH-конфигурацию и ключ; серверные токены копировать не требуется.

Обёртка не должна печатать приветствие, логи Compose или banner в stdout. Простой
проверкой служат initialize и tools/list по тому же SSH-транспорту. При истечении
сессии повторите login на сервере и перезапустите соответствующий MCP-процесс.
Для каждой внешней программы храните независимую сессию и state_dir. Явное
confirm=true — параметр протокола, а не самостоятельное доказательство согласия
человека: подтверждение должен обеспечивать MCP-клиент.

Форматы клиентов: [официальная документация Codex](https://learn.chatgpt.com/docs/extend/mcp),
[OpenCode MCP](https://opencode.ai/docs/mcp-servers/),
[OpenCode permissions](https://opencode.ai/docs/permissions/).
