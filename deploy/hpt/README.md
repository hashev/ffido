# Локальная политика HPT на amster2

Это дополнение для внешнего HPT worker, а не часть официального образа FFIDO.
Оно соответствует локальным JAM узла: обычные эхи KOI8-R, область `utf-8` UTF-8.
Включение для другого набора кодировок исказит сообщения.

`build-hpt.sh` собирает закреплённые Husky-зависимости в `/opt/ffido-hpt`
и применяет `hpt-transport.patch` с `git apply --check` к HPT
`c2a91d64cee0e6cd357376d30c9285ee3f9c624f`. Для Dockerfile worker:

```dockerfile
COPY build-hpt.sh hpt-transport.patch /opt/ffido-local/
RUN sh /opt/ffido-local/build-hpt.sh
ENV FFIDO_HPT_KOI8_CP866=1
```

При включённой политике HPT использует существующий KOI8-R → CP866 `outtab`
для обычных эх и формирует один `CHRS: CP866 2` в экспортируемой копии.
Для `utf-8` (регистр имени незначим) обходит `outtab`, формирует
`CHRS: UTF-8 4` и обходит входящий `intab` при записи в эту JAM.
Для обычных эх требуются `RecodeMsgBase on` и обе таблицы. Если они отсутствуют,
отключены либо загрузчик таблиц возвращает ошибку, HPT завершает запуск с
ошибкой конфигурации до обработки сообщений.
Без переменной со значением `1` поведение upstream сохраняется.
Правила netmail, подписки HPT и исторические JAM не меняются.
Существующая нормализация исходящего текста FFIDO также сохраняется.

На amster2 файлы устанавливаются в `/home/yurik/fido/ffido/ops`;
сборка — `docker compose build ffido-tosser` из `/home/yurik/fido`.
Перед заменой запущенного worker обязательны согласованная резервная копия,
проверка на изолированных базах и остановка действующего worker до конца его цикла.
Не запускайте raw HPT параллельно координированному `ffido-run-hpt`.
При смене upstream повторите проверку; не удаляйте patch ради успешной сборки.

Проверочный сценарий `verify-amster2.py` запускается Python-окружением VPS с grpcio
и сгенерированными модулями FFIDO в `ffido/probe`. Нужны локальные образы FFIDO,
нового worker и контрольного worker до исправления, а также TLS-файлы узла.
Сценарий не изменяет рабочие базы, очереди и конфигурацию: он создаёт отдельные
JAM в `ffido/verification/hpt-charset`, поднимает временный FFIDO на localhost:18082,
отправляет сообщения только в эти JAM и запускает HPT с `--network none`.
Порт и имя временного контейнера должны быть свободны.

```sh
cd /home/yurik/fido
ffido/venv/bin/python ffido/ops/verify-amster2.py \
  --image ffido:encoding-review-local-20261023 \
  --worker ffido-tosser:local \
  --control-worker ffido-tosser:before-hpt-transport-20261023
```

Проверяются публикация и ответ через API → локальная JAM → HPT scan → PKT →
HPT toss второго узла → чтение API. Независимый декодер проверяет байты тела,
темы, имён и CHRS, reply-связь и отсутствие повторного экспорта. Прежний HPT
и новая сборка без включения политики должны воспроизводить исходную ошибку.
Исторические испорченные UTF-8 записи этот сценарий не исправляет.

Подготовка обновления FFIDO, текущая блокировка схемы и восстановление описаны
в [инструкции обновления amster2](ffido-upgrade.md).

## Восстановление исторической базы utf-8

Текущая политика HPT предотвращает перекодировку новых UTF-8 сообщений, но не
восстанавливает старые. Проверка 29.10.2026 обнаружила 30 писем, 55 невалидных
UTF-8 тел/полей из 120 значений. Все 55 обратимы через побайтовое KOI8-R → CP866
с последующим строгим декодированием UTF-8. Это ориентир конкретного снимка,
а не разрешение исправлять любое количество полей без просмотра отчёта.

Инструмент `scripts/repair_jam_utf8.py` работает стандартным Python 3 на Linux/macOS.
Он не устанавливается в backend автоматически. Его применение к рабочей базе —
отдельная операция по явному запросу оператора, после репетиции на согласованной
копии. Обычный apply кода не запускает её.

По умолчанию инструмент только проверяет базу. Требуются существующий общий
`coordination_lock`, относительное имя базы и явный UTF-8 override в конфигурации.
Пути и config относятся к файловой системе процесса, запускающего инструмент.
На хосте amster2 `/home/fido/msgbase` из конфигурации контейнера соответствует
`/home/yurik/fido/msgbase`: подготовьте отдельный минимальный operator config
с `ftn.jam_base_path`, `ftn.coordination_lock` и `ftn.jam_encoding_overrides`,
используя хостовые пути. Lock обязан указывать на тот же inode, который видят
backend и wrapper HPT, а не на новый диагностический lock. Секреты не нужны.

Пример такого config (перед использованием сверить путь lock с рабочей конфигурацией):

```json
{
  "ftn": {
    "jam_base_path": "/home/yurik/fido/msgbase",
    "coordination_lock": "/home/yurik/fido/ffido/hpt.lock",
    "jam_encoding_overrides": {"utf-8": "UTF-8"}
  }
}
```

Для репетиции укажите корень изолированной копии и её отдельный существующий lock.
Дальнейшие команды предполагают текущий каталог с `repair-config.json` и копией
инструмента `repair_jam_utf8.py`. Отчёт, backup и marker хранить с правами 0600/0700
вне репозитория и общедоступного HTTP-каталога.

```sh
umask 077
python3 repair_jam_utf8.py --config repair-config.json --base utf-8 --report report.json
```

Dry-run берёт exclusive lock, чтобы получить согласованный снимок нескольких файлов;
при занятом lock сразу отказывает. Отчёт содержит номера сообщений, типы полей,
диапазоны, hashes и inode; текста писем нет. Уже существующий report не перезаписывается.
Неизвестные/необратимые данные, пересечения диапазонов, повреждённые длины, symlink
внутри выбранной базы и hardlink отклоняются. Лимит — 64 MiB на файл, миллион записей
индекса и 4 MiB на текстовое поле; выход за него требует отдельного разбора, а не
отключения проверок. Валидные UTF-8 поля сохраняются, даже если их историческое
семантическое происхождение неизвестно.

Перед apply завершить цикл HPT, остановить backend, ffido-tosser, jamnntpd и все
другие читатели/писатели этой базы; отключить cron, updater и supervisor, способные
их перезапустить. Проверить фактическое состояние процессов/контейнеров. Lock
защищает только координированных участников; raw HPT и jamnntpd необходимо остановить
отдельно. После остановки повторить dry-run с новым именем отчёта и просмотреть его.
Следующий marker — явное подтверждение оператора об остановке, а не команда остановки
и не автоматическое обнаружение всех сторонних процессов:

```sh
python3 - <<'PY'
import hashlib, json
from pathlib import Path
report = Path('report.json')
Path('maintenance.json').write_text(json.dumps({
    'report_sha256': hashlib.sha256(report.read_bytes()).hexdigest(),
    'stopped': ['backend', 'hpt', 'jamnntpd', 'cron'],
}))
PY
python3 repair_jam_utf8.py --config repair-config.json --base utf-8 \
  --report report.json --apply --maintenance-file maintenance.json --backup backup-before-repair
```

Backup-каталог должен отсутствовать, его родитель существовать. Инструмент создаёт
проверенную копию `.jhr/.jdt/.jdx` и `.jlr`, если он есть, с manifest/hashes, повторно
сверяет исходники и только затем пишет. Исправляются исключительно выбранные
текстовые диапазоны `.jhr/.jdt`; inode и длины файлов, номера, поколение, MsgID/REPLY,
CHRS, даты, флаги и `.jdx/.jlr` сохраняются. SQLite не открывается и не изменяется.
После записи выполняются fsync, побайтовая сверка и повторный план с нулём изменений.
При обычной ошибке записи выполняется полный откат в те же inode.

При любом сбое apply/restore сохраняйте maintenance. Два файла не заменяются атомарно;
после SIGKILL/потери питания сервисы не должны запускаться до проверки manifest и
завершения процедуры. Для прерванной операции или отката до новых записей:

```sh
python3 repair_jam_utf8.py --config repair-config.json --base utf-8 \
  --report report.json --restore --maintenance-file maintenance.json --backup backup-before-repair
```

Restore проверяет backup/hashes, inode и допустимые значения каждого байта текущей
базы; новые поступления или сторонние изменения блокируют автоматический откат.
При неполном rollback оставить сервисы остановленными для ручного восстановления
полного согласованного набора, сохранив исходные inode `.jhr`, когда это возможно.
Замена `.jhr` новым inode меняет generation и требует отдельного плана метаданных.

После успеха выполните новый dry-run с новым report: изменений должно быть ноль.
Запускайте сервисы только после проверки всего набора файлов и ожидаемого состояния
manifest. Через API проверить все страницы `utf-8`, прежние ID и счётчики; полное
чтение письма меняет read-state, поэтому использовать согласованный проверочный
профиль. Сверить прежние закладки, историю и позицию. Рабочие тестовые публикации,
ретоссинг, очистка базы и ручная замена CHRS не требуются.

### Изолированная регрессия

Расширенный `verify-amster2.py` дополнительно создаёт исторически испорченную копию,
воспроизводит INTERNAL, запускает dry-run/apply только на ней и проверяет точные
байты, API ID, прочитанность и неизменность metadata. Затем выполняет чистый
UTF-8/KOI8-R цикл HPT, описанный выше. Для установленной вне репозитория копии
укажите путь инструмента явно:

```sh
cd /home/yurik/fido
ffido/venv/bin/python ffido/ops/verify-amster2.py \
  --repair-script /path/to/repair_jam_utf8.py \
  --image ffido:encoding-review-local-20261023 \
  --worker ffido-tosser:local \
  --control-worker ffido-tosser:before-hpt-transport-20261023
```

Локальные независимые тесты: `python3 scripts/test_repair_jam_utf8.py` из корня.
Они также зарегистрированы в CTest как `JamUtf8Repair`; backend-тест
`PrivateAreasTest.HistoricalUtf8RepairPreservesApiIdentityAndMetadata` проверяет
восстановление нескольких страниц и сохранность пользовательского состояния.
