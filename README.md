# FFIDO

FFIDO — клиент FidoNet для macOS, Windows, Android и Linux и сервер для Linux/macOS,
работающий с существующими JAM-базами и конфигурацией HPT. Клиент общается с сервером
по TLS gRPC; файлы FTN и пароли тоссера не требуется копировать на телефон.

Поддерживаются чтение конференций и цепочек, публикации и ответы, персональная
прочитанность, закладки, история, личные ящики поинтов, приватные области владельца
и UUE-вложения. **Успешная отправка означает устойчивое сохранение в JAM,
а не подтверждённую доставку в FidoNet.**

[Исходники](https://github.com/hashev/ffido) ·
[Скачать пакеты](https://github.com/hashev/ffido/releases) ·
[Подготовка GitHub и выпусков](docs/github-publication.md)

Пакеты появляются после успешного полного CI и настройки release-ключа Android.
Пока это не выполнено, наличие ссылки Releases не означает наличие готового выпуска.

## Выбор пакета

| Система | Клиент | Сервер | Базовое окружение сборки |
| --- | --- | --- | --- |
| macOS Apple Silicon | DMG arm64 | tar.gz arm64 | macOS 15 |
| macOS Intel | DMG x86_64 | tar.gz x86_64 | macOS 15 |
| Windows | ZIP x86_64 | — | Windows 10/11 x86_64 |
| Linux | tar.gz x86_64 | tar.gz x86_64 | Ubuntu 24.04 |
| Android | универсальный APK | — | Android 7 / API 24 или новее |

Это начальная целевая матрица; фактический статус проверок — в
[docs/testing.md](docs/testing.md), идентичность конкретной сборки — в
`release-manifest.json` и `BUILD.json`. Если связанные macOS-библиотеки требуют более новую ОС, упаковщик указывает этот
минимум в BUILD.json и manifest; локальная сборка на новой macOS не доказывает
поддержку macOS 15. Поддержка более старых ОС и других Linux
дистрибутивов не подтверждена. iOS и Web остаются в исходниках; автоматические
пакеты для них в этот выпуск не входят. Сервер на Windows не поддерживается.

В Releases файлы `-dev.` помечены **Pre-release** — это сборки после слияния PR.
Стабильные версии имеют теги `vX.Y.Z`. Клиентские пакеты помечены `client`,
серверные — `server`; выбирайте также свою архитектуру.

## Установка клиента

Скачайте пакет и `SHA256SUMS` из одного релиза. Проверьте сумму:

```sh
# Linux
sha256sum --ignore-missing -c SHA256SUMS
# macOS: сравните результат с соответствующей строкой SHA256SUMS
shasum -a 256 <имя-пакета>
```

В PowerShell: `Get-FileHash .\<имя-пакета> -Algorithm SHA256`.
Контрольная сумма выявляет повреждение, но сама по себе не подтверждает доверие
к автору: скачивайте с официальной страницы релизов.

- **macOS:** откройте DMG, перенесите `fido.app` в Applications. Первый выпуск
  подписывается только ad-hoc, без Apple Developer ID и notarization. Если ОС
  блокирует запуск, используйте штатное разрешение для этого приложения в
  «Системные настройки → Конфиденциальность и безопасность» после проверки источника.
  Не отключайте Gatekeeper глобально.
- **Windows:** распакуйте ZIP целиком и запустите `fido.exe`; DLL и `data/` должны
  оставаться рядом. Может потребоваться Microsoft Visual C++ Redistributable
  2015–2022 x64. Пакет пока без Authenticode; SmartScreen может показать предупреждение.
- **Linux:** установите runtime-библиотеки и доступный desktop keyring:
  `sudo apt install libgtk-3-0t64 libsecret-1-0 libjsoncpp25 gnome-keyring`.
  Распакуйте tar.gz, откройте каталог пакета и выполните `./fido`. Файл desktop
  при переносе в меню должен иметь абсолютный Exec, соответствующий месту установки.
- **Android:** скачайте APK, разрешите установку именно из используемого браузера
  или файлового менеджера и установите его. Для обновлений нужен APK с тем же ID
  и постоянной подписью. Debug APK из CI не является публичным пакетом.

Публичный application ID — `io.github.hashev.ffido`. Ранее установленные локальные
сборки `com.example.fido` считаются отдельным приложением. Автоматического переноса
профилей и Keychain нет; сохраните настройки и войдите в новом приложении заново.
Удалять прежнюю сборку до проверки новой не требуется.

### Первое подключение

Получите у оператора **HTTPS endpoint FFIDO**, имя, FTN-адрес и пароль вашего
линка HPT. Введите их в форме подключения. Сертификат должен быть доверенным
и содержать DNS-имя сервера в SAN; проверку TLS отключать не нужно. Адрес мейлера
BinkP не является endpoint FFIDO.

Нативный клиент хранит сессионный токен и пароль HPT в защищённом хранилище
устройства; для Linux требуется работающий keyring. Пароль привязан к серверу,
FTN-адресу и локальному профилю, подставляется скрыто и удаляется при явном выходе.
При смене адреса или сервера подставленный пароль очищается. Браузер пароль не сохраняет. Прочитанность и закладки
синхронизируются сервером между устройствами. Сессия может потребовать нового
входа после истечения срока или изменения доступа в HPT. При следующем входе
ранее не сохранённый пароль нужно ввести один раз.

Имя существующего серверного профиля повторный Login не меняет. Не выполняйте
первую production-проверку с именем вроде «Deployment verification»: используйте
настоящее имя владельца адреса. Операторское исправление имени описано в
[инструкции аккаунтов](docs/accounts.md).

macOS поддерживает независимые профили:

```sh
/Applications/fido.app/Contents/MacOS/fido --profile point1
/Applications/fido.app/Contents/MacOS/fido --profile point2
```

## Установка сервера

Нужны существующая нода HPT, JAM на локальном диске, Python 3 для wrapper,
доверенный TLS-сертификат и отдельная учётная запись ОС с доступом к нужным базам.
Одна установка backend работает рядом с HPT; сетевые файловые системы и несколько
независимых пишущих backend не поддерживаются. HPT не входит в пакет сервера.

1. Распакуйте серверный tar.gz, например в `/opt/ffido`. В `bin/` находятся
   `fidoback`, `ffido-admin`, `ffido-hpt-auth`, `ffido-run-hpt`; сохраняйте каталог
   `lib/` рядом. `share/ffido/` содержит пример конфига, лицензии и relink-материалы.
2. Создайте отдельный каталог состояния и скопируйте
   `share/ffido/config.example.json` в `/etc/ffido/config.json`. Ограничьте права
   на конфиг и каталоги ключей/состояния; не запускайте сервер от root.
3. Настройте `auth.hpt_config_path`, разрешённые конференции, `ftn.jam_base_path`,
   SQLite и общий coordination lock. Пути FFIDO разрешаются относительно его конфига.
4. Укажите `server.tls_certificate`, `server.tls_private_key`, адрес и порт.
   Для доступа извне используйте выбранный интерфейс вместо `127.0.0.1`, DNS,
   firewall и прокси с HTTP/2 gRPC, если он нужен.
5. Запустите сервер из терминала и проверьте подключение до настройки службы:

```sh
/opt/ffido/bin/fidoback /etc/ffido/config.json
```

После проверки используйте supervisor ОС (systemd/launchd) с постоянным
пользователем, путями и правами. Для Web требуется отдельный
[Envoy gRPC-Web gateway](tools/gateway/README.md); нативным клиентам он не нужен.

Подробные настройки и ограничения: [README backend](apps/backend/README.md).

### HPT в Docker и кодировка JAM

Если HPT видит `/home/fido`, а backend — `/srv/fido`, настройте:

```json
{
  "auth": {"hpt_config_path": "/srv/fido/hpt.cfg", "session_key_path": "/var/lib/ffido/session.key"},
  "ftn": {
    "areacfg_path": "/srv/fido/areas.cfg",
    "jam_base_path": "/srv/fido/msgbase",
    "default_encoding": "KOI8-R",
    "path_mappings": [{"from": "/home/fido", "to": "/srv/fido"}],
    "coordination_lock": "/srv/fido/ffido.lock"
  }
}
```

Это фрагмент для объединения с полным примером. Настройки самого FFIDO — локальные
пути; отображляются пути из HPT, включая активные include и JAM. `areacfg_path`
в mapped-режиме должен соответствовать активному подключённому файлу HPT.
Совпадает наиболее длинный префикс по компонентам, правило применяется один раз.
Выход из JAM-корня и несогласованные физические файлы отклоняются.

По умолчанию используется CP866. `default_encoding=KOI8-R` задаёт кодировку новых
публикаций и чтения без CHRS/с IBMPC. Поддерживаемый явный CHRS письма имеет приоритет
при чтении. История не перекодируется; непредставимые символы отклоняются без
повреждения базы.

Если HPT перекодировал локальную JAM, сохранив прежний CHRS, задайте точные
правила `ftn.jam_encoding_overrides` (пути относительно `jam_base_path`, без `.jhr`):

```json
"jam_encoding_overrides": {
  "ru.anecdot": "KOI8-R",
  "utf-8": "UTF-8",
  "ffido-points/p1": "KOI8-R"
}
```

Для указанных баз правило имеет приоритет над любым CHRS при чтении тела, темы
и имён; новые записи используют эту кодировку и согласованный CHRS. Исторические
файлы не переписываются. Остальные базы сохраняют прежние правила. Регистр пути
значим; wildcard не поддерживается. Неверная кодировка, отсутствующая JAM и разные
правила у физических алиасов (включая отсутствие правила у одного алиаса) запрещают
запуск сервера/admin. После изменения перезапустите сервер и тоссер; используйте
одну конфигурацию в обоих процессах. Не назначайте KOI8-R области с реальным UTF-8.

**Отображение путей не заменяет блокировки.** Все HPT-операции с общими базами должны
выполняться через wrapper с тем же физическим lock-файлом, доступным обеим сторонам:

```sh
/opt/ffido/bin/ffido-run-hpt --config /etc/ffido/config.json -- \
  /usr/local/bin/hpt -c /srv/fido/hpt.cfg scan -w -a RU.TEST
```

Для Docker нужны bind mount lock-файла и синхронный запуск HPT с общей lease.
`docker exec -d` не обеспечивает поддерживаемую координацию. Полный point-mail
цикл требует одной среды выполнения admin и HPT. Детали — в README backend.
Не запускайте независимый cron HPT в обход wrapper.

### Личные ящики и приватные области

Вход определяется HPT-линком; отправитель берётся из серверного профиля.
У поинтов личные ящики включаются явной настройкой `point_mail`; сначала подготовьте
ящики административной командой, затем запускайте полный согласованный цикл.
Обычный RPC не запускает HPT. При неопределённости транспорта данные сохраняются
для восстановления, повторная внешняя доставка не обещается.

```sh
/opt/ffido/bin/ffido-admin provision-mailboxes /etc/ffido/config.json
```

Поля ingress/egress, команды cycle, восстановление и требования `Route nopack`
описаны в [README backend](apps/backend/README.md). Владельцы задаются через `auth.owner_addresses`: они получают чтение и постинг
всех согласованных JAM-эх узла, а также доступ к приватным областям владельца.
Чужие персональные mailbox остаются закрытыми. Права обычных пользователей
по-прежнему основаны на подписках HPT. Подписывать собственный адрес узла в HPT
для владельческого доступа не требуется. Не используйте реальные базы для ознакомительных тестов.

## Обновление, резервирование и диагностика

Сначала сделайте согласованную резервную копию конфигов, SQLite, ключа сессий
и всех JAM companions при остановленных backend/HPT. Не копируйте `.jhr/.jdt/.jdx`
независимо во время записи. Сохраняйте права, владельца и расположение общего lock.

Распакуйте новую версию в отдельный каталог, сохраните конфиг/состояние вне него,
остановите процессы, переключите binaries и проверьте запуск. Миграция SQLite
может сохранить старую прочитанность отдельно и начать новую; закладки/история
сохраняются. Не откатывайте только бинарники поверх изменённой схемы без проверки
совместимости и backup. Pack/replacement JAM требует окна обслуживания.
Не удаляйте instance/coordination locks при работающих процессах.

При удалении клиентских бинарников профили и сессии могут остаться в системном
хранилище. Для отзыва доступа выполните выход/отзыв сессии; базы сервера не удаляются
вместе с клиентом. Смена постоянного Android-ключа нарушает обычное обновление APK.

| Симптом | Проверить |
| --- | --- |
| TLS/соединение не устанавливается | DNS, HTTPS endpoint, firewall, HTTP/2, срок и SAN сертификата |
| Вход отклонён | FTN-адрес, пароль HPT, актуальные include, доступ линка |
| Конференции недоступны | ACL HPT, активный areas include, path mapping и JAM-корень |
| Не читается кириллица | CHRS письма и default_encoding; не перекодировать JAM вслепую |
| HPT/сервер ждёт lock | единый wrapper, правильный физический lock, зависшие процессы |
| Нельзя сохранить сессию Linux | запущенная служба Secret Service/keyring |
| Отправка сохранена, но не доставлена | полный операторский HPT-цикл и транспортная диагностика |

Расширенные руководства: [проверки](docs/testing.md),
[ручной план](docs/manual-test-plan.md), [UUE](docs/uue-attachments.md),
[frontend](apps/frontend/README.md). Перед отправкой диагностики удаляйте пароли,
токены, реальные конфиги и частную переписку.

## Сборка из исходников

Монорепозиторий: `apps/frontend/` — Flutter, `apps/backend/` — C++23,
`contracts/` — общий protobuf, `openspec/` — спецификации. Версии и матрица CI
закреплены в `.github/workflows/` и `scripts/release/`.

Flutter 3.47.7 / Dart 3.13.5; Java 17/Android SDK для Android, Visual Studio C++ для Windows,
Xcode для macOS, GTK/libsecret development packages для Linux. Backend требует
CMake, C++23 compiler, Python 3, OpenSSL, c-ares, RE2, zlib и согласованные
Protobuf 36.2/gRPC 1.84/Husky. Для backend на macOS нужен Xcode 26 или новее:
Xcode 16 ещё не предоставляет стандартный `std::stop_token`. CI использует
установленный Xcode 26.3; при нескольких Xcode выберите его через `DEVELOPER_DIR`.

```sh
# Из корня, Linux/macOS; зависимости устанавливаются только в build/release-deps.
bash scripts/release/dependencies.sh
cmake -S . -B build/backend -C build/release-deps/prefix/ffido-cache.cmake \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build/backend --parallel 4
FFIDO_TEST_HPT="$PWD/build/release-deps/prefix/bin/hpt" \
  python3 scripts/release/check_ctest.py build/backend
python3 scripts/check_cpp.py --build-dir build/backend

cd apps/frontend
flutter pub get --enforce-lockfile
flutter analyze --no-pub
flutter test --no-pub
flutter build linux --release # либо macos/windows/apk на нужной ОС
```

Существующий `build.sh` также предоставляет test/check/proto/coverage и отдельные
sanitizer-сборки; их команды описаны в [документации проверок](docs/testing.md).
Санитайзеры требуют согласованных instrumented зависимостей.

## Docker

Сборка Linux amd64, запуск с постоянными данными и публикация `hashev/ffido`:
[инструкция Docker](docs/docker.md).

Для установки с командами проверки и обновления сервера используйте managed layout
`releases/<версия>` + `current`, описанный в
[руководстве backend](apps/backend/README.md#управляемое-обновление-установленного-сервера).
Клиентский экран «Обновления приложения» доступен до входа на сервер; macOS ad-hoc
после обновления может запросить Keychain или повторный вход. Первый переход
на сборку с updater выполняется вручную.
